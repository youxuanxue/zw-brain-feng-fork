## 一、动机（一句话）

CLAUDE.md「## 决策记录」段**每会话整份入上下文**。memory §6「精品柜净零策展」对 memory 严格执行下架，但 **D-索引只增不减**——61 条 D-决策已聚合 ~1.5 万字符，且新条普遍逼近段 68 守卫的 900 字符上限。另有一道聚合字符守卫（A5 切片在建）会把当前聚合值**棘轮钉死**防再膨胀；**本提案是那道守卫之后、真正"降上限"的内容重构**：把已落地、Why/How 已在外部全文的决策下沉为一行指针，让索引回到「日期+scope+一句裁决+全文指针」的段头契约本意。

字符分布呈**双峰**，这是切分口径的核心事实：

- **老条（D1–D44，GATE-1/1.1/早期 Retrofit）**：绝大多数 24–234 字符（D8=24、D6=34、D28=50…），**已经很短**。它们多 → 拖累条目计数与可读性，但**贡献的字符极少**。

> **结论先行**：单纯归档"多而小"的老条只削减计数、几乎不降字符（见 §五方案 B）；真正降上限的杠杆是**压缩 Why/How 已在外部 `-Dxx.md` 全文的大新条**（见 §五方案 A 第 2 类）。提案据此给**两机制并用**的方案 C。

## 四、切分判据（可执行、机械可判）

一条 D-条目**保留在 CLAUDE.md 活跃上下文**当且仅当满足以下任一：

1. **元规则**：GATE 元规则条 `D28`，及承载「现行硬约束速查」块所引硬约束的父条（`D33` 含 D33.d、`D36` 含 D36.c——速查块直接引用）。
2. **被交叉引用**：拥有 §3.2 列出的"真"子决策锚点（≥2 次、已排除 `.md` 假锚点）——即 **{D31,D32,D33,D34,D36,D42,D43,D45,D46,D47,D52,D56,D57}**。锚点速记必须随父条留在上下文，否则全仓 `Dxx.y` 引用悬空。
3. **近期承重**：最近 N 条（**推荐 N=12，即 D50–D61**）——近期决策仍是日常裁决的活跃参照（如 D61 部门隔离、D58 alembic、D55 权限对齐）。

**其余全部下沉**为一行指针。判据 1–3 均可由脚本机械派生（编号集合 + §3.2 锚点正则 + 编号阈值），无语义判断残差——符合 memory「确定性自动化只在可机械化边界内」。

## 五、归档机制

### 5.1 归档落点

- **统一归档台账**：新建 `docs/decisions/d-index-archive.md`，承载所有下沉条目的**完整原文**（逐字搬运现有 CLAUDE.md 条文，不删信息、只换位置），按 D 编号升序、保留原 GATE 分组小标题。
- CLAUDE.md「## 决策记录」段对每个下沉条目**只留一行指针**，格式固定：

  ```
  - Dxx [日期] scope — <一句话裁决> → 全文 docs/decisions/d-index-archive.md#Dxx（及既有 docs/decisions/<file>.md）
  ```

  示例（D8）：`- D8 [04-18] UI ≤10 场景页 → docs/decisions/d-index-archive.md#D8`
- 已有专属外部全文的条目（§3.1），指针**优先指向该专属全文**，归档台账只做兜底锚。

### 5.2 与聚合守卫解耦

A5 切片在建的聚合字符守卫钉的是 **CLAUDE.md 决策段聚合值**，与归档台账解耦：归档台账 `docs/decisions/d-index-archive.md` **不**进每会话上下文、**不**计入该守卫阈值。本重构落地后：

1. 先按 §六实测的归档后聚合值，**把守卫阈值从棘轮当前值一次性下调到新值**（守卫的 `MAX_AGGREGATE` 常量改一个数）。
2. 此后棘轮在新低位继续防再膨胀。归档台账自身不设聚合守卫（它本就是"溢出柜"，增长不烧每会话 token）。
3. 段 68 单条 ≤900 守卫**不变**：归档指针行天然远短于 900；保留的活跃大条仍受 900 单条上限约束。

## 六、量化收益（实测，N=12 推荐方案 C）

一行指针按固定模板实测均长 ~75 字符/条估算。

| | 现状 | 重构后 | Δ |
| --- | --- | --- | --- |
| D-条目聚合字符 | 14,760 | ~13,836 | **−924（−6%）** |

**坦白说明（反测量假象）**：N=12 窗口下净削减仅 ~6%，因为归档的 38 条里 30 条是 D1–D44 的**小老条**（搬走它们主要降计数，不降字符），而 D46–D61 的**大新条**多落在保留窗口。若要把每会话 token 真正打下来，须叠加 §七的"大条压缩"机制——见下。

## 七、叠加机制：保留大条的"指针化瘦身"（真正的降 token 杠杆）

§六实测点明：字符承重者是 **D46–D61 的大新条**，且它们**多已有专属外部全文**（§3.1）。对**保留集中、已有专属全文**的大条，把索引行从"全锚点速记"收敛为"**裁决一句话 + 被引用锚点 + 全文指针**"，把未被引用的子锚点速记移入全文：

- 例：D46(756) 现列 D46.a–g 七个锚点全文式速记；其中被全仓引用的是 D46.b/c/d/e/f/g，**D46.a 零外部引用**——D46.a 速记可移入 `feature-status-as-function-architecture.md`，索引省 ~40 字符。
- 例：D50(855)/D55(757)/D58(738) 各有专属 `-D50/-D55/-D58.md`，索引行可压到 ~300 字符（裁决 + 指针），单条省 ~450。
- 仅把 D46/D50/D55/D58/D51/D61 六条逼近上限的大条各压到 ~350 字符，即再省 **~2,300 字符**——叠加方案 C 的 924，合计 **~3,200 字符（−22%）**，且不动任何被引用锚点、不丢任何外部已存信息。

> 此机制**纯机械可判**（"已有专属全文 ∧ 子锚点零外部引用 → 速记下沉"），是 §六之外的第二旋钮。建议与方案 C **一并签**，二者正交。
