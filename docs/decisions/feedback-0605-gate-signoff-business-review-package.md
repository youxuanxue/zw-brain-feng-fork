## 1. 找数据可见性口径（反转 D45.b）

- **诉求**（6.5#1 P0）：找数据列表当前展示「待发布」资源且带申请按钮（截图 `lzp自测申请·待发布` 仍可申请）；业务要求「只展示已发布，只有已发布才可申请」。
- **核查**：`discovery_snapshot_projection.py` 现行 `_DISCOVERABLE_STATUSES = {active, approved_pending_publish}` 是 **D45.b 主动决策**（曾把"待发布"当"即将可用"纳入发现页）。本诉求是对该口径的**反转**。

| 候选项 | 建议（Jobs 视角） | 业务方判定 |
|---|---|---|
| 只展示已发布 active；未发布不可见、不可申请 | **采纳** — 消费端只应看到可用资源；"待发布"出现在申请入口会误导用户、产生申请不到的挫败 |  采纳  |
| 维持现状（含待发布，标灰提示） | 排除 — 与"只有已发布才可申请"直接冲突，且 D45.b 当初的"即将可用"假设未被用户接受 | ☐ |

- **签字含义**：通过 = 反转 D45.b，发现视图收敛为 active；连带"命中 N 条"计数下降属预期。

## 2. 资源类型口径收敛（库表 / 文件 / API）

- **诉求**（6.5#4 P0，现场已达共识）：资源挂接缺文件夹 / 链接注册入口；既然不补这两类注册，就要把找数据列表里的文件夹 / 链接资源一并删除（不能列表有、注册无）。
- **核查**：挂接侧本就只支持库表 / 文件（API 走独立入口）；但代码 `resource_kind` 是自由字符串，归一化白名单与详情分型仍把 folder/url 当一等公民。旧库真实数据中**文件夹类仅 1 条、链接类 0 条**（dump 命中：`old/10示例数据/dump-dsp_catalog-202604271409.sql`），影响面极小。CLAUDE.md **无** 资源类型口径的 D 记录。

| 候选项 | 建议（Jobs 视角） | 业务方判定 |
|---|---|---|
| 只支持库表 / 文件 / API，剔除文件夹 / 链接（列表 + 筛选 + 详情一并退役） | **采纳** — 聚焦三类高频；杜绝"能看不能办"的入口断裂；真实数据近乎为空，收敛代价极低 | 采纳 |
| 保留四类 + 补齐文件夹 / 链接注册入口 | 排除 — 为低频长尾建整套注册表单，违背聚焦与减法 | ☐ |

- **签字含义**：通过 = 补登 D「资源类型只支持库表 / 文件 / API」入架构 §11。

## 3. 数据服务入口范式（代理服务注册）

- **诉求**（6.5#6 P0）：「API 服务化 / 选择待服务化 API」看不懂、无服务来源管理页；应改为「代理服务注册」——用户输入原始接口地址、代理到平台共享、与数据目录关联（对标旧「融合服务管理系统-创建代理服务」）。
- **核查**：当前 `P5ApiServiceWizard.vue` 是演示壳（下拉取自写死的 seed 服务，仅提交审核 / 探测）。后端 `resource.api.register` 已注册、可接代理地址（`channel_binding.endpoint_ref`），但前端零调用——**模型已有、缺自助注册 UI**。属既有 `dsp-dataservice-reconstruction-plan-v1.md`（A 类复活）明文落点。

| 候选项 | 建议（Jobs 视角） | 业务方判定 |
|---|---|---|
| 重写为「代理服务注册向导」：用户输入原始地址 + 关联目录，接 `resource.api.register` | **采纳** — 对齐旧平台心智与真实流程；后端能力现成，主要是接线；纳入 dsp-dataservice plan 执行轨 | 采纳  |
| 维持「选已有 API」范式，仅改文案 | 排除 — 范式本身错（选 vs 建），改文案治标不治本 | ☐ |

- **签字含义**：通过 = 确认范式变更并纳入 dsp-dataservice plan。

## 4. 供数信息架构（P5 重排 vs 拆独立系统）

- **诉求**（6.5#8 P0）：供数据应突出「目录 / 资源 / 服务的注册提供流程」，但当前部门管理员 / 操作员进「供数据」首屏是供需对接 / 异议响应的待办计数，弱化了供数主线，用户不知如何注册目录 / 资源；建议把目录系统、资源系统独立出来（借鉴旧系统）。
- **核查**：旧平台「目录管理 / 资源系统 / 服务管理」确为 3 个独立顶级系统（角色菜单 v5 实证），部门角色工作重心是「编目→挂接→审核→发布」。zw-brain 已按 D39 / §5.2.1 **有意收敛**进单一 P5（已 sign-off 的减法）。现状问题是 **P5 页内** 把供需对接 / 异议放在首屏主视觉、供数主动作降级为页头小链接——是页内 IA 问题，不必然推翻"两旅程"骨架。capability / 契约不变，纯 WebUI 投影。

| 候选项 | 建议（Jobs 视角） | 业务方判定 |
|---|---|---|
| **方案 a**：P5 页内重排——「在线编制 / 资源挂接 / 发布」升为首屏主卡，供需对接 / 异议降为次区 | **建议先做** — 直击"找不到如何注册"的体感，不动 D39、不破 ≤10 页、可快速验证 | 采纳，并酌情考虑呈现供数侧的目录管理、资源管理情况。 |
| **方案 b**：供数组拆「目录管理」「资源管理」独立子页 / 二级导航（含版本 / 状态视图） | 视试用反馈再议 — 修订 D39 且破 D1/D8「≤10 页」，须同时指定砍哪个导航项；代价大 | 拒绝 |
| 维持现状 | 排除 — 用户已明确反馈"弱化供数、找不到注册入口" | ☐ |

- **签字含义**：选 a = 纯实现，不进新 GATE 修订；选 b = 修订 D39 + 登记减法项，须 sign-off。

## 5. 业务运营员待办职责口径

- **诉求**（6.4#11 P2，业务验收"未修改完全-权限不对"）：业务运营员待办应是「待发布目录 / 待发布资源 / 待受理申请 / 待受理异议 / 待汇总需求」。
- **核查**：`workbench_backlog_projection.py` 现给「待**审核**目录 / 待**审核**资源 / 待补全用途」——审核是部门管理员职责、发布才是业务运营员职责，故"权限不对"=把管理员的审核待办错配给了运营员。6.4#11 答复原文已白纸黑字给出正确口径。

| 候选项 | 建议（Jobs 视角） | 业务方判定 |
|---|---|---|
| 改为「待发布目录 / 待发布资源 / 待受理申请 / 待受理异议 / 待汇总需求」 | **采纳** — 与角色职责一致，答复原文已界定；去掉错配的审核类待办 | 采纳  |
| 维持现状（含待审核类） | 排除 — 把管理员职责呈现给运营员，权限语义错 | ☐ |

- **签字含义**：通过 = 该答复落 `.testing/signoff/` 账本作为口径依据，按职责重写待办投影。
