  本签字确认后，A 类才进入按 Wave 执行。

## 启动硬前置（sequencing）

- A 类落地**散在多个 Wave**，不是一次性：网关心跳/调用统计（Wave 0，部分已随 e6 网关心跳落地）
  → API 服务资源化（Wave 1）→ 服务发布审批（Wave 2，**依赖 R14 三引擎，F8 已签**）→
  orchestrator 外部化（Wave 3）。
- **唯一前置**：Wave 2 服务发布审批节点复用 R14 审批流引擎（已 F8 sign-off），无新增上游。
  本签字是**形态 + 节奏确认**，不立即铺全部代码。

## 概念边界澄清（防"又把旧服务后台搬回来"误读）

| | 数据服务能力面（本方案） | 旧「服务管理后台 / BSP / 门户」（不做） |
|---|---|---|
| 用户怎么用 | API 服务**作为资源**进 J1 主旅程：P2 发现 → P3 申请 → P4 领凭据调用 | 用户切到独立"服务管理后台"翻菜单 |
| 服务治理动作 | 注册/变更/发布/撤回/撤销 = **写 Capability**（走统一审批 + 审计链路） | 旧 `ServiceManageController` 系列后台页 |
| 网关运行监控 | **B1.1 只读投影** + 对接集团运维（心跳/调用统计不伪装成业务报表） | 旧 hystrix-dashboard / 37 页运行监控 |
| 旧表/旧 URL | **不复刻**，只吸收承重语义 | 旧 `dsp-service-mgmt` schema + URL 兼容 |

> 一句话：**A 类不是"把旧服务后台复活"，是"让 API 服务像目录一样能被找、被申请、被调用"**——
> 能力进主旅程，监控进后台只读，长尾编排外部化。
