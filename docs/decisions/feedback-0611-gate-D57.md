## 裁决一 ｜业务运营员「待受理异议」：不删，补受理面

- **反馈原文**（6.9#3，彭玺）：「业务运营员没有工作台中显示的待受理异议详情，部门管理员有，在业务运营员的待办删掉」。
- **基准依据**：v5 异议受理 = 业务运营员；D55③ 已签（业务运营员保留受理/初级审核）。后端 `objection.case.accept.execute = {ROLE_ORGAN_MANAGER, ROLE_BUSIAUDIT}`（`policy.py:315`）口径正确，但全 WebUI 现无任何页面消费该能力（grep 仅 `pages.generated.ts` 注册行 + `pageAccess.ts:63` 注释）。
- **裁决**：**拒删待办，补齐受理面**——异议收件箱纳入 submitted 态案件 + 接通 `objection.case.accept`。反馈的真实痛点是「有待办、点不到可办理处」，删待办是杀病人治病；修可达性正是现有代码方向。
- **实施承接**：R6（P1）：`/provider/inbox/objection` 收件箱（`pageAccess.ts:64`，MANAGER+BUSIAUDIT）补 submitted 态列示 + 受理动作。证据 `/tmp/wf0611/U5-工作台待办与建议/busiaudit-objection-inbox.png`、`busiaudit-objection-detail.png`。
- **风险与回退**：纯增受理面、不动角色集与状态机；如业务方坚持删待办，属推翻 v5+D55③，须另走 D28 重签。

## 裁决八 ｜反向编目审核改两级管线（唯一改变现行已签口径项，状态机变更）

- **反馈原文**（6.10#17，彭玺）：「部门操作员、部门管理员还需要反向编目及审核，需要同级展示」；承 6.9#6（彭玺）：「反向编目审核无法完成操作」。
- **基准依据**：现行反向草稿审核仅 BUSIAUDIT 一级（`policy.py:380-381` `reverse_draft.confirm/reject = {ROLE_BUSIAUDIT}`）；正向编制是两级（管理员部门审 → 业务运营员平台审）。两套审核体系并存违流程极简；操作员自审违「做的人不审自己」。
- **裁决**：①**审核对齐 v5 两级管线**——反向草稿确认后进入与正向编制同一审核流（管理员部门审 → 业务运营员平台审），替换现行仅 BUSIAUDIT 一级，不另造第二套审核体系；**拒**下放操作员审核（做的人不审自己）。②**同级展示采纳**——反向编目升为供数首屏主卡与「在线编制」并列（现为页头药丸）。
- **实施承接**：状态机变更独立 PR（带 D37 验收）：审核管线复用正向编制 review 流（优先 D49 审批流引擎 schema 节点表达，承 D55④ 受理/审核两级语义）；首屏主卡改 `P5Provider.vue`。**注意 sequencing**：P0 批次 R4 只修反向编目审核收件箱数据源错配（投影改列 `source=reverse ∧ lifecycle=draft`，不动角色），本条是其后续，两 PR 勿合并实施。证据 `/tmp/wf0611/U13-反向编目全链/`（A4/B3 操作员/管理员 field-decision guard、C2 BUSIAUDIT 收件箱）。
- **风险与回退**：本包唯一推翻现行已签口径的条目（反向编目审核归属随 D54/G1 命名签过、角色门随 D55⑥/P14 调过），故单列为状态机变更必签项；回退 = 还原一级 BUSIAUDIT 审核（须重签）。

## 裁决九 ｜挂接审核：角色错位按 v5 关闭；盲批残留独立立项

- **基准依据**：v5 挂接审核 = 部门管理员、业务运营员只发布；现状 `resource.asset.review.execute = {ROLE_ORGAN_MANAGER}`（`policy.py:196`）+ `pageAccess.ts:61` hookup-review 仅 MANAGER——角色现状**正确**，业务运营员本就不该看到挂接审核详情。
- **裁决**：①**角色错位部分按 v5 关闭**（现状正确，不改）。②**独立残留立项必修**：部门管理员挂接审核收件箱是「盲批」——关联资源列全「—」、看不到被审登记信息、无驳回操作；「审核时看不到被审内容」对正确角色仍成立，违端到端与精品意识。
