## 一、先承认现状：当前的「订阅」是个语义空心按钮

zw-brain 现在点「订阅专题」，后端只写了一条 `subscription`-surface 的可见性记录（`intent=use`），
**没有任何下游实质影响**：

- 不触发任何数据供给 / 同步任务；
- 不进「我的订阅」列表（没有这个页面）；
- 不在专区有更新时通知订阅者；
- query 投影甚至不回传「你是否已订阅」，所以前端按钮点了也不变样。

换句话说：**它现在只是"记了一笔你点过"，再无其他**。这是验收暴露的真问题，但更值得先想清楚的是——**政务数据局真正需要的"订阅"应该是什么**。

---

## 二、旧平台的「订阅」考古：两个被混淆的概念

穿透旧平台数据结构（`old/12-datastructure`）+ 示例数据（`old/10示例数据`）+ 旧代码（`old/old_codes`），
发现「订阅」在旧平台其实是**两个完全不同的东西**，过去被一个词模糊掉了：

### 概念 A：「专区订阅 / 收藏」—— 弱语义，演示态
- 表：`share_zone*`（共享专区）、`user_collections_info`（用户收藏表）、`data_example_user_collection`（案例收藏表）
- **真实示例数据全部为 0** —— 专区、专区订阅、收藏，旧平台实际几乎没人用。
- 语义：把某个专区/案例「标个星」，方便下次找。**无下游业务影响**。
- 这正是 D34.a 已确认的：专区是「演示场景」占比高于「运营使用」。

### 概念 B：「资源订阅任务」—— 强语义，真业务
- 表：`dc_subscribe`（资源订阅表）、`dc_subscribe_table`（库表资源订阅）、`dc_subscribe_folder`（文件夹资源订阅）、`dc_to_subscribe`（网关授权 api 资源）
- 关键字段揭示语义：
  - `sub_organ_code / sub_organ_name` —— **订阅的是"部门"，不是"个人"**
  - `up_sub_id` —— **"国家返回订阅编码"**：订阅会上报国家平台、拿回执
  - `sub_status` —— 订阅任务有状态机（申请/生效/停用）
  - `sub_type` —— 订阅类型（库表 / 文件 / API）
- 下游：`acct_folder_job`（文件订阅统计表）、`acct_table_job`（库表订阅统计表）——
  **订阅驱动持续的数据同步任务**，并对同步量做统计。
- 语义：**A 部门向 B 部门（或上级/国家平台）订阅一份数据资源，建立"持续数据供给"关系** ——
  数据按周期/增量推送过来，不用每次重新申请。

> **一句话区分**：
> 概念 A 是「我关注这个专区」（书签级，弱）；
> 概念 B 是「我要持续拿到这份数据」（数据供给契约级，强）。
> 旧平台用「订阅」一个词盖住了两者，zw-brain 现在的实现是退化版的 A。

## 三、站在政务数据局的角度：用户到底需要哪种「订阅」？

数据局的核心 KPI 不是「页面好不好玩」，是**让数据在部门间持续、合规、低摩擦地流动**。从这个目标倒推：

### 弱订阅（概念 A）对数据局的价值：低
- 「收藏专区方便下次找」是个人效率工具，不解决数据流动问题。
- 旧平台真实数据为 0 已经证明：政务用户不靠"收藏"工作，他们靠**任务驱动**（接到一个要数的活，去找、去申请）。
- 给它加 toggle / 订阅量 / 红点，是**为演示盖楼**，不产生运营价值。

### 强订阅（概念 B）对数据局的价值：高，但它不属于"专区"
真正有价值的订阅是「**部门级数据供给契约**」，它的完整业务流程应该是：

```
1. 发现       某部门在 J1 找到一份需要长期使用的数据目录（如"医保码信息"）
2. 发起订阅    不是"申请一次性拷贝",而是"申请建立持续供给"——声明订阅周期/增量方式/用途
3. 授权审批    数据提供方（owner_org）+ 数据局审批：是否允许该部门持续获取
4. 建立供给    审批通过 → 建立数据管道（定时/增量同步任务）
5. 持续运行    数据按约定推送；供给量、时效、异常进统计
6. 变更/退订   用途消失 → 退订，管道停止，留审计痕迹
```

**关键洞察**：这个流程的载体**不是 P7 专区**，而是
- 数据目录（catalog）+ 申请/审批（J1 找数→用数）
- 数据供给任务 + 管道 + 统计（交换线 / 一表通 / 上下级交换，见 [[project_integration_yibiaotong_bridge]]）

P7 专区在这里最多是个**入口**（"从这个主题包里的目录发起订阅"），订阅的**实质业务归属在别处**。

## 四、对 F9「订阅专题」按钮的诚实结论

| 选项 | 是什么 | 数据局价值 | 该不该做 |
|---|---|---|---|
| 给现按钮加 toggle/订阅量/回显 | 把退化版概念 A 做完整 | 低（为演示盖楼） | ✗ 不建议 |
| 把按钮接到概念 B（数据供给契约） | 真业务 | 高 | ✓ 但这是**新的大功能**，跨 J1+交换线，不在 F9 范围，需独立立项 |
| 暂时移除/弱化「订阅」按钮，专区只做「发现+跳目录」 | 诚实表达"专区=发现入口" | 中（不误导） | ✓ 短期最诚实 |

**我的产品判断（待你裁决）**：

1. **F9 专区的真正价值是「发现」**——把高频跨部门主题（医疗救助/医保码/异地就医）的相关目录聚成一个入口，
   让用户少找。这个价值 ③「目录加链接跳转」直接兑现，应该做。
2. **「订阅」当前是伪需求的实现**。要么(a)短期把它降级为诚实的弱信号（甚至先不做态回显，避免假装有业务），
   要么(b)正式立项「部门级数据供给契约」作为概念 B 的真实现——但那是 J1+交换线的大功能，不该塞进 F9。
3. **真正该问的问题**：数据局现在有没有「部门持续订阅数据」的真实诉求？如果有，它的审批流、供给方式、
   和"一表通/上下级交换"如何边界划分？——这决定概念 B 值不值得立项。
