## 〇、两个哲学基石（与 dev-rules / 数字分身工作流方法论同根；硬约束映射见附录 D）

本重构的所有设计决策建立在与数字分身系统同源的两个哲学之上，并叠加政务行业的两条不可妥协的硬约束：

### 乔布斯产品设计哲学 —— 决定「做什么」「怎么做」

> "It means saying no to the hundred other good features that there are." — Steve Jobs

**核心原则**：

1. **聚焦**：旧平台 6 大块、20+ 子系统、上百个菜单。重构的第一动作不是「重写」，而是**对一千个功能说不**。`old/integrated-bigdata-platform/README.md` 中以 ⚠️ 标注的「未封版 / 不交付 / 几乎不用」功能，都是默认应被砍掉或下沉为可选 Skill。
2. **简洁但不取消可见性**：用户感知的入口是**一组极度精简的 WebUI 页面（≤10 页核心场景）+ 嵌入式 NL 加速器**。数据产品天然要求「字段精确、操作可见、状态可读」——纯对话框入口对数据产品是反模式（用户不知道能做什么 + 自然语言天然有歧义）。WebUI 是默认入口，NL 用于「跨步骤一句话穿透」与自动填表，不是替代品。
3. **端到端**：用户的核心旅程是「**我要别人的某条数据，并且要拿到**」。从「想问数据是否存在」到「数据真的进入我的数据库」必须是同一会话或同一 WebUI 旅程线，不是 5 个系统接力。
4. **设计即工作方式**：API/CLI/MCP/A2A 不是为了「时髦」，而是为了让「下一个能力」**不再以页面为代价**——能力本身是可被任何人/Agent 引用的东西。WebUI 与 4 入口共享同一套 Skill 契约，绝不双轨实现。
5. **精品意识**：重构的功能不一定多，但每一个必须达到「客户用一次就再也不愿回到老版本」的水准。

### OPC（One-Person Company）哲学 —— 决定「谁来做」「做多少」

> 一个人 + AI 数字分身 = 一个精干团队的产出。

**核心原则**：

1. **杠杆最大化**：AI Coding 写代码、Agent 监工、Headless 巡检。1 名产品 + N 个 Agent 替代旧团队 5-10 人/年的研发与运维投入。
2. **流程极简**：旧平台的「目录注册 → 资源注册 → 服务注册 → 申请 → 审核 → 数据交换 → 落地」7 步流程，能合并即合并，能 NL 一句话触发的就**不要做表单**。
3. **自动化优先**：所有「需要人类点击」的步骤必须先回答「为什么 Agent 不能替代」。回答不出来 = 砍。
4. **深度 > 广度**：只重构核心场景（资源目录 + 数据共享交换 + 国家直达），不试图一次性覆盖旧平台的全部 20+ 子系统。
5. **反脆弱**：所有规则、契约、技能注册全部代码化、版本化，不依赖任何一个工程师的记忆或一台机器。

### 政务行业叠加的三条硬约束（不能让 Jobs/OPC 把它们删掉）

1. **合规可证迹（Compliance & Auditability）**：每一次数据流通都要可被国家政策审计。所有 Agent 行为必须**强制落审计库**（同步阻塞），并可通过**区块链 adapter** 异步锚定到外部链（如数享链或客户指定的政务链），可在「合规督导」视图重放。国办规范、共享条例、数据安全法的硬要求是**审计可证迹**——上链是其常见实现方式之一，而非唯一方式；adapter 模式确保具体外部链的接口在 Phase 2/3 明确后再详设。
2. **国家上下行通道兼容（National Channel Compatibility）**：「数据直达」与国家平台的对接 API 由国家定义，本平台必须严格遵守。重构再激进，对国家平台的接口语义不能改。
3. **模型服务统一收口（Inference Platform Mandate）**：所有 AI 模型推理（LLM / Embedding / ASR / Rerank / OCR / 多模态 / 任意新增模型能力）**必须且只能**通过集团推理平台（`../pcowork/推理平台/`）提供的统一 SDK / API 调用。**禁止任何模块直连** OpenAI / Anthropic / 百川 / 智谱 / 通义 / DeepSeek / Moonshot 等任何第三方 LLM 服务商的 API。理由：合规（数据出境与未备案模型）、采购（集团已付费）、可审计（推理平台已统一记录）、可替换（一处升级 N 处生效）。详见 §4.5；preflight 段 10 强制检查。

> 这三条硬约束**写在哲学层**，是因为它们会反复触发「我能不能砍这个功能」「我能不能图省事直接调外部 API」的判断。答案：能砍 / 不能直连。删减或绕过前必须检查是否触碰这三条。

### 三个哲学的交汇

```
       Jobs（聚焦/简洁/端到端）
            │
            ▼ 决定形态
   ┌──────────────────────────────────────────┐
   │  政务大脑 = 精简 WebUI（≤10 页）            │
   │           + 嵌入式 NL 加速器              │
   │           + 独立可视化大屏（K12，对外门面）  │
   │           + N 个核心 Agent + M 个 Skill   │
   │           + 全程合规可证迹（强制审计）       │
   │           + 模型推理统一走推理平台 SDK      │
   └──────────────────────────────────────────┘
            ▲ 受约束于
            │
       OPC（自动化/杠杆/深度）   政务三条硬约束（合规 / 国家通道 / 推理平台）
```

### 1.3 这些问题指向的根因

**根因不是任何一个功能做得不好，而是产品形态本身**：

- 旧平台是「**菜单驱动 + 表单驱动**」的传统 BPM/数据治理平台
- 用户必须**学习平台的 20 个子系统**才能完成一次完整的数据共享
- 每一个新业务诉求 → 一次产品需求 → 一次功能开发 → 一次菜单新增 → 一次培训
- **扩展性靠人天投入**，不是靠平台机制

AI 原生重构的命题不是「让旧平台更好用」，而是**换一种产品形态**：让能力本身可组合、可被任何 Agent 调用、可由外部技能平台注册新能力。

## 三、设计原则与「不做清单」

> 乔布斯原则的硬约束：**砍掉的功能与保留的功能同等重要，必须在文档中显式列出与说明理由**。

### 3.1 必须保留（核心场景）

下列功能在重构后必须 100% 行为等价覆盖（用户感知的最终结果不退步），但实现形态可以激进改变：


| #   | 旧平台功能                             | 重构后形态                                                                                                                                           | 不可退步的理由                                                             |
| --- | --------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------- |
| K1  | 资源目录注册（表 / 文件 / 接口）               | `catalog.register` Skill                                                                                                                        | 全平台数据流通的元数据起点                                                       |
| K2  | 资源管理 + 数据源管理                      | `resource.register` / `datasource.register` Skill                                                                                               | 与 K1 配对，是「目录有数据」的真实证据                                               |
| K3  | 融合服务（API 化）                       | `service.publish` Skill                                                                                                                         | 数据消费的唯一出口形态                                                         |
| K4  | 申请审核（含驳回补正）                       | `request.submit` + `request.review` Skill                                                                                                       | 国家共享条例硬要求                                                           |
| K5  | 数据交换任务                            | `exchange.run` Skill                                                                                                                            | 数据真正落地的通道                                                           |
| K6  | 供需对接                              | `need.match` Skill                                                                                                                              | 双向数据流通的需求侧入口                                                        |
| K7  | 数据直达（国家上下行）                       | `national.relay` Skill                                                                                                                          | 国家政策硬要求 + 国家平台 API 兼容                                               |
| K8  | 合规督导 + 异议处理                       | `compliance.audit` + `dispute.handle` Skill                                                                                                     | 国家政策硬要求                                                             |
| K9  | 数享链上链 + 可证迹                       | 大脑统一审计总线（强制） + 区块链 adapter（数享链 / 政务链作为可插拔后端，先轻量）                                                                                                | 法律证据链                                                               |
| K10 | 三类角色 + 权限                         | Agent 上下文凭证 + Skill 级 ACL                                                                                                                       | 政务安全不可让步                                                            |
| K11 | 共享专区（行业 / 主题专区）                   | `zone.publish` / `zone.list` / `zone.subscribe` Skill + WebUI「专区」详情页（§7.3 第 10 页）；后端复用 catalog/resource 实体并附 `zone_tag` 维度                      | 是省内厅局打包对外开放数据的产品化抓手；旧平台「几乎不用」的根因是入口埋深 + 缺乏订阅机制，新形态用 Skill + 订阅事件流复活 |
| K12 | **政务大脑可视化大屏**（指挥中心 / 领导值守 / 对外汇报） | 独立的 `zw-brain-dashboard/` 部署单元（前端 SPA + 拼接屏适配）；后端只读消费 `dashboard.`* Skill（汇总 audit_event / skill_invocation / catalog 状态等已有数据），不引入新业务实体；详见 §7.7 | 政府客户场景中大屏是政务系统的标配价值载体（指挥调度 / 上级视察 / 跨部门通报）；缺位 = 大脑能力对外没有「门面」        |


### 3.2 砍掉（默认）—— 5 个低价值功能

下列在 `old/integrated-bigdata-platform/README.md` 中已经被 ⚠️ 标记为「未封版 / 不交付 / 几乎不用 / 政治敏感」的功能，**重构后默认不再实现**，除非客户实际使用证据出现：


| #   | 旧功能         | 砍掉理由                               | 兜底方案                           |
| --- | ----------- | ---------------------------------- | ------------------------------ |
| C1  | 数据资源库       | 客户为投标被迫加入，上线后无人使用（README §14）      | 真实有需求时通过 Skill 现挂              |
| C2  | 绩效考核        | 政府对部门排名政治敏感，配置后无人启用（README §16）    | 不重构                            |
| C3  | 应用案例（独立子系统） | 几乎无成功案例的真实输入（README §12）           | 下沉为 `case.publish` Skill，非独立模块 |
| C4  | 通用服务、链接资源   | 演示中明确「目前没用」                        | 删除                             |
| C5  | 指标平台        | 与数据治理中心的指标开发能力**职责重叠**（README §18） | 收敛到数据治理中心，安全中心专注风险监测           |

### 4.2 关键设计决定

### 4.4 数据模型（Agent-Native First + Adapter 层）

**设计顺序的关键反转**：不直接继承旧平台数据模型，而是**先以 Agent 能用的形式设计新模型**，再写 adapter 层把旧平台数据**单向同步 / 转换**进来。这是「Agent 友好是一等公民」原则在数据层的兑现。

#### 4.4.1 为什么不直接继承旧平台数据模型

旧模型是为「菜单 + 表单 + 工作流」设计的，对 Agent 不友好的地方至少包括：


| 旧模型问题                        | 对 Agent 的影响            |
| ---------------------------- | ---------------------- |
| 业务字段语义散落在 UI 文本（如「驳回补正」状态）   | Agent 无法用 schema 推理状态机 |
| 同一概念多套 ID（业务编号 / 表主键 / 显示编号） | Agent 跨 Skill 引用对象时混乱  |
| 状态机隐含在前端按钮逻辑                 | Agent 不能离开 UI 谈状态迁移    |
| 审计 / 上链 / 合规字段是事后补的旁路表       | Agent 写操作时容易漏审计        |
| 关系字段大量用 string join          | Agent 难以做静态校验          |
| 没有事件流概念，状态变更是「就地修改」          | Agent 无法回放、回滚、订阅、对账    |


> **如果 Agent 必须先「学会读懂旧平台」才能服务用户，「Agent 原生」就只是一个口号**。

#### 4.4.2 Agent-Native 设计原则

> **URN 是什么？（小白解释）**
>
> URN = **U**niform **R**esource **N**ame，「统一资源名称」，是一类**全局唯一、与位置无关、永不变更**的标识符（与 URL「统一资源定位符」对照——URL 告诉你「资源在哪」，URN 告诉你「资源是谁」）。
>
> 类比：URL 像「我家在 XX 路 XX 号」（搬家就失效），URN 像「我的身份证号」（搬到哪都还是我）。
>
> 在政务大脑中，每个核心实体（目录 / 资源 / 申请 / 异议 …）都有一个稳定 URN，**示例**：
>
> - `urn:zwbrain:catalog:CAT-A1B2C3` —— 一个目录
> - `urn:zwbrain:request:REQ-2026-04-18-0001` —— 一个数据申请
>
> 命名规则：`urn:<命名空间>:<实体类型>:<实体内部 ID>`。
>
> **为什么要 URN，不用旧平台的「数据库主键 + 业务编号」？**
>
> - 旧平台一个目录有 3 个 ID（`id` / `catalog_no` / `national_code`），跨 Skill 调用时容易引用错位、对账失败
> - 旧平台 ID 跟数据库表绑定，分库 / 迁移就要改所有引用
> - URN 是字符串，跨入口（API/CLI/MCP/A2A）和跨 Skill 传递、写日志、上链都不会变形
> - URN 一旦生成永不变更，即使后端存储换技术（PostgreSQL → 别的库），URN 也保持不变；下游 Skill / 审计记录 / 区块链锚点不需要任何改动
>
> 所以：**URN = 大脑里所有实体的「身份证号」**。Agent 之间、Agent 与人之间、大脑与外部链 / 国家平台之间，都用 URN 互相指认。

下列原则是上面这条「身份证号」思路的延展：

1. **每个核心实体一个稳定 URN**：例如 `urn:zwbrain:catalog:CAT-XXX`，跨 Skill / 跨入口稳定可引用，与底层存储 / 命名变更解耦。
2. **状态机显式化**：所有 status 是 enum；每次迁移落 `status_transition` 事件（from/to/by/at/reason）。
3. **意图与决策可序列化**：申请、审核、驳回、上链都对应可独立持久化与重放的事件。
4. **审计是一等字段**：每个写操作必须 emit 一条 `audit_event`，schema 强制；不允许「事后聚合」。
5. **schema 即文档**：用 Pydantic / JSON Schema 定义；自动生成 4 入口契约（API/CLI/MCP/A2A）。
6. **冗余只为读优化**：写永远只写一处；读视图允许冗余但必须可由源重建。
7. **PII 标记内嵌**：每个字段在 schema 上标 `sensitivity: public|internal|confidential|pii`，下游 Skill 自动判断脱敏。

#### 4.4.3 实体清单（首要事实来源）

```

  service              融合服务            urn + 暴露 API 契约（OpenAPI 片段）

  notification         消息通知             urn + channel(短信/邮件/IM/WebUI) + recipient URN + audit_ref
```

#### 4.4.4 Adapter 层（旧平台数据进新模型的唯一通道）

```
[旧平台]                                  [zw-brain Agent-Native 模型]
  legacy.catalog            ─┐            domain.catalog
  legacy.resource           ─┤            domain.resource
  legacy.request            ─┤            domain.request
  legacy.exchange_task      ─┤            domain.exchange_task
  legacy.dispute            ─┤            domain.dispute
  legacy.need               ─┤  adapter   domain.need
  legacy.shared_zone        ─┼──────────▶ domain.zone + zone_subscription
  legacy.application_case   ─┤            domain.case          （C3 下沉来源）
  legacy.application_center ─┤            domain.app
  legacy.user / role        ─┤            （走基础支撑迁入）
  legacy.audit_log_*        ─┘            runtime.audit_event（按 schema 重塑 + 树状级联）

[无旧平台对应、新建即可的实体（无需 adapter）]
  national_relay_task   从国家平台 API 实时拉取（§9.3 国家平台 mock 容器）
  notification          运行时新产生（无历史数据需要回放）
  alert                 运行时新产生（无历史数据需要回放）
```

Adapter 关键策略：


| 策略                    | 内容                                                               |
| --------------------- | ---------------------------------------------------------------- |
| **单向为主**              | Phase 1-3 仅旧 → 新；Phase 4 双跑期允许「反向 adapter」把新模型变更写回旧表，确保旧 UI 期间不破 |
| **不直读旧表**             | Skill / Agent 严禁直接读旧库；只能从新模型读                                    |
| **URN 重生成**           | adapter 为旧主键生成稳定 URN，并维护 `legacy_id ↔ urn` 映射表                   |
| **状态机翻译**             | 旧字符串状态 → 新 enum；翻译表写在 `adapters/lib/status_map.py`               |
| **字段补齐**              | 旧模型缺失的 Agent-Native 字段（如 `intent_history`、`sensitivity`）按默认值补入   |
| **schema 校验**         | 每条 adapter 输出必须通过 Pydantic 校验；失败进 dead-letter 队列 + 报警            |
| **审计补录**              | 旧 audit 流水翻译为 `audit_event`，缺失字段标 `legacy: true`                 |
| **adapter 自身是 Skill** | `adapter.run` Skill：可被 CLI / Agent 触发，方便迁移、回滚、增量同步               |
| **PII 默认从严**          | 旧表无敏感度标记的字段在 adapter 中默认 `sensitivity: confidential`，避免漏脱敏       |

#### 4.4.6 与旧白皮书 V1.3/V1.4 的对位

旧白皮书的实体仍然是「业务真相的描述」，新模型的 domain 实体在**业务语义上**与之一致（同名实体、同样的字段含义）；差异仅在**形态**（URN、enum、事件流、PII 标）。这意味着：

- 业务专家阅读旧白皮书的认知**不需要重学**
- adapter 层把「业务一致 / 形态升级」这一翻译显式化，不让歧义沉到代码里
- 新模型在 Phase 0 末完成 schema 评审；adapter 在 Phase 1 跟随核心 Skill 一起落地

### 4.5 模型服务调用唯一通路：集团推理平台 SDK（硬约束）

> 本节是 zw-brain 最强的硬约束之一，与「合规可证迹」并列。违反将无法通过 preflight 段 10。

#### 4.5.1 立场

所有 AI 模型推理（LLM 文本生成 / Embedding / Rerank / ASR 语音转写 / OCR / 图像理解 / 视频理解 / 多模态 / 任何后续新增模型能力）**必须且只能**通过集团推理平台（`../pcowork/推理平台/`）提供的统一 API / SDK 调用。

**禁止**：

- 直连 OpenAI / Anthropic / Google / 百川 / 智谱 / 通义 / DeepSeek / Moonshot / MiniMax / 任何其他第三方 LLM 服务商的 API
- 在大脑内自建模型推理服务（vLLM / Ollama / TGI / sglang 等本地后端，除非作为推理平台的内部实现）
- 绕过推理平台直接读取 HuggingFace / ModelScope 上的本地模型权重做推理
- 将 `OPENAI_API_KEY` / `ANTHROPIC_API_KEY` / `BAICHUAN_API_KEY` 等任何第三方厂商密钥写入 zw-brain 的配置文件、环境变量、CI Secret

**允许的唯一形态**（具体调用契约 ⚠️ 待集团推理平台同步详细 API 文档后定稿，下面是占位示意）：

```python
from zw_brain.shared.inference import inference_client

# ⚠️ 以下参数名 / 模型 ID / 返回结构都是示意，真实形态以推理平台文档为准
resp = inference_client.complete(
    model="<推理平台模型 ID>",                # 由推理平台目录给出
    messages=[...],
    tenant="zhengwu",                       # 多租户隔离
    parent_audit_ref=agent_session.audit_root_urn,
                                            # ↑ audit_event 是按「会话级根 → 步骤级子」级联的；
                                            # agent_session 启动（session_open）时已开根 audit_event（§4.3 编排示例上方「审计级联」），
                                            # LLM 调用作为 Step 1 自动派生子 audit_event 并挂在根下。
                                            # 推理平台 SDK 内部统一记录 token / prompt 哈希 / 模型版本，
                                            # 大脑侧仅传根 urn，不需要预先为每次调用单独建 audit_event。
)
```

`zw_brain/shared/inference/` 是大脑内对推理平台 SDK 的唯一封装层，所有 Agent / Skill 只能 import 这个封装，不允许直接 import 任何第三方 SDK。

**待回填项（不阻塞硬约束生效，仅影响封装层定稿）**：


| 待办                                                                 | 状态              | 来源                           | 影响范围                                                                         |
| ------------------------------------------------------------------ | --------------- | ---------------------------- | ---------------------------------------------------------------------------- |
| 推理平台对外 API/SDK 的具体协议（HTTP/gRPC/原生 Python）、鉴权方式、模型目录、错误码、限流头、审计字段命名 | ⏳ 待业务侧拿到详细文档后同步 | 集团推理平台团队（`../pcowork/推理平台/`） | 仅影响 `zw_brain/shared/inference/client.py` 的实现，**不影响**「禁止直连第三方」「必须经封装层」的硬约束生效 |
| 多模态（ASR / OCR / 视频）的统一动词命名                                         | ⏳ 同上            | 同上                           | 同上                                                                           |
| 同/异步流式接口（SSE / WebSocket）的形态                                       | ⏳ 同上            | 同上                           | 同上                                                                           |


**Phase 0 占位策略**：在拿到推理平台文档之前，封装层先以 mock 实现接口骨架（按上面占位 schema），让上层 Skill 可以基于稳定接口先开发。文档到位后只需替换 `client.py` 的内部实现，上层零改动。

#### 4.5.2 为什么这条约束必须硬执行


| 角度        | 不走推理平台的代价                                           |
| --------- | --------------------------------------------------- |
| **合规**    | 政务数据出境、未备案的境外模型调用 → 直接违反《生成式 AI 服务管理暂行办法》《数据安全法》    |
| **采购成本**  | 集团已经为推理平台付了授权与算力 → 大脑再单独签合同 = 重复投入                  |
| **可审计**   | 推理平台已经统一记录 token 用量、prompt 哈希、模型版本 → 大脑跳过它就丢失了这一层证据 |
| **可替换**   | 模型版本升级 / 国产化替换 → 推理平台一处升级，大脑不用动；直连 = N 处改动          |
| **限流与配额** | 推理平台已经做了租户级配额、QPS 限制、降级策略 → 大脑直连 = 重新造轮子            |
| **架构清洁**  | 模型供应是基础设施，不是应用层职责；混进来会污染大脑的领域代码                     |


#### 4.5.3 封装层的最小职责

`zw_brain/shared/inference/client.py` 必须且只能做以下事：

1. **统一签名**：`complete()` / `embed()` / `rerank()` / `transcribe()` / `ocr()` 等动词级接口，参数 schema 与推理平台 API 对齐
2. **审计透传**：把当前请求的 `audit_event.urn` 作为 `audit_ref` 传给推理平台，便于跨系统追溯
3. **超时与重试**：网络抖动级重试（最多 3 次，指数退避），业务级失败直接抛错
4. **降级策略**：推理平台 down 时，调用方决定是降级到无 AI 路径还是直接报错；封装层不做隐式降级
5. **不缓存语义结果**：缓存（如果有）由推理平台自己做或上游 Skill 显式做，封装层只做透传

封装层**不允许**：业务逻辑、prompt 模板、模型选择策略（这些都属于 Skill 层）。

#### 4.5.4 检查机制


| 检查                                    | 实现                                                                                                  | 时机                  | 失败动作   |
| ------------------------------------- | --------------------------------------------------------------------------------------------------- | ------------------- | ------ |
| 源码不允许出现第三方 LLM SDK 的 import           | `scripts/check_no_direct_llm.py`（grep `from openai`、`anthropic.Anthropic`、`langchain_openai` 等模式列表） | preflight 段 10 + CI | exit 1 |
| `requirements.txt` 不允许出现第三方 LLM SDK 包 | 同上脚本扫描 `pyproject.toml` / `requirements*.txt`                                                       | preflight 段 10      | exit 1 |
| 环境变量黑名单                               | `scripts/check_env_blacklist.py`（启动时检测 `OPENAI_API_KEY` 等存在即拒绝启动）                                   | 服务启动 / 容器健康检查       | 服务不启动  |
| 推理平台健康度                               | `inference_client.health()` 集成到 `/healthz`                                                          | 运行时                 | 主动告警   |


`scripts/check_no_direct_llm.py` 的黑名单模式应至少包括：

```text
from openai
import openai
from anthropic
import anthropic
from langchain_openai
from langchain_anthropic
from baichuan
from zhipuai
from dashscope          # 通义
from moonshot
from minimax
HuggingFacePipeline
vllm.LLM
ollama.Client
```

唯一的白名单是 `zw_brain/shared/inference/` 目录本身（封装层内部即使要适配推理平台底层细节，也仅限这一个目录）。

## 五、Agent-Facing 契约（API / CLI / MCP / A2A）

> 设计原则：**同一能力在四种暴露方式中行为一致**（同一 Skill ID + 同一参数 schema + 同一返回结构），由 `scripts/export_agent_contract.py` 一键生成四份契约文档，CI 强制不漂移（`agent-contract-enforcement.mdc`）。

### 5.1 REST API（人 + 程序通用）

```
POST /v1/skills/{skill_id}/invoke
Content-Type: application/json
Authorization: Bearer <token>

{
  "params": {...},                  # Skill 自定义参数
  "context": {                       # 大脑级上下文
    "session_id": "...",
    "actor": {"type":"human|agent","id":"..."},
    "purpose": "...",                # 合规要求
    "deadline": "..."
  }
}
```

返回：`{"invocation_id":"...","status":"ok|pending|error","result":{...},"audit_ref":"..."}`。

每一次 invoke 自动写 `audit_log` + `chain_record`。

### 5.2 CLI（运维 + 批处理）

```bash
zwbrain skill list                                # 当前可用 Skill 列表
zwbrain skill describe catalog.register           # 查看 Skill 详细 schema
zwbrain skill invoke catalog.register \           # 直接调用
  --param '{...}' \
  --purpose "市公安局年度数据接入" \
  --json
zwbrain agent ask "我要..."                        # 直接对话
zwbrain audit query --since 2026-04-17            # 审计回溯
zwbrain skill register --manifest skill.yaml      # 注册外部 Skill（见 §六）
```

CLI 是 OPC 视角下「运维一切自动化」的关键：所有 UI 动作都有 CLI 等价。

### 5.3 MCP Server（让 Cursor / Claude Code 等 IDE Agent 直接用）

│   ├── resource.find.json

### 5.4 A2A（Agent-to-Agent，跨平台调用）⚠️ 协议待集团/客户同步

**立场（已定）**：让其他 Agent 系统（部委自有 Agent / 集团其他平台 Agent / 客户既有 AI 平台）能够直接驱动政务大脑的 Skill；同时让大脑能够反向调用外部 Agent。这是「政务大脑成为大政务 Agent 网络的一个节点」的协议基础。

**协议（待回填）**：具体协议形态待业务侧拿到详情后同步，候选方案至少包括：


| 候选                                | 说明                             | 适用场景           |
| --------------------------------- | ------------------------------ | -------------- |
| Google A2A（Agent2Agent，2025 开放协议） | 标准化 message + agent card，跨厂商互通 | 跨集团 / 跨客户的开放对接 |
| 集团内部 Agent 互联协议                   | 集团若已定义统一标准 → 优先采用              | 集团内部 Agent 网络  |
| 客户指定协议                            | 部分政务客户可能有自有规范                  | 客户侧已有 AI 中台时   |


**Phase 0 占位策略**：先以「服务端骨架 + 协议适配层」结构实现：

```
其他 Agent 系统
   │
   │ <协议待定>  ← Adapter 层（按协议拆分多个实现）
   ▼
[a2a-adapter]   ← 把外部协议消息转成大脑内部统一的 SkillInvocation
   │
   ▼
内部统一 SkillInvocation（与 REST/MCP 共用同一编排路径）
```

适配器层与封装推理平台的策略一致：**外部协议变化只影响 adapter，不影响 Skill 与编排核心**。第一阶段先实现服务端（被别人调用），客户端（主动调用别人）放到 Phase 3。

**待回填项**：


| 待办                                             | 状态            | 影响范围                                                              |
| ---------------------------------------------- | ------------- | ----------------------------------------------------------------- |
| A2A 具体协议（消息 schema / 鉴权 / agent card 格式 / 错误码） | ⏳ 待业务侧拿到详情后同步 | 仅影响 `a2a-adapter/` 的实现，不影响「外部 Agent 接入是合法路径」「所有调用都走统一编排 + 审计」的硬约束 |
| 与集团内部 Agent 协议、客户既有协议的优先级                      | ⏳ 同上          | 同上                                                                |


### 5.5 四种入口的契约同步


| 入口  | 契约文件                                                        | 生成方                                |
| --- | ----------------------------------------------------------- | ---------------------------------- |
| API | `docs/agent_integration.md`、`openapi.yaml`                  | `scripts/export_agent_contract.py` |

## 六、Skill / Agent 扩展模型（系统扩展性的核心）

> 旧平台扩展靠「内部研发排期」。新平台扩展靠「外部技能平台**注册**」。

### 6.1 Skill 三件套（具体注册协议 ⚠️ 待集团 / 外部技能平台同步）

**立场（已定）**：任何外部 Skill 接入政务大脑必须提供「身份 + 调用契约 + 权限/合规声明 + 健康检查」四类信息；大脑通过统一注册流程审批、上架、热更新。**这是不变的硬约束**。

**协议（待回填）**：具体的 manifest 字段命名、注册端点、签名方式、Skill 卡片格式等待集团 / 外部技能平台拿到详情后同步。下面是占位 schema，便于先开发本地 Skill 与编排逻辑：

任何外部 Skill 接入政务大脑，必须提供：

1. **manifest.yaml**（占位 schema）：身份 / 描述 / 调用契约 / 权限声明 / 责任主体 / 合规字段
2. **执行端点**：HTTP / MCP / 待定第三方协议；大脑通过它调用 Skill 实现
3. **健康检查端点**：大脑定时探活，失败自动下线

```yaml
# skill.yaml 占位范例（最终字段以集团/外部技能平台规范为准）
skill_id: gov.shandong.population.lookup
version: 1.0.0
display_name: 山东省人口数据查询
description: 按身份证号或户籍地址查询本省人口基础信息
owner:
  org: 山东省大数据局
  contact: ops@xxx.gov.cn
endpoint:
  type: http
  url: https://intra.example.gov.cn/skills/population/lookup
  auth:
    type: oauth2_client_credentials
    token_url: https://intra.example.gov.cn/oauth/token
input_schema:                       # JSON Schema
  type: object
  required: [id_card]
  properties:
    id_card: {type: string, pattern: "^[0-9X]{18}$"}
output_schema:
  type: object
  properties:
    name: {type: string}
    address: {type: string}
permissions:                        # 调用方需具备的权限
  required_roles: ["数据消费者"]
  data_classification: "重要数据-人口"
  must_have_purpose: true
compliance:                         # 合规约束
  audit_level: "full"
  retention_days: 365
  upload_to_chain: true
```

### 6.2 注册流程

```
外部技能平台开发者
       │
       │ 1. 用 Cursor + Claude Code 写 Skill（产品研发工作流）
       │    - decompose → 原型 → 审批 → 实现 → 测试
       │
       ▼
   skill.yaml + 执行端点
       │
       │ 2. zwbrain skill register --manifest skill.yaml
       │
       ▼
   政务大脑「待审 Skill 池」
       │
       │ 3. 平台管理员审批（合规检查）
       │    - 责任主体 / 数据分级 / 权限声明 / 上链合规
       │
       ▼
   注册到 skill_registration 表 → 立即可被调用
       │
       │ 4. 大脑自动 reindex（编排层下一次意图路由可命中）
       │
       ▼
   用户：「帮我查一下 XXX 的户籍信息」
   大脑 → 路由到 gov.shandong.population.lookup → 完成
```

### 6.3 与外部技能平台的关系

外部技能平台 = 大脑外部的 Skill 开发与托管平台（参考集团已有的 `agent-skills/` 仓库 + 各部门自建 + 客户既有 AI 中台）。


| 角色          | 责任                       |
| ----------- | ------------------------ |
| 外部技能平台      | 提供 Skill 开发脚手架、托管、版本、监控  |

## 七、用户侧体验设计（精简 WebUI + NL 加速器）

### 7.1 设计立场（先说清楚不做什么）

数据产品有两条不可让步的体验底线：**字段精确**与**操作可发现**。这两条决定了：

- ❌ **不做裸对话框入口**：用户打开就只见聊天框 = 用户不知道能做什么 + 自然语言天然有歧义会污染数据精确性。
- ❌ **不做旧平台 20+ 子系统菜单复刻**：菜单复杂是旧平台被薛娇当面吐槽「设计太复杂」的根因。
- ✅ **做精简 WebUI（≤10 个端到端场景页）**：每页对应一个完整业务旅程，按 Jobs 原则「显然没有多余」。
- ✅ **WebUI 顶部内嵌 NL 加速器**：跨步骤穿透与自动填表，相当于给 WebUI 装一个「AI 副驾」。

### 7.2 核心交互范式（以「申请数据」为例）

```
┌──────────────────────────────────────────────────────────┐
│  政务大脑 · 数据申请                       [我的申请 ▾]   │
│  ┌──────────────────────────────────────────────────────┐│
│  │ NL 加速器：用一句话告诉我你想要什么数据                  ││
│  │  > 我要市卫健委 2024 年的接种数据，下周一前完成          ││
│  └──────────────────────────────────────────────────────┘│
│  ────────────────────────────────────────────────────────│
│  自动填好的申请表（每一项都可直接编辑或覆盖）              │
│  ┌──────────────────────────────────────────────────────┐│
│  │ 数据目录       [免疫规划接种数据 ▾]  匹配 1 个 ✓        ││
│  │ 数据范围       2024-01-01 ─ 至今                       ││
│  │ 提供方         市卫健委                                  ││
│  │ 申请理由 *     [_________________________________]      ││
│  │ 使用部门 *     [本部门 ▾]                               ││
│  │ 期望完成时间   2026-04-21（下周一）                     ││
│  │ □ 同意行为上链留痕（合规要求，默认勾选）                  ││
│  └──────────────────────────────────────────────────────┘│
│  [提交申请]   [保存草稿]   [取消]                          │
└──────────────────────────────────────────────────────────┘
```

**关键**：WebUI 永远是「字段精确 + 状态可见 + 操作可发现」的最终保证；NL 加速器只是降低用户填表成本的「AI 副驾」，**所有字段在提交前都可被用户检视与覆盖**，写操作的最终触发必须由人点按钮。

### 7.5 NL 加速器的边界（防滥用）


| 不允许                        | 替代方式                            |
| -------------------------- | ------------------------------- |
| 直接执行写操作（提交 / 审批 / 交换 / 上链） | 仅允许预填表单，最终提交按钮必须人点              |
| 跨用户操作（替别人审批 / 替别人申请）       | 仅允许操作当前登录用户授权范围内                |
| 输出未脱敏的敏感数据                 | 后端 Skill 层做脱敏，NL 不参与脱敏决策        |
| 「猜」缺失字段                    | 缺字段时反问，不允许编造                    |
| 调用未注册 Skill                | 仅能调用 `skill_registration` 中已批准项 |


NL 加速器路由失败的兜底：


| 场景               | 兜底                                  |
| ---------------- | ----------------------------------- |
| 意图模糊             | 反问，最多 3 轮，第 4 轮起引导用户用 WebUI 表单完成    |
| 多个 Skill 都能匹配    | WebUI 弹出 Top-3 选择器                  |
| 没有 Skill 能匹配     | 引导用户去「Skill 市场」页提交需求 → 外部技能平台开发     |
| 调用失败（Skill 端点错误） | 自动重试 1 次 → 失败则在 WebUI 显示错误 + 自动报警   |
| 用户指令含混导致风险（如越权）  | NL 显式拒绝 + 写 audit_event（拒绝事件也是审计对象） |


### 7.6 立场修正声明

旧设计稿中「UI 不是产品形态、其他一切通过对话完成」是**错的**——数据产品里 UI 反而是产品形态的核心。修正后的立场：

> **WebUI 是默认入口**，但页面数从「20+ 子系统首页 + 数百菜单项」收敛到「≤10 个端到端场景页」；**NL 加速器是 WebUI 的 AI 副驾**，不是替代；**API/CLI/MCP/A2A 是给 Agent / 程序的同等入口**，与 WebUI 共享同一套 Skill 契约；**可视化大屏（§7.7）是独立的对外门面**，与 WebUI 同源数据但形态独立。

### 7.7 政务大脑可视化大屏（独立部署单元，K12）

> 大屏不是 WebUI 第 11 页，而是与 WebUI **平级且独立**的另一种 surface。理由：受众、形态、生命周期、性能要求、安全模型都不同。

#### 7.7.1 为什么单独立项（不并入 WebUI）


| 维度      | WebUI（§7.3）             | 可视化大屏（§7.7）                  |
| ------- | ----------------------- | ---------------------------- |
| 主要受众    | 业务办理人员（操作员 / 管理员 / 申请方） | 领导值守、上级视察、对外汇报、跨部门通报         |
| 主要交互    | 表单 / 列表 / 详情 / 审批等读写操作  | 只看不点（≥95% 时间纯展示，5% 一键钻取）     |
| 显示介质    | 个人办公电脑（1080p / 2K，单屏）   | 拼接大屏（4K-8K / 多屏拼接 / TV-wall） |
| 字号 / 排版 | 14-16px，密集信息            | 24-72px，远观可读                 |
| 刷新策略    | 用户操作触发                  | 定时自动刷新（10s-1min）+ 关键事件即时推送   |
| 写操作     | 是产品核心                   | **禁止**（详见 N7）                |
| 部署模式    | 与主 WebUI 同套部署           | 独立部署单元（可只在指挥中心机房运行）          |
| 故障影响面   | 故障即业务中断                 | 故障仅影响展示，不影响业务（隔离设计）          |


把大屏挤进 WebUI 会同时污染两边：WebUI 加入大屏需要的「炫酷动效 / 大字号视图」就违反了「数据产品要精确可发现」的立场，大屏被 WebUI 的「字段密集 / 表单为主」拖累就丢失了对外汇报的力量感。

#### 7.7.2 工程结构（独立项目）

```
zw-brain-dashboard/                    # 独立 git 子项目 / 独立 docker 镜像
├── frontend/                          # 大屏 SPA（React/Vue + ECharts/AntV）
│   ├── layouts/
│   │   ├── command-center.tsx         # 指挥中心模板
│   │   ├── leader-watch.tsx           # 领导值守模板
│   │   └── public-report.tsx          # 对外汇报模板
│   └── widgets/                       # 可拼装的展示组件
├── server/                            # 大屏专用 BFF（仅做聚合和缓存）
│   └── routes/
│       ├── overview.py                # 调用 dashboard.* Skill
│       ├── flow.py                    # 实时数据流通看板
│       └── compliance.py              # 合规状态总览
└── deploy/
    ├── Dockerfile
    └── README.md                      # 拼接屏分辨率 / 走线 / 时区配置
```

**与主大脑的关系**：大屏前端 / BFF 都是只读消费者，**不直接读数据库**，全部通过大脑暴露的 `dashboard.`* Skill 取数。`dashboard.*` Skill 只做「聚合 + 缓存」，不引入新业务实体；底层数据全部来自已有的 `audit_event` / `skill_invocation` / `catalog` / `request` / `exchange_task` 等。

#### 7.7.3 三个标准模板（开箱即用）


| #   | 模板       | 主要受众          | 必有看板项                                               | 数据来源 Skill                                                             |
| --- | -------- | ------------- | --------------------------------------------------- | ---------------------------------------------------------------------- |
| T1  | **指挥中心** | 平台管理员 / 大区调度  | 实时数据流通量 · Skill 调用 QPS · Agent 在线数 · 异常告警 · 国家通道状态  | `dashboard.realtime` · `runtime.health` · `national.relay.status`      |
| T2  | **领导值守** | 厅局领导 / 上级视察   | 累计开放数据集数 · 累计申请处理量 · 累计交换字节数 · 共享专区订阅趋势 · 合规审计通过率   | `dashboard.cumulative` · `compliance.summary` · `zone.subscribe.stats` |
| T3  | **对外汇报** | 对接其他厅局 / 上级督导 | 部门贡献排名（**默认关闭**，避免触政治敏感）· 重点专题进展 · 异议处理时效 · 国家任务完成度 | `dashboard.portfolio` · `dispute.sla` · `national.task.progress`       |


> **T3 的部门排名功能默认关闭**——继承旧平台「绩效考核」被弃用的教训（README §16，政治敏感）；客户明确要求时再走 `product-dev.mdc` 流程开启。

#### 7.7.4 安全与防滥用（继承 N7）


| 约束                   | 实现                                              | 检查                                                    |
| -------------------- | ----------------------------------------------- | ----------------------------------------------------- |
| 大屏只读，禁止任何写操作         | BFF 路由白名单（仅 `GET` + 仅 `dashboard.`* Skill）      | `scripts/check_dashboard_readonly.py`（preflight 段 11） |

| 大屏被截屏 / 拍照外传         | 加水印（部门 + 时间戳 + 操作员）+ 敏感模板需登录                    | 前端水印组件 + 模板 ACL                                       |
| 「一键钻取」不绕过权限          | 钻取链接跳回主 WebUI 走标准 RBAC                          | 路由跳转，不在大屏内开权限旁路                                       |


#### 7.7.5 与现有 ❝运营看板 / 合规督导❞ 的关系

旧平台的「数据运营看板」「合规督导面板」散落在多个子系统首页，本质都是「读视图」。重构后：

- **办公场景的看板** → 仍在 WebUI 第 7 页（合规督导 + 审计回溯）和第 9 页（运营面板），用于业务人员日常工作
- **大屏场景的看板** → 进 §7.7 的三个模板，用于领导 / 对外
- **数据来源同一**：都消费同一组 `dashboard.`* / `compliance.*` Skill，避免双轨数据
