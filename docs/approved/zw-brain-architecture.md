## 一、我们造什么

### 1.1 我们造什么

**zw-brain 是一个让政府部门之间共享数据的产品——一个"数据共享网关"。**

旧平台被各省客户磨练了多年，骨架已经成型——**5 步骨干**：

```
编制 → 审核 → 发布 → 申请 → 交换
```

这条骨架本身是对的，不需要重新发明。zw-brain 做的是：
- **保留 5 步骨干**（旧平台已验证的正确逻辑）
- **删除多年累积的冗余**（18+ 菜单 → 8 页面，删 56%）
- **加上 AI 让定制不靠改代码**（项目级流程/表单/推荐通过配置 + AI 辅助生成）

> 命名澄清：项目名继续沿用 `zw-brain` 与"政务数据大脑"（代码、文档、客户口径已用），但**产品身份**是"数据共享网关"——立项会议（2026-04-17）Jane 在听完红军讲完整平台后自己识别出的本质："**你其实就是个网关数据服务的网关？**"（1:00:15）

### 1.2 用户每天做什么（两条核心旅程）

**J1 找数→用数**（每日高频，数据使用方）：

> 搜资源 → 申请 → 审批通过 → 凭据领取（API Key + curl 示例）→ 调用使用

**J2 挂数→维数**（部门提供方）：

> 在线编制目录 → 资源挂接 → 部门内审 → 平台发布 → 处理使用方异议

**B1 看全局→处异常**（后台支撑面，仅大数据局管理员/审计员）：

> 看共享是否合规 → 看异常是否被处理 → 看绕过流程的违规

普通用户每天只接触 J1+J2 这两条；B1 是合规底线，不是产品差异化重点。

### 1.3 我们不做什么

**zw-brain 不做以下事情**（旧平台做了但客户不用 / 或别的产品已经做了）：

| 不做的事 | 原因 |
|---|---|
| 数据治理 / 清洗 / 质量 / 血缘 | 集团数据治理中心（石云志团队）已经做 |
| 数据分类分级 / 敏感识别 / 脱敏 | 集团数据安全中心已经做 |
| 大屏 / 指挥中心 / 演示页面 | 没人天天看大屏，是演示功能 |
| 主题库 / 专题库 / 人口库 | 各部门线下建库 + 数据治理中心治理 |
| 运行监控 / 告警 / 巡检 | 集团统一运维监控平台 |
| 国家目录治理 / 国家直达 | 客户重心在本级共享（红军原话"用得最少"） |
| 数据存证 / 区块链 | 可插拔 adapter；外链 down 不阻塞业务 |
| 标准服务 / 指标平台 / 应用案例 | 旧平台"几乎不用"（红军确认） |
| 脚本管理 / 通用服务 / 融合服务编排 | 同上 |
| 客户级后端 fork | 客户差异通过配置承接，不通过分叉代码 |

完整不进 IA 清单见 §5.6。

### 1.4 为什么这个产品值得做（差异化承诺）

1. **项目级个性化不再改代码**——审批流/表单/推荐通过配置 + AI 辅助生成（§10.3 Wave 2 三引擎）
2. **人 + Agent 共用同一能力面**——后端只维护一套契约，5 消费面（WebUI/API/CLI/MCP/A2A）自动投影
3. **合规默认内建**——审计总线 / 模型调用集团推理平台 / 区块链 adapter，不靠"靠自觉"
4. **单一 WebUI**——不是旧平台 8 个独立 SPA 拼接，避免角色困惑
5. **基于旧平台真相而非纸上设计**——18+ 菜单 → 8 页面的减法逐项可追溯到旧库 572 表 / 291 截图 / 21 条业务反馈

### 1.5 衡量成功的标准

不是"代码上线"，而是：

- **客户上线后第 90 天的真实使用频度**：J1 找数→用数 是否每日有 10+ 次申请？
- **项目个性化交付速度**：新客户落地的流程定制/表单定制是否能在 1 周内完成（不改代码）？
- **角色困惑次数**：业务方培训后是否还需要回头问"我是哪个角色"？（目标：0）
- **客户演示 vs 真实使用占比**：大屏 / 国家通道这类演示功能的使用占总申请的 < 10%？

这些是 zw-brain 与旧平台的**真实差距**，也是产品成功的真实衡量。

## 二、设计哲学

### 2.1 Jobs：产品必须围绕旅程，而不是围绕模块名与协议名

旧平台已经证明：菜单多、系统多、接口多，不会自然汇聚成好产品。原始证据（见附录 B.2–B.4 的接口清单、库表与使用日志）进一步表明：旧平台代码面和数据库面极大，但真实调用高度集中在少数能力簇与少数高频链路上。

因此 v4 明确采用乔布斯式减法：

1. **先定义少数关键旅程，再决定页面、Agent、契约怎么配合**。不是先列 30 个子系统，再想办法给每个子系统找“AI 化位置”。
2. **对大多数 legacy 表面说不**。源码里存在、数据库里存在、菜单里存在，不等于该进入新产品。
3. **把复杂度留在后端与底座，不留在前台心智里**。用户看到的是少数清晰入口，而不是“能力中心 + 注册中心 + 生态中心 + 配置中心 + 门户中心”并列。
4. **写操作必须看得见**。自然语言可以加速，但不能把政务场景的状态机、确认边界、责任边界都藏掉。
5. **AI 的价值在于减摩，不在于夺权**。评价 AI 体验好坏的标准，不是它是否“像聊天一样顺”，而是它是否减少语义表达、跨步骤切换、证据阅读的摩擦，同时不增加责任歧义。

### 2.2 OPC：一人可运转，才有资格成为默认方案

OPC 不是“少人硬扛”，而是“架构、流程、工具都必须服务于一人可运转”。因此 v4 明确：

1. **新增功能默认不进主仓库**。长尾能力优先外部构建为能力包，再注册接入。
2. **只允许一个事实源**。Capability contract 是唯一事实源，WebUI / API / CLI / MCP / A2A 都从它投影，不接受五处手维护。
3. **先打通一条真正可用的黄金链路，再补治理后台**。控制面是必要的，但不能先长成一个需要平台团队维护的平台。
4. **自动化优先于流程化**。能靠 schema、preflight、契约生成解决的，不靠会议、约定、人工同步。
5. **拒绝 per-tenant fork**。客户差异必须落在配置、多租户策略、外部能力包，不落在主仓后端逻辑分叉。

### 2.3 合规与治理必须内建，但不能长成另一个“平台产品”

政务场景确实要求：
- 写操作可审计、可回放、可追责
- 外部监管接口与国家通道语义不能被智能化重写
- 模型调用必须统一经集团推理平台收口

但这些要求的正确落地方式，是把合规与治理**嵌入主旅程**，而不是做成又一套需要用户理解和切换的产品层。v4 因此坚持：

- 审计、策略、租户、权限、回执必须成为主流程默认能力
- 但注册中心、能力市场、治理后台只服务管理员和平台运营者
- 普通用户的第一心智始终应是“我怎么找、怎么要、怎么拿、怎么追踪”

### 2.4 v4 的总哲学

```text
少数高频旅程
        +
单一能力契约
        +
外部长尾注册优先
        +
合规默认内建
        +
控制面保持纤薄
        =
政务数据大脑
```

## 三、从证据得到什么结论

> 本章不展开全量数字 Pareto 明细，而只提炼那些会改变架构决策的结论。原始证据见附录 B.2–B.4 的旧平台接口清单、数据库结构与使用日志统计。

### 3.1 旧平台真实拓扑：17 模块 / 572 张表 / 8 个独立 SPA


旧平台真实拓扑的数据级事实：

| 旧 schema 模块 | 表数 | 业务领域 | 真实分量级 |
|---|---|---|---|
| `dsp_catalog` | 161 | 政务目录 + 资源 + 物化（rc_resource_table/file/url）+ 共享审批 | **最大主线** |
| `dsp_basesubject` | 81 | 基础主题库（与政务目录并行的独立编制系统） | **并行主线**（v4 前版未识别） |
| `dsp_bsp` | 76 | IAM + 应用中心 + API 网关 + 用户/角色/权限/菜单 | 平台底座 |
| `dsp_metaresource` | 59 | 元数据 + 数据血缘（graphdb_node / graphdb_relation 5 表） | 含外部治理范围 |
| `dsp_connect` | 57 | 跨地市数据通道（dc_* 系列）+ 国家直达 | **省市间真实主线** |
| `dsp_pipelines` | 50 | ETL 任务编排（batch_job / etl_meta） | 外部数据治理范围 |
| `dsp_monitor` | 50 | 服务调用 / 失败分析 / 告警工单 / 巡检 / 拨测 / 知识库 | **运行监控独立体系** |
| `dsp_require` | 29 | 申请审批 5 步流程（编制→校核→汇总→响应→反馈） | J1 主旅程核心 |
| `dsp_perform` | 16 | 数据质量评分（kpi_index_*） | 外部数据治理范围 |
| `dsp_handling` | 10 | 异议 5 维度（authz / catalog / content / resource / use） | 强状态领域 |
| `dsp_service` / `dsp_message` / `app_center` / `dsp_block` | ≈72 | 服务 / 消息 / 应用 / 数享链 | 基础设施 |

**真实拓扑结论**：

1. **真正的主线不是 6 个抽象"能力簇"**，是 11 个真实表簇（上表）。其中 **3 个 v4 前版完全未识别**：基础主题库（81 表）、跨地市数据通道（57 表）、运行监控（50 表）。
2. **8 个独立前端 SPA**（portal-vue / app-center-web / dsp-catalog-web / dsp-metadata-web / dsp-objection-web / datasecurity-front / data-operation-board-front / cascade-front）—— 旧平台不是单一 WebUI，是多 SPA 拼接。

### 3.2 真实业务价值密度：291 截图 + 18+ 菜单的高频分布


**截图密度高频前 6（基于 291 张真实页面）**：

| 业务模块 | 截图数 | 占比 | 新平台中归属 |
|---|---|---|---|
| 运行监控 | **37** | 12.7% | **§3.4 新外部依赖**（dsp_monitor 50 表对接集团运维监控平台） |
| 数据直达 | **36** | 12.4% | J1 子旅程 + §3.4 省市间数据通道 |
| 供需对接 | **36** | 12.4% | ia-v2 §J1 供需对接子流程（待复议/责任分发细化） |
| 国家目录治理 | 27 | 9.3% | §5.6 独立子旅程，延后 P2 |
| 申请审批 | 20+ | 7% | J1 ✓ |
| 资源管理 | 20+ | 7% | J2 ✓ |

**真实菜单形态**：旧平台采用侧边菜单树 + **3-4 级嵌套深度**，主导航 **18+ 项**（目录 / 资源 / 供需对接 / 数据交换 / 融合服务 / 共享专区 / 应用中心 / 运行监控 / 国家通道 / 数据安全 / 数据治理 / 标准服务 / 指标平台 / 应用案例 / 通用服务 / 消息 / 工单 / 配置 etc.）。

**真实价值密度结论**：

1. **运行监控 / 数据直达 / 供需对接** 是真实使用频度前三（37+36+36 = 109 页 ≈ 37%）—— §3.4 第 6 类外部依赖（集团统一运维监控平台）承接。
2. **国家目录治理 27 页**虽多，但红军立项会议原话"用得最少"—— §5.6 标 P2 优先级正确。
3. **18+ 菜单 → 8 页面是 56% 减法**——Jobs 式收敛正确，但收敛逻辑需明示（详见 §5.2 收敛表）。

### 3.3 真实强状态领域：8 态 catalog status + 5 步申请 + 5 维度异议


**真实状态机事实**：

| 领域 | 真实状态机 | 来源 | 处置 |
|---|---|---|---|
| **目录** | `data_catalog.status` 8 态（草稿 / 待审 / 审批通过 / 驳回 / 发布 / 下线 / 国家通道转报中 / 撤销中） | `dsp_catalog.xml` | §9.2 `Catalog` 补真实状态机标注 ✓ |
| **共享类型** | `shared_type` **3 态**（无条件 / 有条件 / **不予共享**） | `dsp_catalog.xml` `data_catalog` | ia-v2 §J1 漏第 3 态"不予共享"，**待业务方 sign-off 后补** |
| **资源物化** | 3 种物化形式（`rc_resource_table` / `rc_resource_file` / `rc_resource_url`） | `dsp_catalog.xml` `rc_*` 表 | §9.2 `Resource` 补 3 物化形式标注 ✓ |
| **申请审批** | 5 步严格流程（编制 → 校核 → 汇总 → 响应 → 反馈） | `dsp_require.xml` + 立项会议 1:33-1:42 | §9.2 `Application` 补 5 步标注 ✓ + ia-v2 §J1 供需对接子流程 ✓ |

## 四、AI-Native 重构原则

### 4.0 AI 原生的五条成立条件

本文中的"AI 原生"只有五条同时成立时才成立：

1. **研发方式 AI 原生**：平台以 AI coding 为默认研发方式，规则、契约、检查都必须可被 Agent 理解、执行、校验。
2. **能力形态 AI 原生**：平台内部以统一 Capability 为最小单位，再投影到 WebUI / API / CLI / MCP / A2A，不为每个入口各造一套实现。
3. **体验形态 AI 原生**：用户看到的首先是**结构化主旅程优先**的产品界面；AI 只作为嵌入式副驾介入少数关键摩擦点——把用户意图翻译成检索/申请条件，把跨步骤上下文串起来，把审计/异常/交付等复杂证据转成可读摘要。它不是旧门户换皮，也不是只剩聊天框，更不是责任动作的默认入口。
4. **扩展路径 AI 原生**：新增功能默认在外部 ANP / hub-compatible 能力包中构建，再注册进入平台，而不是继续在主仓库里长菜单、长模块、长分叉。
5. **可配置化 AI 原生**：政务场景项目级个性化（**审批流、表单字段、推荐规则、门户布局**）是基本盘——立项会议红军原话「各项目门户、表单、流程都个性化；旧平台靠改代码 + 改数据库」。**真正的 AI 原生差异化不是"在每页塞一个聊天框"，而是把"改代码 / 改库"以前必须做的事，提升为"用自然语言生成 schema / 节点 / 选人规则 → 平台运行可配置物 → 不再回主仓发版"**。该条件落地在 Wave 2 的三大引擎（§10.3：审批流引擎 + 表单 schema 化 + 智能推荐），由 §11 R14 锁定。

### 4.1 Capability 是唯一中性最小单位

v4 继续坚持：平台内部真正稳定的最小单位不是页面、API、脚本或 Agent，而是 **Capability**。

每个 Capability 至少回答：
- 它做什么
- 输入 / 输出是什么
- 谁能调
- 在哪个租户范围内调
- 是否需要人工确认
- 调用后落什么级别的审计
- 由什么执行绑定完成
- 能暴露给哪些消费面

页面、REST、CLI、MCP、A2A 都只是同一 Capability 的投影。

### 4.2 五个消费面共享契约，但不要求同速成熟

v4 不再把“五入口共享契约”误解为“五入口同时做成完整产品”。正确原则是：

- **契约层必须统一**
- **投影层自动生成**
- **生产级硬化顺序服从真实需求**

因此：
- WebUI / API / CLI 是首波必须做实的消费面
- MCP / A2A 必须从同一契约投影出来，但可随 Agent 真实接入需求逐步硬化
- 绝不允许因为追求协议对称而推迟主旅程交付

### 4.3 核心高频内建，长尾默认外部化

能力分三层：

| 层级 | 定义 | 默认去向 |
|------|------|----------|
| Core | 跨项目高频、直接构成主旅程 | 平台内建 |
| Common | 有复用价值，但不必进入主导航 | 后台入口 / 可选能力 |
| Long-tail | 项目特有、低频、试验性、行业特化 | 外部 ANP / hub-compatible 包注册 |

这条原则的目标不是“分类漂亮”，而是**不给低价值复杂度永久居住权**。

### 4.4 自然语言只负责加速，不负责越权提交
自然语言在 v4 中只应强介入**四类**关键摩擦点：

- **语义入口**：把一句话转成检索条件、申请草案或字段候选值
- **上下文编排**：在发现 → 申请 → 审批 → 交付之间保留上下文，减少重复填写与重复理解
- **证据摘要**：把审计、异常、异议、交付状态转成可读的判断辅助
- **配置生成**：把项目个性化需求（"我们这边审批要走二级部门"、"这个表单要加一个备注字段"、"先按相似目录推荐"）用自然语言生成可执行 schema（审批流节点 + 选人规则 / 表单字段 + 校验 / 推荐过滤规则），由管理员在结构化配置页确认并入库——**不是直接生效**。这是 §10.3 Wave 2 三大引擎（审批流引擎 + 表单 schema 化 + 智能推荐）的统一 AI 落点。

自然语言不能承担：
- 替代结构化页面本体
- 直接触发责任性写操作
- 绕过审批与确认
- 替代关键状态展示
- 让用户失去"当前处于哪一步、将要提交什么、谁会承担责任"的可见性
- **直接修改生产配置**（配置生成必须走管理员"草稿 → 预览 → 确认入库"三步）

涉及申请、审批、交付、共享、下线、跨租户访问等写操作的 Capability，必须显式声明 `human_confirmation_required`，并在结构化页面内完成确认与回执留存。

一句话原则：**AI 原生不是"全页面 AI 化"，而是"关键摩擦点 AI 化 + 项目个性化可配置化"；主工作流仍必须结构原生。**

### 4.5 控制面必须存在，但要保持纤薄

v4 认可 Registry / Policy / Audit / Compatibility / Rollback 这些控制面能力是必须的，但它们的目标只有一个：**把主旅程做稳，把长尾扩展纳入秩序**。

因此控制面遵循四条约束：

1. **只保留负载真正决策的字段与状态**。
2. **不为“未来也许会用到”提前造复杂审批流、版本矩阵、市场前台**。
3. **所有消费面的投影从同一 registry/contract 派生，而不是分别维护**。
4. **普通用户不需要理解控制面概念**。

### 4.6 canonical model 优先，但物理边界分波次落地

本基线承认存在多个 load-bearing 领域概念，但把“概念重要”与“Phase 1 必须独立持久化”明确分开。

因此 v4 明确：

- 在概念层，`CatalogModel`、`Catalog`、`Resource`、`Application`、`ApprovalTask`、`DeliveryTask`、`ObjectionCase`、`AuditEvent`、`CapabilityPackage`、`TenantOrg` 都是 load-bearing 语义
- 在 Phase 1 物理落地层，不必把每个概念都拆成独立服务、独立子系统、独立前台面
- 先把最影响主旅程的聚合边界做对，再按真实压力把概念升格

### 4.7 代码层必须继续服从项目既有分层纪律

运行时可以谈 Surface / Experience / Control Plane / Domain / Runtime / External，但**代码组织不能因此膨胀成一层一个王国**。

本项目代码层仍服从：

```text
entry → command → domain → shared
```

Capability、Registry、Policy、Audit 等实现都必须回落到这套代码纪律里，而不是再复制一套并行层级体系。

### 5.3 嵌入式自然语言加速器
必要的核心页面可以内嵌自然语言输入，但其职责严格限定为减摩组件，而不是主交互形态：

- 把一句话解析成检索条件、预填字段、跨步骤跳转建议
- 在结构化页面中完成确认
- 让人和 Agent 在同一上下文下协作，而不是把结构化界面替换掉
- **生成配置草稿**：在管理员侧（项目实施 / 平台运营）由自然语言生成审批流节点 / 表单字段 / 推荐过滤规则的 schema 草稿，结构化预览后入库；不直接修改生产配置

最适合内嵌 AI 的页面类型是：
- 资源发现页（语义入口）
- 申请形成页（语义入口 + 上下文编排）
- 审批判断页（证据摘要）
- 合规调查页（证据摘要）
- **管理员配置后台**：审批流可视化编辑器 / 表单 schema 编辑器 / 推荐规则编辑器，AI 生成草稿 + 管理员确认

最不适合让 AI 成为主交互的页面类型是：
- 责任性确认页
- 高确定性配置生效页（生产入库动作）
- 大屏主视图

一句话原则：**自然语言负责缩短路径，不负责吃掉页面；AI 只减摩，不夺主；AI 可生成配置草稿，但生效必须经过结构化确认。**

### 5.4 AI 体验设计原则清单

本节用于把上文的体验形态约束进一步落成可执行的设计判据，供后续原型、设计评审与实现统一口径。

#### 5.4.1 总原则

1. **关键摩擦点 AI 原生，主工作流结构原生。** AI 只解决语义翻译、上下文串联、证据摘要三类摩擦；页面、状态机、确认流、回执流仍是主工作流本体。
2. **AI 是副驾，不是入口本体。** 用户首先进入的是工作台、检索页、申请页、审批页、交付页，不是聊天框。
3. **AI 减摩，不夺权。** AI 可以建议、草拟、解释、追问，但不能代替人提交、审批、授权、下线、跨租户放行。
4. **结构优先于对话。** 任何 AI 输出，最终都应落回结构化字段、结构化状态、结构化回执，而不是停留在一段自然语言里。

#### 5.4.2 必要性判据

只有满足以下三类之一，才值得上 AI：

- 用户不会说系统语言，只会说业务语言；
- 用户必须跨多个步骤反复搬运上下文；
- 用户面对大量证据、日志、审计信息，阅读成本高。

反之，高确定性、高责任、高频动作不需要 AI 主导，例如审批确认、交付确认、共享授权、服务下线、配额调整、租户配置。

一个设计上的硬判据是：**去掉 AI 后，这个页面仍应能完成主任务。** 若去掉 AI 页面就不可用，说明不是 AI 在减摩，而是页面设计失职。

#### 5.4.3 合理性判据

- AI 必须贴着当前动作出现。搜索上下文贴搜索框；申请草案贴字段区；审批建议贴审批动作；调查摘要贴证据区。
- AI 先给中间结果，不先给抽象评价。好的输出是检索条件、缺失项、申请草案、审批依据、状态解释；差的输出是泛泛建议、空洞提醒、长段旁白。
- AI 结论必须带证据或依据。审批建议、异常归因、调查摘要都必须能回指到结构化材料、日志、审计事件或规则。
- AI 的视觉权重必须低于主任务内容。标题、表格、状态、按钮是主位；AI 结论、摘要、建议是辅位。
- AI 的不确定性必须可见。对缺失项、边界项、反事实、风险项要显式提示，而不是伪装成确定答案。

#### 5.4.4 精准落点

- **P2 资源发现**：AI 做“搜索上下文助手”——意图解析、缺口追问、推荐理由、下一步建议；不替代目录树、筛选器与资源详情。
- **P3 申请形成**：AI 做“申请草拟助手”——预填字段、补件建议、草拟摘要、审批风险预估；不自动提交，不自动确认责任字段，不自动决定口径。
- **P3 审批判断**：AI 做“依据阅读助手”——归纳依据、提示风险、给出反事实与后续影响；不替审批人点通过/驳回/补正。
- **P4 交付与交换**：AI 做“状态解释助手”——解释当前阶段、异常原因、影响范围、下一步动作；不替代时间线、回执与任务状态本体。
- **B1.1 合规与运营**（原 P6）：AI 做"调查摘要助手"——证据分类、事件归纳、工单/知识建议串联；不覆盖原始审计证据，也不替代人工调查结论。
- **B1.2 平台接入后台**（原 P8）：AI 做"审核缺项助手"——标缺项、草拟退回意见、提示确认边界问题；不自动批准、自动发布。
- **K12 大屏**：AI 做“指挥辅助结论”——结论、责任人、下一动作、依据摘要；不成为主视图主交互。

#### 5.4.5 一票否决项

出现以下任一情况，应判定为 AI 体验失真：

- 首页以聊天框作为默认主入口；
- AI 替代结构化页面或状态机；
- AI 直接触发责任性写操作；
- 审批/交付/合规结论没有证据支撑；
- 用户看不懂当前步骤，只能靠 AI 才知道自己在哪；
- AI 组件压过表格、字段、时间线、回执本体；
- 每页机械性塞一个 AI 模块，只为“看起来 AI 原生”。

#### 5.4.6 评审时的六个问题

1. 这个 AI 组件到底在减少哪一种摩擦？
2. 去掉它，主任务还能不能完成？
3. 它有没有让责任边界变模糊？
4. 它的输出能不能落回结构化字段、状态、回执？
5. 它的结论有没有证据来源？
6. 它是在帮用户完成任务，还是在向用户解释系统？

## 六、统一能力契约

### 6.1 一个 Capability，五个消费面

v4 继续采用五个消费面：

| 消费面 | 目标用户 | 首波优先级 |
|--------|---------|-----------|
| WebUI | 人类用户 | 高 |
| API | 第三方系统 | 高 |
| CLI | 运维 / Headless / 后台 Agent | 高 |
| MCP | IDE / Claude / Cursor 类 Agent | 中 |
| A2A | 外部 Agent 平台 | 中 |

这里的“中优先级”不是说 MCP / A2A 不重要，而是说 **首波不为了协议对称牺牲交付顺序**。

### 6.2 Capability 最小契约

每个 Capability 至少定义：

```json
{
  "slug": "resource.apply",
  "version": "1.0.0",
  "input_schema": {},
  "output_schema": {},
  "tenant_scope": "tenant|cross-tenant-approved",
  "auth_policy": "user|service|agent",
  "human_confirmation_required": true,
  "audit_class": "write-critical",
  "execution_binding": "builtin|registered-package|adapter-call",
  "exposure": ["webui", "api", "cli", "mcp", "a2a"]
}
```

最重要的不是字段数量，而是这份定义必须足以让任一消费面知道：
- 能不能调
- 怎么调
- 何时要人确认
- 调完会留下什么回执与审计

### 6.3 投影原则

- WebUI：把 Capability 组装成页面与旅程
- API：把 Capability 暴露为 REST / OpenAPI
- CLI：把 Capability 暴露为命令与参数
- MCP：把 Capability 投影为工具 / 资源
- A2A：把 Capability 暴露为可发现的 agent skill / action

投影的本质是**同一能力被不同消费方式消费**，不是五套实现。

### 6.4 权限、租户、策略、审计必须内嵌在 contract 中

统一契约不仅描述“做什么”，还必须描述：
- 谁能调
- 在哪个租户范围内调
- 是否需要审批 / 人工确认
- 调用后落什么审计
- 是否可被外部消费面暴露

这些边界若散落在页面逻辑、脚本或运维约定中，OPC 模式必然失控。

### 6.5 契约生成原则

文档、OpenAPI、CLI spec、MCP manifest、A2A card 都应由同一 registry / contract 派生，而不是人工分别维护。对 v4 来说，**自动生成本身就是产品边界的一部分**。

## 七、架构与代码边界

### 7.1 运行时视图

```text
L0 Surface
  WebUI | API | CLI | MCP | A2A | Dashboard

L1 Experience
  Structured Page Flow | Human Confirmation | Context Retention | NL Accelerator

L2 Control Plane
  Capability Registry | Policy Engine | Audit Bus | Exposure Router

L3 Domain Workflows
  Catalog | Resource | Application | Approval | Delivery | Objection | Compliance

L4 Runtime & Adapters
  Built-in Skills | Registered Packages | Adapter Skills | Tool Bindings

L5 Data / External
  Canonical DB | Audit Store | Registry Store | Legacy Adapters | IAM | 推理平台 | 区块链 | 国家平台 | 对象存储 | 消息
```

### 7.2 代码视图必须回落到项目既有分层

运行时视图是为了帮助理解产品，不是为了驱动代码目录无限膨胀。代码实现仍服从：

| 代码层 | 职责 |
|-------|------|
| `entry` | WebUI / API / CLI / MCP / A2A / Dashboard 的入口与适配 |
| `command` | Capability 调度、用例编排、确认边界、投影组装 |
| `domain` | 领域模型、状态机、策略约束 |
| `shared` | 审计、鉴权、推理、存储、注册、外部 SDK 封装 |

v4 明确反对两种做法：
- 为每个消费面复制一套纵向实现链
- 为每个概念新建一个“中心”与一个顶级目录

### 7.3 依赖约束

允许：
- `entry → command`
- `command → domain / shared`
- `domain → shared`

禁止：
- 页面直接绕过 command / policy / audit 写数据
- 注册能力包直接读写 canonical DB
- domain 反向依赖 legacy schema 命名与旧门户结构
- WebUI / API / CLI / MCP / A2A 各自实现各自的业务逻辑

### 7.4 控制面的最小可用要求

v4 只要求控制面先具备以下最小能力：
- 注册 / 启停
- 暴露范围控制
- 版本与来源可追溯
- 权限 / 租户 / 审计边界声明
- 回滚目标声明

在首条黄金链路落地前，不要求先做：
- 面向普通用户的“能力市场”前台
- 复杂多级评审工作流
- 全协议全矩阵兼容后台
- 大而全的生态运营页面

## 八、外部能力集成模型

### 8.1 ANP / hub-compatible 包是能力生产线，不是产品首页

本基线确立：新增能力默认从外部 ANP / hub-compatible package 生产，再注册进入 zw-brain。

但 v4 同时收紧一个表述：

**外部能力生态是平台的扩展机制，不是普通用户的主要产品心智。**

这意味着：
- 对管理员而言，它是扩展路径
- 对工程团队而言，它是复杂度隔离策略
- 对普通用户而言，它最多体现为“多了一个可用能力”，而不是“我要先理解一个生态系统”

### 8.2 外部能力包的最小形态

参考 hub 样例，外部能力包至少应包含：

- `manifest.json`：包级元信息
- `a2a/agent_card.json`：A2A 可发现面（如适用）
- `skills/bindings.json`：Skill 绑定与 schema
- `tools/runtime_bindings.json`：工具绑定
- `runtime/`：执行入口与适配逻辑
- 可选的 prompt / assets / references

### 8.3 Registry 最小字段

Capability Registry 至少维护：

| 字段 | 含义 |
|------|------|
| `slug` / `version` | 稳定标识 |
| `package_kind` | skill / agent / tool / bundle |
| `source_type` | builtin / imported / external-register |
| `review_status` | draft / pending / approved / disabled / archived |
| `tenant_scope` | 可见范围 |
| `auth_policy` | 调用边界 |
| `audit_class` | 审计等级 |
| `human_confirmation_required` | 是否要求人工确认 |
| `compatibility` | 支持哪些消费面 |
| `runtime_binding` | 实际执行绑定 |
| `rollback_target` | 回滚版本 |

### 8.4 注册流水线

外部能力进入生产链路的最短路径：

1. 在 ANP 构建并测试能力
2. 导出 hub-compatible 包
3. 在 zw-brain 执行静态契约校验
4. 声明租户、权限、审计、确认边界
5. 通过审核后注册进 Registry
6. 自动投影到允许暴露的消费面
7. 所有调用回到统一审计与观测面

### 8.5 允许外部化与禁止外部化的边界

允许外部化：
- 行业特定 Skill
- 项目特有流程
- 长尾能力
- 试验性 Agent
- 快速迭代能力

不能外部化：
- 租户 / 权限 / 策略 / 审计总线
- canonical domain 的核心状态机
- 关键写操作的确认与问责边界
- 模型推理统一接入边界

## 九、数据模型

### 9.1 设计准则

1. **模型围绕旅程与审计组织，不围绕 legacy 表名组织**。
2. **关键实体必须有显式状态机**。
3. **每次 Capability 调用都应能回放到实体变化与审计事件**。
4. **旧 schema 只作为 adapter 输入面**。
5. **概念层完整，物理层分波次**。

### 9.2 概念层的 load-bearing 领域概念
本基线在概念层保留以下 load-bearing 概念。基于 `old/12-datastructure/` 真实表事实补充状态机 + **概念到真实表簇的完整溯源**（让每个概念都能追踪到旧库具体表）：

| 概念 | 说明 + 真实状态机 | 真实表簇溯源（旧库具体表） |
|------|------|------|
| `CatalogModel` | 目录模板、属性、维度、步骤定义；**真相补**：旧库支持"政务目录 + 国家扩展要素目录"双轨编制 | `dsp_catalog.xml`: `data_catalog_model`, `data_catalog_model_field`, `data_basic_elem_catalog` |
| `Catalog` | 目录节点与主题分类；**真相补**：`status` 真实 8 态（草稿→待审→审批通过/驳回→发布→下线 etc.）；`shared_type` 真实 **3 态**（无条件 / 有条件 / **不予共享**）—— ia-v2 §J1 共享审批分支待业务方 sign-off 后补"不予共享"行 | `dsp_catalog.xml`: `data_catalog` (51 字段), `data_catalog_item`, `data_cascade_catalog_topic` |
| `Resource` | 可被发现与申请的数据资源；**真相补**：旧库 3 种物化形式 `rc_resource_table` / `rc_resource_file` / `rc_resource_url` | `dsp_catalog.xml`: `data_resource`, `rc_resource_table`, `rc_resource_file`, `rc_resource_url`, `rc_catalog_materialize`, `rc_generate_file_log` |
| `Application` | 申请单；**真相补**：旧 `dsp_require` 5 步流程严格定义（编制 → 校核 → 汇总 → 响应 → 反馈） | `dsp_require.xml`: `data_require`, `data_original_require`, `data_require_approve`, `business_requirements` (29 表中核心) |
| `ApprovalTask` | 审批任务与决策轨迹；**真相补**：明示与 `ObjectionCase` 边界——前者是申请审批 5 步流程，后者是异议 5 维度独立状态机 | `dsp_require.xml` 含 `data_business_approve` 等 + `dsp_catalog.xml` 含 `data_catalog` status 8 态联动 |
| `DeliveryTask` | 交付、交换、直达任务 | `dsp_connect.xml`: `dc_catalog`, `dc_example_resource`, `dc_example_matters`（57 张 dc_* 表的核心） |
| `ObjectionCase` | 异议与纠错链；**真相补**：旧 `dsp_handling` 5 维度独立状态机（authz / catalog / content / resource / use） | `dsp_handling.xml`: `dc_objection_apply`, `dc_objection_accept_audit`（5 维度异议合计 10 表） |
| `AuditEvent` | 全量审计事件 | 旧库分散在各 dump 的 *_log / *_record / capability_call 等；新平台 zw-brain audit_event 统一 |
| `CapabilityPackage` | 注册能力包元信息；**真相补**：**zw-brain AI 原生重构引入的承重抽象**，无旧库继承——不是从旧平台事实推导，是为 AI 原生扩展模式新发明 | **无旧库表对应**——是 R7 / R14 引入的新概念；外部 ANP / hub-compatible 能力包注册路径 |
| `TenantOrg` | 组织、租户、部门、区域上下文；**真相补**：旧库支持多级区划（省/市/区）+ 跨地市协作，不是简单单租户 | `dsp_bsp.xml`: `pub_org`, `pub_org_role`, `pub_org_region`, `sys_user_role`, `sys_permission`（IAM 由 IAF 外部化，本地保留 actor_org_role_binding 投影） |

**真相溯源结论**：

1. **10 概念覆盖度 ≈ 70%**：CapabilityPackage 是 zw-brain 新发明，其余 9 个全部能溯源到 dsp_* 真实表簇——证明 10 概念不是凭空抽象，是基于旧平台真实业务事实的合理收敛。
2. **零覆盖区域**（10 概念未触及但旧库真实存在）：基础主题库（basesubject 81 表）/ 运行监控（dsp_monitor 50 表）/ ETL 编排（dsp_pipelines 50 表）/ 数据血缘（graphdb_* 5 表）/ 数据质量（dsp_perform 16 表）—— 这些已在 §3.4 / §5.6 标为外部依赖或不进 IA，不进 §9.2 是设计有意，不是疏漏。
3. **多概念合并到 Phase 1 聚合**（§9.3）：10 概念按 6 个物理聚合落地，仍服从"概念完整 + 物理收敛"原则（R5）。

### 9.3 Phase 1 物理落地边界

Phase 1 不要求把所有概念都做成独立“产品面 + 服务面 + 持久化面”，而先收敛到最影响主旅程的聚合边界：

| Phase 1 聚合边界 | 吸收的概念 |
|----------------|-----------|
| `CatalogResourceAggregate` | `CatalogModel` / `Catalog` / `Resource` |
| `ApplicationApprovalAggregate` | `Application` / `ApprovalTask` |
| `DeliveryAggregate` | `DeliveryTask` |
| `ObjectionAggregate` | `ObjectionCase` |
| `AuditAggregate` | `AuditEvent` |
| `CapabilityRegistryAggregate` | `CapabilityPackage` / `TenantOrg` 相关暴露与治理信息 |

这样做的目的：
- 保留领域语义
- 控制 Phase 1 的物理复杂度
- 避免因为“概念上重要”就立刻长成“系统上独立”

### 9.4 物理存储分层

建议的物理存储仍分为：
- **Canonical DB**：核心聚合与状态机
- **Audit Store**：审计事件、执行轨迹、回执
- **Registry Store**：能力包注册、发布、停用状态
- **Search / Cache**：检索与页面加速
- **Legacy Adapter Reads**：只读读取 legacy MySQL / 文件 / 外部接口

### 9.5 Adapter 规则

adapter 只负责：
- 读取 legacy 数据（如需调研对比，**纯只读**）
- 为迁移评估提供输入证据

adapter 绝不负责：
- 成为新的业务写入口
- 承担新的业务状态机
- 把 legacy schema 原样扩散到 domain 层
- **作为常驻数据同步通道**（zw-brain 是全新项目，无历史负担；adapter 只在 PoC / 调研期出现）

### 9.6 数据库 schema 管理：drop & recreate，不背 alembic 历史负担

zw-brain 是**全新项目**，没有历史客户、没有存量数据需要迁移。本期数据库 schema 管理遵循"全新项目"原则：

- **SQLAlchemy `Base.metadata` 作为唯一 schema 真相**：`zw_brain/domain/models.py` 是 schema 单一事实来源
- **本机 / CI / 部署用 `Base.metadata.drop_all()` + `create_all()`**：每次启动重建 schema；不维护迁移链
- **alembic 不进入产品基线**：原 `alembic/` 目录（10 个迁移文件 + alembic.ini + env.py）**本期完全删除**——它是历史兼容思维的工具，与"全新项目"定位冲突
  - 原 0009/0010 D23 retrofit 迁移：在为不存在的 r1-r8 存量数据做映射，是逆向工程旧平台的副作用，本质性错误
  - 删除影响：`zw_brain/shared/migrate.py` 改为直接 SQLAlchemy 调用；`tests/test_alembic_*` 删除；`scripts/check_no_legacy_role_codes.py` 仅保留源代码 grep 检查
- **alembic 复活条件**：第一个真实客户上线 + 第一次生产 schema 变更时，把当时的 schema 作为新 baseline 重启 alembic（那时才有"迁移"的真实需求）；本期不未雨绸缪

### 9.7 这种边界为何符合 Jobs / OPC

- Jobs 视角：前台产品心智被压缩，但后台领域语义没有被偷掉
- OPC 视角：Phase 1 不因为概念过多而失控，先用少数聚合边界交付真实价值；schema 管理不背历史包袱，drop & recreate 是新项目的正确姿势

## 十、实施路线图

> **旅程编号说明**：本节按 J1 找数→用数 / J2 挂数→维数 / B1 看全局→处异常（后台支撑面） 命名。历史演化（旧 J1-J4 + S1/S2 → 3 旅程 → 2 旅程 + B1）见附录 D 决策记录。

### 10.1 Wave 0：机械守卫 + 首条黄金链路（首条 = J1 找数→用数的端到端 5 步）

目标：先证明"统一能力契约 + 合规边界 + 一条真实旅程"能成立，而不是先堆平台全景。

必须完成：
- Capability Registry 最小 schema
- WebUI / API / CLI 的契约投影打通
- MCP / A2A 从同一契约可生成，但不要求首波全部产品化
- 审计总线最小闭环
- 推理平台统一入口 mock / 封装
- **首条黄金链路 = J1 找数→用数**：检索 → 申请草稿 → 提交审批（含**有条件 / 无条件共享分支**两种内置流程）→ 通过后凭据领取 → 调用样例 → 调用监控；这一条必须能让客户跑通真实数据

一句话：**先做成一个真能用的最小产品，不先做一个看起来完整的平台。**

### 10.2 Wave 1：J1 闭环深化 + J2 挂数→维数最小闭环

优先做：
- J1 异议处理子流程（基线 ia-v2 §J1 异议子流程 6 步）
- J1 供需对接子流程（meta 合并，非数据合并；6 步流程）
- J2 在线编制 → 资源挂接 → 部门审 → 平台发布的核心 4 步
- 审计回执与基本运营可见性

约束：
- 不追求长尾覆盖率
- 不为每个入口分别开发业务逻辑
- 不为每个概念都升格成独立前台面与系统边界

### 10.3 Wave 2：AI 原生差异化三引擎 + B1 合规底线 + 共享专区
**Wave 2 关键升级**：原 §10.3 仅"J4 供给侧治理 + 注册治理"，扩为**三大 AI 原生差异化引擎**——这是 R14（项目级可配置 = AI 原生差异化）的兑现，也是 D25/D26 + 业务反馈 #6 的具体落地形态。

**三大差异化引擎（Wave 2 核心产品资产）**：

| 引擎 | 来源 | 解决什么 | AI 原生落点（§4.4 第 4 类） |
|---|---|---|---|
| **审批流可视化引擎**（D25 / 业务反馈 #4） | 项目级流程定制是基本盘（鞍山"编制→二级部门审→一级部门审→发布"） | 替代硬编码状态机；节点 + 选人规则 + 条件分支可配置；**先内置"有条件 / 无条件共享"两种基线流程**，再开放项目级编辑 | 自然语言生成流程草稿、节点建议、选人规则；管理员结构化确认入库 |
| **表单 schema 化引擎**（D26 / 业务反馈 #17） | 各项目（四川 / 荆州）表单都改；旧平台靠改数据库 | 字段、校验、布局 schema 化；不再回主仓发版 | 自然语言生成字段定义、校验规则；管理员结构化确认入库 |
| **智能推荐前置引擎**（业务反馈 #6） | 一开始不确定要哪些目录时应有推荐 | 需求登记前置：相似目录推荐 → 推荐失败再转人工需求登记 | 真正的 AI 价值落点；基于 J1 历史申请 + J2 资源元数据 |

**Wave 2 其他内容**：
- B1.1 合规与运营最小可用（异常发现 + 抽查 + 督查三段）
- B1.2 接入扩展中心（外部能力包注册、启停、回滚）
- 共享专区 / 专题包（P7，K11 必保留）
- 一表通可选预填 adapter（**降级路径**，不默认；详见 §3.4 C）

注意：这里仍然是"最小注册治理"，不是"生态产品化运营"。

### 10.4 Wave 3：协议扩展硬化 + 大屏 + 多租户深化 + 国家通道独立子旅程

包括：
- MCP / A2A 生产级硬化
- 大屏只读能力完善（K12）
- 多租户 / 多部门 / 多区域策略深化
- 成本、性能、调用配额、观测告警
- **国家数据直达**独立子旅程实现（业务反馈 #13，优先级 P2）
- **国家扩展要素目录编制**独立子旅程（业务反馈 #18，优先级 P2）

### 10.5 Wave 4：legacy 退役

退役判断标准不再是"迁完多少菜单 / 多少子系统"，而是：
- 核心旅程（J1 / J2）是否已被稳定替代
- 后台支撑面（B1）合规底线是否已被覆盖
- 长尾需求是否已被外部能力包覆盖
- legacy 是否仍承担唯一写入口
- 是否还能证明某项 legacy 表面必须进入新平台核心

### 10.6 明确不做的事

在首条黄金链路与 J1 / J2 闭环前，明确不做：
- 不先做面向普通用户的能力市场前台
- 不先做全协议等成熟度投入
- 不先做大而全的治理运营后台
- 不先为长尾 legacy 能力寻找"新平台安置位"
- 不接受客户级后端 fork 作为交付手段
- 不复造数据治理 / 数据安全 / 消息中心 / API 服务网关 / 应用中心脚本管理 / 数据存证 / 工单管理（详见 §3.4 B / C）
- **不维护 alembic 迁移链**（R15）：本期 schema 用 SQLAlchemy `drop_all` + `create_all`；alembic 删除
- **不开发 K12 大屏**（R17）：`zw-brain-dashboard/` 已删除；不再作为独立部署面承诺

## 十一、关键设计主张

> 本节用 **R-编号** 标注本基线的核心设计主张，作为后续实现与扩展的硬约束。新增决策追加请使用 D-编号（见 CLAUDE.md §决策记录）。
> R10-R17 为基线持续演化中追加的设计主张（源自 GATE-1.1 retrofit + 二轮反转 + reality check 三个阶段），与 R1-R9 同级生效。

### R1 — 产品叙事围绕"高频主旅程"，而非"平台能力全景"

影响：普通用户只需要理解 J1 / J2 两条核心旅程；B1 后台支撑面只对管理员/审计员可见，不进入普通用户主导航。

### R2 — 生态接入定位为后台支撑面，不进入前台旅程

影响：能力注册放在 B1.2 管理员面（归 B1 后台支撑面），不进入普通用户主导航心智中心。

### R3 — 五个消费面共享一套契约，但硬化顺序服从真实需求

影响：WebUI / API / CLI 先做实；MCP / A2A 同 contract 生成，但不要求首波等成熟度。

### R4 — 控制面必须存在，但以最小可用为先

影响：Registry / Policy / Audit 先服务主旅程和扩展秩序，不先长成平台产品。

### R5 — 领域概念完整保留，Phase 1 物理边界按聚合收敛

影响：承认目录、审批、交付、异议等是强状态领域，但不在首波一次性拆成全套独立系统边界。

### R6 — 代码实现服从 `entry → command → domain → shared`

影响：防止"运行时分层图"演化成另一套膨胀的代码组织。

### R7 — 外部长尾注册优先，主仓库只承接高频核心与底座

影响：OPC 模式下，主仓只保留高频核心与底座，长尾能力默认转向外部能力包路径。

### R8 — 反 per-tenant fork 作为硬边界

影响：客户差异只能通过配置、多租户策略、外部能力包实现，不能回到客户分叉后端模式；**强化**：客户差异中**项目级流程 + 表单 + 推荐规则**由 R14 三大引擎承接（不进主仓代码）。

### R9 — AI 原生定义为"关键摩擦点 AI 原生 + 项目级可配置化"，主工作流结构原生

影响：页面设计与原型评审以"结构化主旅程是否完整、AI 是否只在关键摩擦点减摩"为标准，而不是以"每页是否有 AI 组件"为标准；防止体验层滑向聊天框主入口或提示卡泛滥。与 R14 联动：AI 不只是页面减摩，更承担"把以前必须改代码改库的事变成可配置物"。

### R10 — 用户角色定义严格对齐旧平台 ROLE_* 码，不引入并行命名空间
影响：7 角色码（`ROLE_SYSTEM` / `ROLE_BUSIAUDIT` / `ROLE_ORGAN_MANAGER` / `ROLE_ORGAN_OPERATER` / `ROLE_SECURITY_ADMIN` / `ROLE_SECURITY_AUDIT` + `tag_lead_dept` 标签）冻结；新增需走 GATE + 业务方 sign-off；R1-R8 用户角色编号**已退役**，仓库 grep 残留 = 0 由 `policy.assert_no_legacy_role_codes()` + preflight 段 19 双层兜底。

### R11 — 角色与数据流向解耦：方向由运行时计算，不通过角色拆分表达
影响：部门管理员 / 操作员**同一角色既可为提供方也可为需求方**，方向由 `applicant_org_code` / `owner_org_code` 对照运行时计算；禁止再通过新增角色码表达"提供方 vs 需求方"方向。

### R12 — 工程术语不进 UI
影响：`package` / `projection` / `capability` / `write-with-audit` / `register-version` / `apply-tenant-policy` / `reconcile-receipt` / `submit-evidence` / `policy_decision` 等仅在代码与契约出现，前端必须用业务语义命名（详见 §5.5）。

### R13 — GATE-x 元规则：角色 / 业务流程 / 状态机决策必须业务方 sign-off
影响：任何"角色定义 / 业务流程 / 状态机"类决策必须有业务方（客户产研代表 / 海若产品部业务方）sign-off 才能进 D-编号；GATE-1 立项会议输出（白皮书 + 转写录音 + 角色梳理）是 GATE 决策的强制输入，不是参考材料；GATE-1.1+ retrofit 必须先做立项会议对照自检。建议同步进 `dev-rules/global/CLAUDE.md` §2 会话级硬纪律。

### R14 — 项目级可配置化是 AI 原生在政务场景的真正差异化
影响：Wave 2 必达三引擎（审批流可视化引擎 + 表单 schema 化引擎 + 智能推荐前置）；任何反对"项目级流程 / 表单 / 推荐通过改代码改库实现"的硬边界由本条约束；该条与 R8（反 fork）联动——客户差异由配置 + 多租户策略 + 外部能力包承接，**不由主仓代码分叉**。AI 在三引擎中的角色严格限定为"生成配置草稿，结构化预览，管理员确认入库"，不直接修改生产配置。

### R15 — 全新项目不背历史兼容，alembic 不进入产品基线
影响：zw-brain 是全新项目（无历史客户、无存量数据、无既存生产部署），schema 管理用 SQLAlchemy `Base.metadata.drop_all` + `create_all`，不维护迁移链；`alembic/` 目录、`alembic.ini`、`alembic/env.py` 本期完全删除；新功能直接改 `zw_brain/domain/models.py` + drop & recreate；CI / 本机 / 部署都重建 schema；第一个真实客户上线 + 第一次生产 schema 变更时再启动 alembic baseline。**对全新项目维护迁移链是历史兼容思维的副产品，干扰主目标 J1 黄金链路聚焦**。

### R16 — 产品形态变更触发 R13 业务方 sign-off
影响：本次产品形态从 3 旅程反转为 "2 核心旅程 + 1 后台支撑面"（详见 §5.1）是业务流程类决策，触发 R13 元规则；当前状态：**pending 业务方下次 review 二次 sign-off**；技术与产品研发负责人侧执行落地（前端 / 后端 / 文档），业务方评审前禁止对外宣称"3 旅程"或"2 旅程"为最终态；ia-v2.md 维持 3 旅程描述作为历史快照，本节为乔布斯式聚焦提案。元教训：sign-off 不是终点是起点，发现更精准的产品形态应该再走一次 sign-off，而不是装作没事。

### R17 — K12 大屏本期退役，不作为独立部署面承诺
影响：D15 历史决策"K12 必保留"反转。理由：（1）大屏不是 J1 黄金链路必要条件；（2）独立部署 + 独立技术栈 + 独立 BFF 分散 OPC 单人维护精力；（3）真正的客户大屏诉求未明确，提前内建违反 R7（外部长尾注册优先）；（4）旧平台"演示场景"占比高于"运营使用"，客户演示需求等真实出现再做。代码层：`zw-brain-dashboard/`、`zw_brain/entry/dashboard_bff.py`、`scripts/check_dashboard_readonly.py`、preflight 段 11、4 个相关 tests 全部删除。复活路径：作为外部能力包独立产品或 Wave 3+ 立项。
