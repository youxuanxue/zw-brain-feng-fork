# zw-brain 法人单位基础信息台账模板上层场景与 user journey 设计 v1

> 形成日期：2026-04-25  
> 目标：回答“法人单位基础信息台账模板”做出来之后，如何成为 zw-brain 的上层应用场景，而不是沦为一个后台标准配置对象；并明确它与 v4 主旅程、P5/P6/P7/P8 的一体化关系。  
> 结论摘要：**法人单位基础信息台账模板不应被设计成独立‘标准管理系统’，而应成为 zw-brain 面向所有涉企场景的默认基础信息复用能力：用户从需求发起开始，平台优先推荐复用该模板，贯穿发现、申请、交付与审计全链路。**

---

## 一、设计判断

“法人单位基础信息台账模板”的价值，不在于多了一张标准字段表，而在于让 zw-brain 能把涉企场景中的重复采集、重复解释、重复申请，收敛为一条统一链路：

- 有现成标准对象可发现；
- 有统一字段口径可复用；
- 有授权交付路径可执行；
- 有来源证据与审计链可追溯。

因此，它在产品层的正确定位不是：

- 一个给管理员看的字段后台；
- 一个独立“标准管理平台”；
- 一个要求用户先理解标准体系再做事的治理入口。

而是：

- **zw-brain 首个场景验证切片的默认复用对象**；
- **涉企数据需求的默认起点**；
- **P7 共享专区中的高频专题资产**；
- **P5/P6/P8 共用的一套标准能力底座**。

一句话说，它在 zw-brain 中应该被用户感知为：

**“关于一个法人单位的基础信息，平台已经有一套标准、可复用、可授权、可审计的底座，我先用它，而不是重新要数。”**

---

## 二、为什么它适合作为第一个上层场景

结合 `docs/approved/zw-brain-data-standards-slice-candidates-v1.md`，法人单位基础信息模板之所以适合作为第一个上层场景，不只是因为字段多，而是因为它天然符合 v4 的主旅程组织方式。

### 2.1 它天然跨旅程复用

这类字段不是单一事项专属字段，而是几乎所有涉企场景都会反复用到的基础对象字段，例如：

- 统一社会信用代码
- 机构名称
- 法定代表人
- 行业代码 / 行业门类代码
- 成立日期
- 登记机关
- 注册资本
- 经营场所

这意味着它不是某个垂直流程的局部配置，而是能够横跨：

- 资源发现
- 申请审批
- 授权交付
- 台账治理
- 合规审计

### 2.2 它更适合先验证“已有资产可复用”

v4 强调先打通黄金旅程，而不是先建全量治理平台。法人单位基础信息模板更适合验证的，是下面这组更基础也更关键的问题：

- 是否已有标准模板可被直接发现；
- 是否能覆盖绝大多数涉企基础字段需求；
- 是否能在用户发起需求时优先推荐复用；
- 是否能在交付时输出统一 schema；
- 是否能留下一条清楚的来源与使用审计链。

它优先验证的是“复用能力成立”，而不是“复杂事项流程成立”。

### 2.3 它更符合 Jobs 和 OPC 的减法

如果第一刀选的是事项型主题，产品很容易滑向：

- 状态机膨胀
- 证明材料膨胀
- 审批分支膨胀
- 专题流程系统膨胀

而法人单位基础信息模板更像一个平台级公共底座：

- 对普通用户足够直观；
- 对平台治理足够有价值；
- 对实现路径足够克制；
- 对后续第二刀事项型模板也有支撑作用。

## 三、在 zw-brain 中的产品定位

## 3.1 它不是“模板管理”，而是“默认基础信息复用能力”

对普通用户来说，平台不应该把它呈现为“请选择一个 CatalogModel 模板”。

普通用户真正关心的是：

- 这次涉企需求平台有没有现成底座；
- 我还要不要重新填这些基础字段；
- 哪些字段能直接取；
- 哪些字段还需要补；
- 谁能看、谁能拿、谁批、谁留痕。

所以，上层产品定义应当是：

**法人单位基础信息模板 = 涉企场景的默认基础信息复用能力。**

## 3.2 它在前台是一个专题化对象，在后台是一组统一资产

前台用户看到的，应该是：

- 一个高频可用的专题对象；
- 一组清晰的核心字段；
- 能做什么的能力入口；
- 使用范围、权限边界、最近更新时间、覆盖情况。

后台维护者看到的，才是：

- `CatalogModel`
- `catalog_model_field`
- schema / capability version
- source / evidence / authority / confidence
- 发布与版本治理

也就是说：**前台消费的是能力，后台维护的是资产。**

## 四、与 v4 主旅程的一体化关系

`docs/approved/zw-brain-architecture-v4-gpt55.md:324` 已明确，v4 前台收敛为四条核心旅程：J1 发现数据、J2 申请与审批、J3 交付与交换、J4 供给侧治理，并以 P5/P6/P7/P8 承载相应页面与支撑面。

法人单位基础信息模板不应另起一条新旅程，而应嵌入这四条现有主旅程。

## 4.1 J1 发现数据：先发现标准模板，而不是先造表

当用户产生一个涉企数据需求时，平台首先要做的不是让用户上传 Excel 或手填字段清单，而是优先判断：

- 是否已有“法人单位基础信息台账模板”可直接复用；
- 已覆盖哪些字段；
- 哪些字段属于缺口；
- 是否已有可申请的交付能力。

因此，它对 J1 的强化是：

- 把“找数据”提升为“先找有没有现成标准法人对象”；
- 把“字段检索”提升为“模板级复用判断”；
- 把“资源发现”从分散资源检索，提升为场景化对象发现。

## 4.2 J2 申请与审批：先判断能否复用，再判断是否准入新增

用户要发起涉企报表、共享申请、专题包补数时，系统先做一层标准模板匹配：

- 能被法人基础信息模板满足的，优先复用；
- 不能满足的，系统明确列出差异字段；
- 差异字段进入申请或准入判断，而不是整张表从零审批。

这样 J2 的体验会从“整单申请”变成“标准复用 + 差异补齐”。

这正是 zw-brain 想通过基层报表减负场景证明的减负点。

## 4.3 J3 交付与交换：输出统一 schema，而不是临时拼字段

一旦模板成为正式标准资产，交付时就不再需要每次重新拼接一套字段说明。

J3 里应默认支持：

- 以模板标准字段交付；
- 附带字段口径与值域说明；
- 附带来源证据与更新时间；
- 附带使用与授权回执。

因此，模板不是静态说明书，而是 J3 的统一交付骨架。

## 4.4 J4 供给侧治理：维护的是默认能力，不是孤立配置

在 J4 中，提供方真正维护的不是“某个后台配置项”，而是：

- 哪些字段足以构成法人基础画像；
- 哪些字段进入正式版本；
- 哪些字典和值域被绑定；
- 哪些字段仍处于待确认状态；
- 发布哪个模板版本给前台场景消费。

因此，J4 的治理动作必须直接服务前台复用效果，而不是长成一个与前台割裂的治理系统。

## 五、页面落位：P5 / P6 / P7 / P8 怎么协同

## 5.1 P7 共享专区 / 专题包：前台主入口

参考 `docs/approved/research-yibiaotong-zw-brain-v4.md:96`，基层报表减负类场景最适合通过 `P7 共享专区 / 专题包` 被前台组织出来。

法人单位基础信息模板在 P7 中应被设计成：

- 一个高频专题资产卡片；
- 一个“涉企基础信息”专题入口；
- 一个支持订阅、复用、查看覆盖情况的标准对象。

P7 上用户首先看到的应该是：

- 名称：法人单位基础信息台账模板
- 适用范围：涉企共享、报表预填、事项基础信息复用
- 核心字段摘要
- 可用动作：查看详情、申请取数、作为模板复用、查看差异字段
- 信任信息：来源等级、最近更新时间、版本号、责任方

这里的重点是：**把模板从后台对象变成用户可发现、可理解、可消费的专题资产。**

## 5.2 P5 提供方管理：维护与发布面

P5 负责供给侧动作，但不应该成为普通用户的主入口。

P5 中应承载：

- 核心字段集维护；
- 值域绑定与字段口径维护；
- 模板发布与下线；
- 版本变更；
- 异议处理与字段修订。

P5 关注的是“把资产做对”，不是“让所有用户都先来配模板”。

## 5.3 P6 合规与运营：复用、绕行与减负效果的判定面

当法人基础信息模板成为标准资产后，P6 可以围绕它形成一组运营和合规视角：

- 哪些涉企申请已直接复用模板；
- 哪些需求绕开模板重复要数；
- 哪些字段最常被补录；
- 哪些申请最常因“已有模板可满足”被打回重提；
- 模板是否真的减少了基层重复填报。

也就是说，P6 不是只看日志，而是围绕模板形成治理效果观察面。

## 5.4 P8 平台接入与扩展中心：管理员控制面与能力暴露治理

P8 不应作为普通用户主入口，但它必须承载：

- 模板相关 capability 的注册与暴露；
- schema version 管理；
- 外部系统可消费的接口边界；
- 权限与暴露范围控制。

对外系统、Agent、Skill 来说，法人基础信息模板不是一篇文档，而是一组稳定能力：

- 查询标准字段
- 按模板申请数据
- 获取模板版本与 schema
- 订阅模板变更

## 六、推荐的 user journey

法人单位基础信息模板最适合承载的第一条黄金旅程，不是“管理员新建模板”，而是：

**新建一个涉企需求时，平台优先复用法人单位基础信息模板，减少重复采集。**

下面给出推荐 user journey。

## 6.1 Journey A：业务用户发起涉企需求

### Step 1：用户表达业务目标

用户的起点不应是字段配置，而应是业务目标，例如：

- 我要做一张涉企报表；
- 我要为某专题包补法人主体信息；
- 我要核验一批企业基础画像；
- 我要申请一份法人基础信息共享数据。

平台在这一刻识别到：这是一个典型涉企基础信息需求。

### Step 2：平台优先推荐“法人单位基础信息台账模板”

系统给出的第一反应应是：

- 已存在可复用的法人基础信息模板；
- 当前需求已被覆盖的字段比例；
- 可直接复用的核心字段；
- 仍需补齐的差异字段。

这里 AI 的作用是把自然语言需求翻译成模板匹配建议，而不是替用户直接做责任性确认。

### Step 3：用户查看模板覆盖情况

用户进入模板详情页或专题详情页后，只需要快速看清三件事：

- 已覆盖什么；
- 还缺什么；
- 我可以直接做什么。

推荐呈现：

- 核心字段摘要
- 数据来源与责任部门
- 版本状态与更新时间
- 可交付方式
- 差异字段清单

### Step 4：用户选择复用动作

面向普通用户，动作应当极简，优先只保留：

- 直接查询 / 查看
- 发起共享或交付申请
- 作为报表 / 事项预填底座
- 查看差异并补充申请

不要把十几种治理动作暴露到这里。

### Step 5：平台生成结构化结果

根据用户选择，平台输出的不是一篇说明，而是一个可执行结果：

- 一份可查询的数据视图；
- 一份带标准 schema 的申请；
- 一份预填好的字段草稿；
- 一份明确的差异字段补件清单。

### Step 6：全链路留痕并可审计回放

从推荐、查看、申请、审批、交付到消费，整条链路都应写入审计事件：

- 用了哪个模板版本；
- 消费了哪些字段；
- 哪些字段来自标准模板；
- 哪些字段属于差异补录；
- 谁申请、谁审批、谁交付、谁消费。

这样，平台真正获得的是一条“标准资产被实际复用”的运营链路，而不只是一个模型定义。

## 6.2 Journey B：提供方维护模板

维护者旅程必须被放在后台，不干扰普通用户。

推荐流程：

1. 维护者发现涉企需求高频复用同一批基础字段；
2. 在 P5 中维护字段集、值域、来源与版本；
3. 发布新的模板版本；
4. 该版本自动成为前台推荐与交付的默认底座；
5. P6 持续反馈复用效果、绕行情况与异议。

这样，后台维护动作与前台复用效果能形成闭环。

## 七、AI 在这个场景中的正确角色

`docs/approved/zw-brain-architecture-v4-gpt55.md:359` 已明确，自然语言能力只能作为减摩组件，不替代结构化主流程。

因此，法人基础信息模板场景里，AI 适合做的是：

- 把一句话需求翻译成模板匹配结果；
- 识别可复用字段与差异字段；
- 生成申请预填草稿；
- 解释字段口径、值域、来源与更新时间；
- 生成审计摘要与复用建议。

不适合让 AI 自动做的是：

- 自动批准共享或交付；
- 自动确认责任性字段；
- 自动发布模板版本；
- 自动越权调用模板数据。

AI 在这个场景中的本质职责，是让用户更快进入结构化流程，而不是把流程本身聊天化。

## 八、最小可落地的页面体验

为了符合 v4 的减法原则，首版不需要新增独立“一表通中心”页面。

建议首版只通过以下组合完成体验：

1. **P7 专题卡片**：提供“法人单位基础信息台账模板”的发现与进入。  
2. **P2 / P7 详情页**：展示模板字段、覆盖情况、来源等级、版本、可用动作。  
3. **P3 申请页嵌入模板推荐**：用户发起涉企需求时先看到“可复用模板 + 差异字段”。  
4. **P5 模板维护页**：仅供提供方发布和修订。  
5. **P6 审计与运营视图**：看模板复用效果、绕行行为与减负成效。  

这就足以跑通首条黄金链路，而不必新增并列大模块。

---

## 九、与数据模型的对应关系

为了保证“上层场景”和“底层模型”一致，建议保持以下映射：

- 法人单位基础信息台账模板 → `CatalogModel`
- 模板字段定义 → `catalog_model_field`
- 模板对应的对外查询 / 交付 schema → `capability_version`
- 来源、版本、证据、置信度 → Registry / mapping evidence
- 前台专题对象 → P7 上基于上述资产聚合的 read model

这样可以保证：

- 前台没有自造一套模板概念；
- 后台没有脱离产品场景孤立建模；
- 同一个模板既能被 UI 消费，也能被 Skill / API / Agent 消费。

## 十、首个验收标准

如果“法人单位基础信息台账模板”被正确地设计成 zw-brain 的上层场景，首轮验收应至少满足：

1. 用户在涉企需求起点能被优先推荐到该模板，而不是从零填字段。  
2. 用户能看清已覆盖字段、差异字段、来源等级和可用动作。  
3. 申请与交付能够直接消费模板标准 schema，而不是每次临时拼字段。  
4. P5 能维护模板版本，P6 能看到复用与绕行情况，P8 能统一治理能力暴露。  
5. 整个体验没有新增一个并列“标准平台”或“一表通中心”主导航。  
6. AI 只做减摩，不替代结构化确认、审批和授权动作。

## 十一、推荐的下一步动作

1. 基于 `jbxx` 首批 12–20 个字段，形成“法人单位基础信息台账模板”首版字段确认清单。  
2. 为这批字段补齐 `source_type`、`authority_level`、`version_status`、`evidence_link`、`confidence`。  
3. 形成该模板对应的 `CatalogModel` / `catalog_model_field` / `capability_version` 映射底稿。  
4. 同步起草 P7 专题卡片、模板详情页、P3 模板推荐区的最小交互草案。  
5. 在后续 Wave 0 验证中，以“涉企需求优先复用法人基础信息模板”作为首条黄金链路候选。

## 十二、一句话定义

“法人单位基础信息台账模板”在 zw-brain 里不应只是一个后台标准对象，而应是：
