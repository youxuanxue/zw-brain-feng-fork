# zw-brain 数据标准最小切片候选与优先级建议 v1

> 形成日期：2026-04-25  
> 目标：基于 `old/08标准服务系统标准数据/` 的历史沉淀和 `old/09数据标准文件/` 的样本标准，收敛 zw-brain 首个场景验证切片候选，并明确优先顺序。  
> 结论摘要：**首选切片应为“法人单位基础信息台账模板”，次选切片为“人口-死亡事项台账模板”；不建议优先从生产经营、许可资质、行政处罚等大杂糅主题切入。**

---

## 一、判断依据

本次判断只使用两类证据：

1. **历史沉淀密度**：`old/08标准服务系统标准数据/` 中某类主题是否已有较多字段沉淀、是否已有少量可用字典、是否容易形成一个相对稳定的业务表模板。
2. **样本标准贴合度**：`old/09数据标准文件/` 中是否存在能直接为该主题提供数据元定义或值域支撑的样本标准。

遵循 Jobs / OPC 原则，本次不追求“覆盖最多字段”，而追求：

- 主题边界清楚；
- 标准样本能覆盖到核心字段；
- 便于先落一个 `CatalogModel`；
- 能较快验证“模板发现 → 取数/复用 → 审计追溯”的最小闭环。

---

## 二、已观察到的关键事实

## 2.1 `old/08` 的历史沉淀分布

主数据元表共约 **3611** 个数据元，分布很不均匀。

高频目录包括：

- `jbxx` 基本信息：**494** 个
- `scjy` 生产经营：**437** 个
- `xkzz` 许可资质：**361** 个
- `xzcf` 行政处罚：**314** 个
- `zbyzc` 资本与资产：**295** 个
- `shbz` 社会保障：**205** 个
- `sw` 死亡：**37** 个

但这些目录的“可直接拿来做最小切片”的质量并不相同：

- `jbxx` 虽然字段多，但主题边界最清楚，且样本字段明显围绕法人单位基础信息展开。
- `scjy`、`xkzz`、`xzcf` 虽然数量更大，但字段高度异质，像是多个行业和监管事项的混装池，不适合作为第一个标准业务表模板。
- `sw` 字段数量不大，但主题很集中，并且和人口样本标准目录中的“死亡数据元”直接对应。

## 2.2 `old/08` 中可直接看到的两个成型主题

### A. 法人单位基础信息主题（`jbxx`）

在 `old/08` 中，`jbxx` 的前排字段已经能组成一个稳定模板，包括：

- 统一社会信用代码
- 机构名称
- 经营范围
- 行业代码 / 行业门类代码
- 法定代表人
- 法定代表人身份证件类型代码
- 法定代表人身份证件号码
- 成立日期
- 登记机关
- 注册资本 / 实缴资本
- 从业人员数量
- 经营场所

同时存在少量直接可用字典：

- 行业门类代码
- 身份证件类型代码
- 机构性质代码
- 国别（地区）代码
- 活动地域类型代码
- 社会组织类型代码
- 社会组织状态代码
- 组成形式代码
- 经费来源代码

### B. 人口-死亡主题（`sw`）

在 `old/08` 中，`sw` 目录字段集中于死亡事项，示例包括：

- 死亡标识
- 死亡日期
- 死亡原因
- 生前常住地址
- 生前工作单位
- 逝者姓名
- 死亡地点代码
- 死亡年龄
- 死亡证明发证机关
- 死亡医学证明签发日期
- 火化日期
- 火化所在殡仪馆

同时存在直接对应字典：

- 死亡地点代码
- 丧葬补助类型

`DB37/T 4223.1—2020 政务信息资源 数据元 第1部分：人口`

## 三、候选切片排序

## 3.1 首选：法人单位基础信息台账模板

### 推荐等级

**P1 / 首选最小切片**

### 为什么最适合先做

1. **历史沉淀最厚且边界最稳。**  
   `jbxx` 有 494 个字段，是当前最成型的基础信息池，且前排字段明显属于法人单位基础画像。

2. **与样本标准直接贴合。**  
   `DB37/T 4223.2—2020` 就是法人单位数据元样本，天然适合作为首个字段确认依据。

3. **跨部门复用价值高。**  
   统一社会信用代码、机构名称、法定代表人、登记机关、行业门类、经营场所等字段，天然适合做“维护一次，多处复用”的台账模板。

4. **更符合 zw-brain 第一刀应该验证的能力。**  
   第一个切片更应该验证“是否已有标准台账可复用”，而不是一开始就切进复杂事项流程。

5. **字典约束已有最小基础。**  
   虽然多数字段仍是“无字典”，但至少已有行业门类、证件类型、机构性质等基础字典可用于首轮绑定。

### 推荐首批确认字段

建议第一轮只确认 12–20 个核心字段，不一开始铺满 494 个字段：

- 统一社会信用代码
- 机构名称
- 行业代码
- 行业门类代码
- 法定代表人
- 法定代表人身份证件类型代码
- 法定代表人身份证件号码
- 成立日期
- 登记机关
- 注册资本
- 实缴资本
- 从业人员数量
- 经营场所
- 机构性质代码
- 社会组织类型代码
- 社会组织状态代码

### 适合作为最小闭环验证的问题

- 是否已有标准法人单位模板可复用，避免重复要数。
- 某部门申请取数时，是否可直接从标准台账映射交付。
- 字段口径、来源证据、值域绑定是否可追溯。
- `CatalogModel` / `catalog_model_field` / `capability_version` 是否能支撑基础法人台账闭环。

---

## 3.2 次选：人口-死亡事项台账模板

### 推荐等级

**P2 / 次选切片**

### 为什么值得做，但不作为第一刀

1. **主题集中、标准样本贴合。**  
   `sw` 只有 37 个字段，但和人口样本标准中的“死亡数据元”章节贴合度很高。

2. **字典和事项语义都比法人基础信息更强。**  
   死亡地点代码、丧葬补助类型等字段，更像一个可运营的事项型模板。

3. **适合做第二个切片。**  
   在法人基础信息模板验证完毕后，死亡事项很适合用来验证更强的“事项状态 + 证明材料 + 准入审计 + 数据回流”能力。

### 为什么不建议先于法人单位基础信息

- 主题虽然集中，但事项属性更强，流程复杂度也更高。
- 一旦作为首刀，团队容易被拉向“事项流程系统”，而不是先把标准台账底座做稳。
- 对 zw-brain 来说，第一刀更适合先做跨部门都要复用的基础信息模板。

### 推荐首批确认字段

- 死亡标识
- 逝者姓名
- 死亡日期
- 死亡原因
- 死亡地点代码
- 死亡地点
- 生前常住地址
- 生前工作单位
- 死亡证明发证机关
- 死亡医学证明签发日期
- 火化日期
- 丧葬补助类型

## 四、不建议优先的主题

## 4.1 生产经营（`scjy`）

虽然有 437 个字段，但前排字段呈现明显的杂糅状态，例如 `ais类别`、`GPS时间`、`报刊出版单位`、`报纸类别` 等，说明它更像旧系统长期拼接后的混合池，而不是适合首刀的标准业务表。

## 4.2 许可资质（`xkzz`）

虽然有 361 个字段，但行业跨度过大，字段同质性弱，很容易把第一刀带入复杂监管场景。

## 4.3 行政处罚（`xzcf`）

虽然有 314 个字段，但事件性太强、业务语义过重，也更适合作为后续事项型专题，而不是最小标准切片。

## 4.4 社会保障（`shbz`）

虽然有 205 个字段，且和人口样本标准目录中的“社保数据元”有一定呼应，但目前样本证据没有像法人基础信息那样稳定，也没有像死亡主题那样边界集中。

---

## 五、建议的实施顺序

## 5.1 Wave 0 立即锁定

先锁定：

**切片 1：法人单位基础信息台账模板**

并把它作为以下对象的第一轮映射对象：

- `CatalogModel`：法人单位基础信息模板
- `catalog_model_field`：12–20 个核心字段
- Registry evidence：样本标准、历史来源、authority level、confidence
- `capability_version`：对外查询 / 取数 / 交付最小 schema

## 5.2 Wave 0 预备第二刀

并行保留：

**切片 2：人口-死亡事项台账模板**

作为下一轮事项型验证对象，用于补强：

- 事项字段的来源追溯
- 字典绑定
- 证明材料 / 签发机构类字段
- 在 zw-brain 前台场景中的事项复用与审计

---

## 六、推荐的下一步动作

1. 以 `jbxx` 为基础，抽取法人单位基础信息首批 12–20 个字段，形成字段确认清单。  
2. 将这 12–20 个字段逐一映射到 `DB37/T 4223.2—2020` 样本标准与现有历史字段。  
3. 为每个字段补上 `source_type`、`authority_level`、`version_status`、`evidence_link`、`confidence`。  
4. 生成首个 `CatalogModel` / `catalog_model_field` 映射底稿。  
5. 把 `sw` 主题保留为第二优先级切片，待首刀闭环后进入事项型验证。  

---

## 七、一句话判断

如果只选一个最小切片进入 zw-brain v4 的标准资产闭环，**应先选“法人单位基础信息台账模板”，而不是泛化的大目录，更不是生产经营/许可资质/处罚等历史混合池。**
