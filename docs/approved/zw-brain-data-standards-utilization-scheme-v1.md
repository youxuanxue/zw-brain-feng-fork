# zw-brain 数据标准原文件与历史沉淀数据利用方案 v1

> 形成日期：2026-04-25  
> 适用范围：`old/08标准服务系统标准数据/`、`old/09数据标准文件/` 以及与其直接相关的 zw-brain v4 架构/数据模型/一表通调研文档。  
> 本文目标：回答“业务侧提供的部分标准样本和旧平台沉淀数据，如何被克制地利用，支撑 zw-brain 的标准资产底座与首个场景验证闭环，而不是演变成另一个大而全的标准平台”。

---

## 一、结论先行

这批资料不能再被简单理解为“标准原文 + 结构化落地”两层模型，而应按真值等级和用途重新分层：

- `old/09数据标准文件/` 只是**已收集的标准样本与示例证据**，并不全面，不能充当完整权威标准库。
- `old/08标准服务系统标准数据/` 是**旧平台长期沉淀并导出的历史实现数据**，反映的是旧系统已经怎样做，而不是规范意义上的最终标准真值。

因此，zw-brain 对这批资料的正确利用方式不是“把旧标准服务系统搬进来”，也不是“先做全量标准库”，而是建立单一事实源链条：

**外部官方规范真值（L0） → zw-brain 内部机器真值（L1） → 标准样本证据（L2） → 历史实现观测（L3） → 待确认队列（L4）**

落地原则只有一句话：

**用最少必要的标准确认，把一个高价值主题切片写进统一 Registry / canonical model，先跑通 zw-brain 的首个标准资产闭环与场景验证链路。**

因此，这批资料最终应转化为四类长期资产：

1. 面向 `CatalogModel` 的标准业务表/台账模板资产。
2. 面向 `catalog_model_field` 的字段定义、值域、校验与口径资产。
3. 面向 `capability_version` 的统一契约 schema 资产。
4. 面向 Registry / adapter mapping evidence 的来源、版本、证据、置信度资产。

---

## 二、为什么现在必须重新定义这批资料的角色

结合 `docs/approved/zw-brain-architecture-v4-gpt55.md`、`docs/approved/zw-brain-data-model-v4-gpt55.md` 和 `docs/approved/research-yibiaotong-zw-brain-v4.md`，重新定义资料角色不是文字修订，而是避免走偏。

### 2.1 v4 要求单一事实源，不能把样本和沉淀误当真值

v4 已明确：legacy 只作为 adapter 输入面，不再成为新的业务写入口；系统运行时应只有一个内部机器真值源。如果把 `old/09` 误写成完整权威库，或把 `old/08` 误写成标准本体，后续 canonical 资产就会建立在错误前提上。

### 2.2 zw-brain 要的是标准资产最小闭环，不是再造标准平台

`docs/approved/research-yibiaotong-zw-brain-v4.md` 已说明，基层报表减负只是 zw-brain 用来验证平台价值的一类代表性场景；其长期资产仍是标准业务表、字段口径、值域、来源、权限边界，不是报表页面本身。Jobs 和 OPC 哲学都要求我们克制：先打通一个高价值场景，不做全量平台铺陈。

### 2.3 旧资料真正的价值，是加速选择“先做哪一个切片”

`old/08` 的价值在于暴露旧系统里哪些字段高频、哪些字典常用、哪些主题已经沉淀；`old/09` 的价值在于给这些候选主题补充一部分外部规范证据。两者都服务于“先做成一条链路”，而不是“先收全集”。

## 三、资料分层与真值层级

## 3.1 L0：外部官方规范真值源

来源：国家、行业、地方现行官方标准发布源。

角色：
- 是规范意义上的最终裁定来源。
- 决定标准号、版本、术语、定义、章节条款和适用范围。
- 当样本 PDF 与历史导出数据冲突时，最终以上游官方现行标准为准。

在 zw-brain 中的用途：
- 不作为运行时业务库直接接入。
- 作为标准确认环节的外部真值依据。
- 用于给进入内部机器真值源的资产提供裁定依据。

## 3.2 L1：zw-brain 内部机器真值源

来源：经确认后写入 Registry / canonical model 的正式标准资产。

角色：
- 是 zw-brain 运行时唯一承认的内部事实源。
- 是模板、字段、值域、契约 schema、映射证据的统一落点。
- 是共享专区、基层报表减负场景、准入审计、交付交换共同消费的标准资产底座。

在 zw-brain 中的用途：
- `CatalogModel`：标准业务表 / 台账模板。
- `catalog_model_field`：字段定义、约束、值域绑定。
- `capability_version`：对外输入输出 schema。
- Registry / mapping evidence：来源、版本、证据、置信度、映射链路。

## 3.3 L2：标准样本证据层

来源：`old/09数据标准文件/`。

角色：
- 提供已收集的标准样本、条款佐证和引用材料。
- 可为某个候选字段、值域、业务表模板提供证据支撑。
- 不能被表述为完整标准全集，也不能替代 L0。

在 zw-brain 中的用途：
- 作为 `evidence_link` 和来源说明的一部分。
- 为“为什么这样确认字段口径”提供可回看的样本证据。
- 在缺少更完整官方链接前，作为临时可引用材料，但其覆盖边界必须被显式标注。

## 3.4 L3：历史实现观测层

来源：`old/08标准服务系统标准数据/`。

角色：
- 反映旧平台长期沉淀并导出的历史实现结果。
- 暴露旧系统已使用过的数据元、字典、聚类、口径和重复建设痕迹。
- 适合做候选筛选、覆盖率分析、差异识别和实施经验抽取。

在 zw-brain 中的用途：
- 发现高频主题和高复用字段。
- 形成候选字段池、候选字典池、候选业务表池。
- 识别旧平台已有沉淀与现行标准之间的偏差。

## 3.5 L4：待确认队列

来源：在 L0/L2/L3 交叉核对过程中出现的冲突、缺失和不可判定项。

角色：
- 承接暂时无法判定的字段、值域、来源版本和映射关系。
- 明确把“不确定”留在队列里，而不是污染 L1。

准入规则：
- 未完成确认的项不得进入正式 `CatalogModel`、`catalog_model_field`、`capability_version`。
- 可作为草稿候选存在，但不能成为平台运行时默认真值。

## 3.6 真值优先级

发生冲突时，必须按以下顺序处理：

1. **L0 外部官方规范真值**
2. **L1 已确认的 zw-brain 内部机器真值**
3. **L2 标准样本证据**
4. **L3 历史实现观测数据**
5. **无法裁定则进入 L4 待确认队列**

这意味着：
- 不是“PDF 一定大于 XLSX”，而是“官方规范真值大于样本证据，已确认内部真值大于历史导出观察”。
- `old/09` 只能证明“我们已收集到这些样本”，不能证明“标准全集就是这些”。
- `old/08` 只能证明“旧系统曾这样实现”，不能证明“这就是今天应采纳的标准定义”。

## 四、与 zw-brain v4 架构和数据模型的对齐方式

## 4.1 对齐原则

这批资料进入 zw-brain 时，必须同时遵守四条约束：

1. 围绕主旅程与审计组织，不围绕 legacy 文件名和旧模块组织。
2. legacy 资料只作为 adapter 输入面、样本证据和历史观测，不成为新的业务写入口。
3. 正式标准资产统一进入 canonical model 与 Registry，不散落在页面配置、报表配置或个人表格中。
4. 以基层报表减负等场景包形态落在 P7/P5/P6/P8，不新增并列大平台。

## 4.2 在 canonical model 中的推荐落位

| 标准资产 | 推荐落位 | 用途 |
|---|---|---|
| 标准业务表 / 台账模板 | `CatalogModel` | 表达一类标准业务对象或台账模板 |
| 字段定义、是否必填、类型、长度、说明 | `catalog_model_field` | 表达字段约束、口径与展示/校验基础 |
| 值域字典与候选值 | `catalog_model_field` + Registry 辅助表 | 表达枚举约束、候选值解释与绑定 |
| 对外输入输出字段 schema | `capability_version` | 统一五消费面的契约输入 |
| 来源、版本、证据、置信度 | Registry / mapping evidence | 支撑追溯、审计、复核与争议裁定 |
| legacy 字段到 canonical 字段的映射关系 | adapter mapping evidence | 支撑迁移、回放、差异审查 |

## 4.3 建议补齐的最小治理元数据

每项进入 L1 的标准资产，至少应保留：

- `source_type`：official / sample_pdf / legacy_export / mixed
- `authority_level`：official_confirmed / internally_confirmed / sample_only / observed_only
- `version_status`：current / historical / unknown / pending_confirm
- `evidence_link`：外部规范或样本证据链接/路径
- `confidence`：high / medium / low

这五项不是为了把治理做重，而是为了让自动化和审计知道“这条定义有多可信、来自哪里、能否直接用于运行时”。

## 4.4 明确不做的事

- 不把 `old/09` 扩写成“完整权威标准库”。
- 不把 `old/08` 当成正式运行时标准库。
- 不按旧标准服务系统模块重建新导航和新子系统。
- 不为标准治理单独造一套平行于 v4 的大平台。
- 不在 Wave 0 追求全量标准收集、全量字典清洗、全领域覆盖。

## 五、原文件与历史沉淀数据分别怎么用

## 5.1 `old/09` 的正确使用方式：样本证据，不是全集

重点场景：

### 5.1.1 为候选字段或值域提供条款佐证

当我们准备确认某个主题切片中的字段、值域、名称或口径时，可引用 `old/09` 中已收集到的 PDF 样本作为证据。

### 5.1.2 为来源追溯提供初始证据链接

若某个标准资产暂时尚未补齐官方发布源，可先挂接样本 PDF 路径，并将 `authority_level` 标为 `sample_only` 或 `pending_confirm`。

### 5.1.3 为冲突分析提供参考对照

当 `old/08` 的历史字段定义与当前候选定义不一致时，可先用样本 PDF 辅助判断，但最终若要进入 L1，仍需以上游官方现行规范闭环确认。

## 5.2 `old/08` 的正确使用方式：历史观测，不是标准本体

重点场景：

### 5.2.1 提炼高频主题候选

从旧平台沉淀中识别：
- 哪类主题已经形成较稳定的数据元集合。
- 哪类字段跨表重复率高。
- 哪类字典在旧系统中高频复用。

这决定“先做哪个 zw-brain 场景验证切片”比决定“先建什么大平台”更重要。

### 5.2.2 提炼候选字段池与候选字典池

将历史导出数据整理成候选索引，用于发现：
- 可直接映射的字段。
- 可能需要合并去重的同义字段。
- 可能存在历史偏差或弱质量的字段。
- 哪些字段看起来高频，但证据不足，需进入 L4。

### 5.2.3 做覆盖率统计与缺口分析

适合统计：
- 某个候选业务表在旧系统中已沉淀多少字段。
- 有多少字段已有历史字典可参考。
- 有多少字段需要回到外部规范重新确认。
- 哪些字典存在重复码值、无字典占位、弱质量分类。

### 5.2.4 抽取旧系统实施经验，而不是继承旧系统结构

`old/08` 的价值是帮助我们知道旧平台哪里已经有沉淀、哪里重复建设严重、哪里最值得先收敛，不是要求 zw-brain 继续继承旧平台的目录和模块分法。

## 六、建议形成的最小落地产物

这批资料的利用不应停留在“阅读 + 归档”，而应沉淀为一组能支撑最小闭环的资产。

## 6.1 主题候选清单

目标：从历史沉淀中先选出一个最值得做的 zw-brain 场景验证切片。

每个候选主题至少回答：
- 跨部门复用价值是否高。
- 历史字段重复度是否高。
- 哪些字段可自动回填。
- 哪些字段必须由基层维护。
- 是否已有足够样本证据支撑首轮确认。

## 6.2 候选数据元主索引台账

目标：形成历史观察到的候选数据元统一索引，而不是直接宣布其为正式标准。

最小字段建议：
- `candidate_element_code`
- `candidate_element_name`
- `candidate_element_name_en`
- `domain_code`
- `domain_name`
- `data_type`
- `length_rule`
- `dictionary_code`
- `legacy_source_file`
- `sample_evidence_file`
- `authority_level`
- `version_status`
- `confidence`
- `status`
- `notes`

## 6.3 候选字典资产

建议拆分为：
- 字典主表：字典编码、字典名称、历史来源、状态。
- 字典项表：字典编码、项编码、项名称、排序、有效状态。
- 映射表：候选数据元编码 ↔ 候选字典编码。

注意：只有确认后才能升级为 L1 正式值域资产。

## 6.4 标准来源追溯字段

每项进入 L1 的标准资产都应保留：
- 来源类型
- 来源标准号
- 来源版本
- 来源文件或链接
- 引用条款/章节
- authority level
- confidence
- 确认批次

## 6.5 待确认清单

必须单独维护以下问题：
- 样本 PDF 与历史导出数据不一致。
- 无法确认现行官方版本。
- 字典重复码值或无效占位项。
- 字段存在弱质量，无法直接进入 canonical 建模。

## 七、如何服务 zw-brain 的前台场景与治理闭环

## 7.1 正确定位

这批资料的价值，不是支撑一个新的“报表中心”或“标准管理平台”，而是支撑 zw-brain 在基层报表减负、共享交换和标准资产沉淀上的前台场景与治理闭环：

- 在 P7 共享专区中形成标准业务表/台账模板资产。
- 在 P5 提供方管理中支持模板维护、字段治理、发布与变更。
- 在 P6 合规与运营中支持报表准入、取数留痕、绕行识别、基层负担分析。
- 在 P8 平台接入与扩展中心中支撑 Capability schema、版本治理和标准暴露。

## 7.2 优先支撑的能力

建议优先把资料用于以下能力，而不是先做大而全后台：

- 标准业务表模板定义。
- 字段去重与口径统一。
- 临时报表字段到标准数据元的映射。
- 已有台账是否足以满足临时报表需求的准入判断。
- 值域解释、字段说明、预填建议。
- 数据交付时的字段来源追溯与口径说明。

## 7.3 必须避免的方向

- 通用低代码表单平台。
- 另一个独立数据治理大平台。
- 与 v4 主旅程分裂的“一表通专属后端”。
- 只做报表页面，不做来源、准入、审计和追溯。

## 八、建议的实施路径

## 8.1 Wave 0：从历史沉淀中收敛一个最小切片

目标：不是“收全集”，而是“选准第一个闭环主题”。

应完成：
- 盘点 `old/08` 中的高频主题、字段和字典。
- 选出一个跨部门复用价值高的主题候选。
- 为该主题形成候选字段池和候选字典池。
- 用 `old/09` 补挂现有样本证据。
- 标出仍需补齐的官方规范来源和待确认项。

Wave 0 完成标准不是“做了一个界面”，而是“第一个主题切片已形成可确认、可映射、可审计的底稿”。

## 8.2 Wave 1：把切片写入统一 Registry / canonical model

目标：验证标准资产是否能真正进入 zw-brain 主旅程。

应完成：
- 将确认后的标准业务表写入 `CatalogModel`。
- 将确认后的字段与值域写入 `catalog_model_field`。
- 将对外消费所需字段写入 `capability_version`。
- 为每个字段保留来源、证据、置信度和映射关系。
- 验证“标准业务表发现 → 申请/准入 → 授权交付 → 审计回放”的最小闭环。

## 8.3 Wave 2：接入 zw-brain 前台专题场景

目标：让标准资产真正支撑场景，而不是停留在后台台账。

应完成：
- 接入 P7 共享专区 / 专题包。
- 接入 P5 提供方管理中的模板维护与发布。
- 接入 P6 的准入审计、取数留痕和基层负担分析。
- 接入 P8 的 schema 暴露与版本治理。

## 九、治理规则与风险控制

## 9.1 核心治理规则

1. **外部官方规范真值优先。** 任何正式裁定以上游官方现行标准为准。  
2. **zw-brain 内部机器真值唯一。** 一旦确认进入 L1，就以 Registry / canonical model 为运行时唯一事实源。  
3. **样本证据不是全集。** `old/09` 只能证明已收集样本，不能证明标准覆盖完整。  
4. **历史导出不是标准本体。** `old/08` 只能作为历史观测与候选来源，不得直接视为正式 canonical 资产。  
5. **争议字段进入待确认队列。** 不允许带病进入正式模型。  
6. **基层报表减负只作为 zw-brain 前台场景包复用 v4 底座。** 不得另起平行平台。  

## 9.2 已知资料质量风险

至少应预防以下问题：

- `old/09` 覆盖不全，无法承担完整规范库职责。
- `old/08` 中的字段和字典携带历史实现偏差，不一定符合现行标准。
- 可能存在无字典占位、重复码值、弱质量分类和历史清洗误差。
- 若直接继承旧系统结构，会把历史实现偶然性固化为新平台长期结构。

## 9.3 取舍说明

采用“少量确认、先做闭环”的路径，看起来慢于“直接拿旧 Excel 全量建模”，但它更符合 Jobs 和 OPC：

- 不把平台做重。
- 不把错误前提写进真值层。
- 不要求一次性收全集。
- 先形成一个能跑通、可审计、可复用的最小资产闭环。
