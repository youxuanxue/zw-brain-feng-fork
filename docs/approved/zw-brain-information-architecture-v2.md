# zw-brain 信息架构 v2：3 旅程 + 8 页面

## 一、设计原则

1. **用户意图为锚**：旅程按"用户想做什么"建模，不按"业务流程阶段"建模
2. **3 旅程上限**：超过 3 个一级入口，用户必然记不住；这是 Jobs 原则的下限
3. **页面服从旅程**：基线 §5.2 P1-P8 页面清单不变，每页只归属一个主要旅程
4. **首屏=待办**：所有人登录第一屏是"今日待办"（P1 工作台），不是菜单树
5. **每页一动作**：每个页面承载一个核心动作，工程术语全部从 UI 隐藏

## 二、3 旅程定义

### J1 找数→用数（Get Data）

| 维度 | 说明 |
|---|---|
| **用户意图** | 我要这份数据来做这件业务 |
| **典型用户** | 各业务部门（委办厅局）的部门操作员/管理员；偶尔上级业务司局 |
| **主要角色** | `ROLE_ORGAN_OPERATER`（发起申请）+ `ROLE_ORGAN_MANAGER`（部门内审/复核）+ `ROLE_BUSIAUDIT`（数据主管部门 = 大数据局，审批/受理） |
| **收敛旧** | 基线 J1 资源发现 + J2 申请审批 + J3 交付 |
| **闭环动作** | 发现 → 申请草稿 → 提交审批 → 通过后凭据领取 → 调用样例 → 调用使用 |
| **异常分支** | 不复用 → **需求登记 + 主管部门汇总（相似需求合并）+ 提供方认领/拒绝/复议**（详见下方"供需对接子流程"）；资源不满足 → 回流提供方补建（J2）；数据质量 / 接口可用性问题 → **异议处理子流程**（详见下方） |
| **不复刻** | 数据直达申请（属国家平台流程，作国家通道子旅程；红军原话"用得最少"，延后优先级最低）；代理授权申请（已无） |

#### J1 关键审批分支：有条件 vs 无条件共享（红军立项会议明确）

资源在编制时由数据提供方标定共享类型，决定审批人完全不同：

| 共享类型 | 标定方 | 审批人 | 流程 |
|---|---|---|---|
| **无条件共享** | 提供方编制时勾选 | **主管部门 `ROLE_BUSIAUDIT` 单独审批** | 申请 → 平台方受理并审批 → 授权 |
| **有条件共享** | 提供方编制时勾选 | **主管部门受理 + 提供方 `ROLE_ORGAN_MANAGER` 审批** | 申请 → 平台方受理 → 提供方审批 → 授权 |

这是 D25 审批流引擎延后立项时**必须最先支持的两种内置流程**；项目级定制（鞍山的"编制→二级部门审→一级部门审→发布"）在引擎上线后通过节点 + 选人规则配置。

#### J1 供需对接子流程（红军立项会议第二轮明确）

需求 → 数据这条线的实际多步骤多角色流程（**反馈 #1 处置的完整形态**）：

1. 需求方 `ROLE_ORGAN_OPERATER` → 提交需求登记
2. 需求方 `ROLE_ORGAN_MANAGER` → 校核（描述清晰度、合理性）
3. 主管部门 `ROLE_BUSIAUDIT` → **需求汇总**（识别相似需求合并；**是 meta 合并，不是数据合并**）
4. 主管部门 → 判断单部门数据 vs 多部门融合数据
5. **单部门** → 数据提供方 `ROLE_ORGAN_MANAGER` 认领
   - 认领 + 愿意提供 → 责任清单 → 关联已有资源或新建并发布 → 同步给需求方
   - 认领 + 不愿提供（涉密/法规等） → **数据拒绝清单**
   - 不认领 → **责任复议**（主管部门重新分发到其他部门）
6. **多部门融合** → 主管部门 → 需求治理分解 → 各部门分别走单部门认领流程

#### J1 异议处理子流程（数据共享核心服务体验，不归 J3）

数据使用中发现质量/可用性问题的标准闭环：

1. 使用方 → 异议填报（目录纠错 / 资源申请异议 / 数据使用异议 / 数据质量异议 / 服务响应异议 / 其他）
2. 主管部门 `ROLE_BUSIAUDIT` → 受理（合规性 + 信息完整性）
3. 主管部门 → 判断责任方：平台方问题（自留）vs 提供方问题（分发到 `ROLE_ORGAN_MANAGER`）
4. 相应方 → 提交核查回复（**实际整改是线下操作**，平台仅承载结论；红军原话）
5. 主管部门 → 异议审查（处理规范性）
6. 超时 → 督办（站内信 + 短信，红军原话"山东对接短信"）

#### J1 与外部数据治理中心的边界（反馈 #14 处置补强）

数据治理（清洗/质量/血缘）**不是本平台能力**，属外部"数据治理中心"（红军原话"得去联系石云志石总那边的"，即数据平台产品部）。本平台仅：
- 通过融合服务系统**注册并代理**治理平台暴露的数据接口（如治理后的数据服务）
- 在目录质量检测中做"目录是否长期无人申请"的旁路诊断（**目录质量**，非**数据质量**）
- 数据质量问题统一走 J1 异议处理子流程上抛给提供方

## 四、UI 原则（落实业务方 3 条 UX 反馈）

### 原则 1：每页一个核心动作（落实 U-1）

- 一个页面不要承载"查 + 改 + 申请 + 审批"四件事
- 列表页只做"查 + 进入详情"；操作走详情子页
- **删除所有工程术语**：以下词汇**禁止出现在前端 UI**：

  ```
  package / projection / capability / write-with-audit / register-version
  apply-tenant-policy / reconcile-receipt / submit-evidence
  ```

  改用业务语义：
  - `capability_call` → "操作"
  - `projection` → "视图" / "统计"
  - `package` → "能力包"（在 P8 接入中心可用）
  - `policy_decision` → "审批结果"

### 原则 2：首屏=今日待办（落实 U-2）

P1 工作台是所有角色登录后的默认页：

- 左侧：今日待办（按重要程度排序：超时 > 临期 > 普通）
- 中央：进行中事项（最近 7 天）
- 右侧：推荐 + 通知

不允许在 P1 显示菜单树作为主视觉。

### 原则 3：闭环必现凭据领取（落实 U-3）

申请审批通过后，P4 交付页面必须包含：

- 授权码 / API Key 查看与复制
- 调用样例（curl + Python + Java 三种）
- 调用配额（剩余次数/有效期）
- 调用监控入口（链接到 P6 合规运营对应视图）
