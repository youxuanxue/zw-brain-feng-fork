# zw-brain 真实用户角色清单与 end-to-end journey 蓝图 v1

> 形成日期：2026-04-25  
> 目标：明确 zw-brain 在政府与政务体系中的真实用户是谁，他们原来的岗位职责是什么，以及他们如何沿着统一产品链路使用 zw-brain。  
> 边界前提：传统“一体化大数据平台”主要面向国、省、市、区的数据交换与共享管理；传统“一表通”主要面向镇街道、村社区的一线填报减负。**zw-brain 的目标不是只服务其中一边，而是打通“上游共享资源池”与“下游基层填报链路”。**
> 结论摘要：**zw-brain 的真实用户不是抽象的“政府用户”，而是沿着“要数的人 → 管数的人 → 填数的人 → 审数的人 → 查责的人”这条跨部门、跨层级协同链展开的 8 类具体岗位。产品设计必须同时覆盖上游共享侧与下游填报侧，并把它们收敛进同一条发现—申请—交付—回流—审计链路。**

---

## 一、为什么必须先明确真实用户

如果不拆开真实岗位，产品很容易走向两个错误极端：

### 1.1 只按“一体化大数据平台”思维设计

这时产品看到的只有：

- 目录管理员
- 共享审批员
- 数据交换人员
- 接口调用方

结果是：

- 基层填报人员被排除在主旅程之外；
- 产品只剩共享与交换，没有真正解决“反复填报”的痛点；
- 上游资源无法在一线填报场景中被有效消费。

### 1.2 只按“一表通”思维设计

这时产品看到的只有：

- 镇街填报员
- 村社区填报员
- 审核汇总员

结果是：

- 产品只剩填报流程，没有把共享资源池真正接入前台减负；
- 一线填报结果也无法自然回流为标准资源；
- 系统仍会退化成一个“更集中的填表系统”。

### 1.3 zw-brain 的正确方向

zw-brain 要做的，是打通两边：

- 上游一体化平台的共享、交换、标准与目录能力；
- 下游基层报表减负场景中的预填、补录、审核、汇总和减负治理。

因此，zw-brain 的用户体系必须覆盖一条完整协同链：

**要数的人 → 管数的人 → 填数的人 → 审数的人 → 查责的人**

## 二、真实用户角色清单

## 2.1 角色总表

| 角色编号 | 真实岗位人群 | 所在层级 / 组织 | 原岗位核心职责 | 在 zw-brain 中的主要目标 |
|---|---|---|---|---|
| R1 | 上级业务需求发起人 | 省 / 市 / 区业务处室 | 发报表、要数据、做专题、做分析 | 优先发现现有资源与模板，只有缺口才新增采集 |
| R2 | 区县 / 部门审批承接人员 | 区县政数局、行业主管部门 | 审共享、审报表准入、判是否可复用 | 控制重复要数，判断复用还是新增 |
| R3 | 镇街道基层填报人员 | 镇街业务口 | 填报、维护台账、响应多部门要数 | 系统自动预填，只补缺口字段 |
| R4 | 村社区一线填报人员 | 村居、社区、网格末端 | 采集最细颗粒度信息、核实上报 | 轻量补录最末端动态信息，避免多头重复填报 |
| R5 | 镇街 / 区县审核汇总人员 | 镇街条线负责人、区县汇总岗 | 审核基层上报、退回修改、汇总上报 | 只处理异常与差异，自动汇总，不再人工拼表 |
| R6 | 数据提供方 / 台账管理员 | 部门数据科、业务系统管理员 | 维护台账、解释字段口径、提供共享数据 | 发布标准模板与标准字段，支撑共享与预填 |
| R7 | 数据共享 / 目录管理员 | 大数据局、政数局、平台运营方 | 编目、上架、权限配置、交换治理 | 把共享资源、模板、schema 编成统一能力入口 |
| R8 | 合规运营 / 督查 / 减负治理人员 | 督查、减负、审计、治理岗位 | 查绕行、查留痕、看减负效果 | 监测重复要数、绕开平台和基层负担改善情况 |

## 三、每类角色原来的真实工作是什么

## 3.1 R1 上级业务需求发起人：要数的人

典型人群：

- 省厅 / 市局 / 区局业务处室经办；
- 专项治理、主题分析、督查报送、业务统计的牵头人员。

原来的工作方式通常是：

- 以通知、Excel、系统任务等形式向下要数；
- 反复催报、补件、解释口径；
- 自行汇总结果后再做分析。

他们不是填表人，而是**需求发起人**。

在 zw-brain 中，他们应被引导为：

- 先发现现有数据资源；
- 先发现现有标准业务表 / 台账模板；
- 先判断能否由已有资源自动生成；
- 只有确有缺口，才发起新增采集或补录流程。

## 3.2 R2 区县 / 部门审批承接人员：控入口的人

典型人群：

- 区县政数局共享审批岗；
- 行业主管部门数据审核岗；
- 报表准入审批人员。

原来的工作方式通常是：

- 审核申请材料；
- 判断是否已有数据可复用；
- 协调多个部门；
- 决定是否允许继续向基层发起采集。

在 zw-brain 中，他们的核心价值不是做人工中转，而是：

- 判断这次需求能否被现有资源或模板满足；
- 判断是否属于重复要数；
- 拦截不必要的新报表和重复采集；
- 明确差异字段和责任边界。

## 3.3 R3 镇街道基层填报人员：被反复要数的人

典型人群：

- 镇街道办条线经办；
- 民政、人社、市监、应急、综治等基层业务填报岗。

原来的工作方式通常是：

- 接收来自不同部门的多张表；
- 在多个系统、Excel、群消息之间来回切换；
- 重复填写相似的基础信息；
- 被退回后再次修改并上报。

他们是基层报表减负场景最核心的服务对象。

在 zw-brain 中，他们不应该再承担“重复录入”这项低价值劳动，而应该：

- 接收已预填的任务；
- 核对系统自动读取的共享数据；
- 只补录真正缺失、最新、现场性强的字段；
- 一次确认，多处复用。

## 3.4 R4 村社区一线填报人员：最末端采集入口

典型人群：

- 社区工作者；
- 村两委工作人员；
- 网格员及协助采集的末端人员。

原来的工作方式通常是：

- 接受镇街或上级任务下派；
- 采集居民、企业、事项的细颗粒信息；
- 在多张表中反复填同类内容。

他们是最末端的数据入口。

在 zw-brain 中，这类用户的体验应尽量轻量：

- 任务轻量下达；
- 已有数据自动带出；
- 只要求补录最动态、最现场、最不可自动获取的信息；
- 不要求他们理解复杂的共享平台概念。

## 3.5 R5 镇街 / 区县审核汇总人员：审数的人

典型人群：

- 镇街条线负责人；
- 区县业务科室汇总岗；
- 负责口径审核、退回重填、汇总上报的人员。

原来的工作方式通常是：

- 收集基层表格；
- 人工核对差异；
- 人工汇总、退回、再汇总；
- 最终整理成上报数据。

在 zw-brain 中，他们应当：

- 只处理异常和差异项；
- 看到字段来源、口径和预填依据；
- 审核通过或退回补充；
- 自动生成汇总结果，而不是手工拼表。

## 3.6 R6 数据提供方 / 台账管理员：供数的人

典型人群：

- 部门数据科；
- 业务系统管理员；
- 维护本部门台账和资源目录的人员。

原来的工作方式通常是：

- 维护本部门业务数据；
- 回应共享需求；
- 解释字段含义和更新频率；
- 提供导出文件、接口或共享目录条目。

在 zw-brain 中，他们负责：

- 维护标准业务表 / 台账模板；
- 维护标准字段、值域、来源和版本；
- 把部门数据发布成可供预填与共享的标准资产；
- 让数据从“内部系统可用”升级为“跨层级、跨部门可复用”。

## 3.7 R7 数据共享 / 目录管理员：管共享秩序的人

典型人群：

- 政数局 / 大数据局目录管理员；
- 一体化平台运营人员；
- 数据交换共享平台管理员。

原来的工作方式通常是：

- 编目录、上资源、配权限；
- 审批共享申请；
- 管接口与批量交换任务；
- 维持平台运行秩序。

在 zw-brain 中，他们不再只管“上游共享”，还要连接上下游：

- 让共享资源真正进入一线预填；
- 让基层采集结果回流共享资源池；
- 把模板、schema、能力注册成统一出口；
- 管理跨部门、跨层级的共享边界。

## 3.8 R8 合规运营 / 督查 / 减负治理人员：查责的人

典型人群：

- 督查室；
- 减负办；
- 审计、治理、运营统计岗位。

原来的工作方式通常是：

- 看制度执行是否到位；
- 查是否绕开平台；
- 查是否留痕；
- 评估基层负担是否真的下降。

在 zw-brain 中，他们关心的不是技术日志本身，而是治理结果：

- 谁还在绕开平台要数；
- 哪些字段仍被基层反复补录；
- 哪些部门重复发起相似采集；
- 是否真正实现“一次填报，多处复用”。

## 四、角色优先级

虽然用户有 8 类，但产品主角并不平均分布。

## 4.1 第一优先级：真正承受负担的一线角色

- R3 镇街道基层填报人员
- R4 村社区一线填报人员
- R5 镇街 / 区县审核汇总人员

这是 zw-brain 必须真正减负的人群。

## 4.2 第二优先级：需求与准入控制角色

- R1 上级业务需求发起人
- R2 区县 / 部门审批承接人员

如果只优化基层，不优化“谁还能继续往下要数”，负担仍会反复回流。

## 4.3 第三优先级：平台持续运转角色

- R6 数据提供方 / 台账管理员
- R7 数据共享 / 目录管理员
- R8 合规运营 / 督查 / 减负治理人员

这类角色决定产品是否会长期退化回 Excel、线下群消息和临时报送。

## 六、四条“真人链路”

为了让产品收敛，不建议直接按 8 类角色各自独立设计页面，而应进一步压缩为 4 条更高层的真人链路。

## 6.1 链路 A：要数的人

包含角色：

- R1 上级业务需求发起人
- R2 审批承接人员

他们的核心目标是：

**先看现有资源和现有模板能不能满足，只有不满足时才新增采集。**

## 6.2 链路 B：填数的人

包含角色：

- R3 镇街道基层填报人员
- R4 村社区一线填报人员

他们的核心目标是：

**系统自动带数，我只补差异，一次填报，不重复填。**

## 6.3 链路 C：供数的人

包含角色：

- R6 台账管理员
- R7 目录管理员

他们的核心目标是：

**把已有共享资源、标准模板和 schema 管成可被前台直接复用的能力。**

## 6.4 链路 D：查责的人

包含角色：

- R8 合规督查人员
- 部分 R2 审批岗

他们的核心目标是：

**查是否重复要数、绕开平台、加重基层负担，并推动治理闭环。**

## 七、zw-brain 的 end-to-end journey 蓝图

zw-brain 的主链路不应只停留在“资源共享”或“基层填表”任一侧，而应把两边串起来。

推荐蓝图如下：

## 7.1 Journey 1：上级发起需求

触发者：R1 上级业务需求发起人

典型场景：

- 专题治理要数；
- 统计分析要数；
- 督查考核要数；
- 新报表需求。

用户动作：

- 用自然语言或结构化条件描述需求；
- 查询是否已有现成资源或标准模板；
- 查看覆盖情况和可用字段。

产品目标：

- 先把“我要新建一张表”改造成“先看有没有现成底座”。

## 7.2 Journey 2：系统优先推荐复用而非新增采集

参与者：R1、R2

系统动作：

- 发现已有目录资源；
- 匹配已有标准业务表 / 台账模板；
- 判断能否直接共享交付；
- 判断哪些字段可自动预填，哪些字段仍存在缺口。

产品目标：

- 让“新增采集”成为例外，而不是默认动作。

## 7.3 Journey 3：需要新增采集时，进入受控准入

参与者：R2、R5

用户动作：

- 审核新增报表或临时采集是否必要；
- 判定是否属于重复要数；
- 明确差异字段、责任边界和回流要求；
- 批准后再向下派发任务。

产品目标：

- 把过去无约束的“往下发 Excel”改造成一条有准入、有证据、有留痕的流程。

## 7.4 Journey 4：基层收到预填任务，只补缺口字段

参与者：R3、R4

用户动作：

- 接收任务；
- 查看已由共享资源自动带出的信息；
- 核对系统预填值；
- 只补录最动态、最现场、最缺失的部分；
- 提交结果。

产品目标：

- 让基层从“重复录入者”变成“差异确认者”。

## 7.5 Journey 5：审核汇总人员处理异常并形成上报结果

参与者：R5

用户动作：

- 查看异常项和差异项；
- 退回、补充或通过；
- 自动汇总并形成上报结果。

产品目标：

- 让审核岗从“人工拼表员”转成“差异处理员”。

## 7.6 Journey 6：结果回流共享资源池与标准资产体系

参与者：R6、R7

系统与用户动作：

- 将确认后的基层填报结果回流到共享资源池；
- 更新标准业务表、台账实例或 read model；
- 更新字段口径、版本和来源信息；
- 使下次需求可直接复用这次沉淀结果。

产品目标：

- 打通传统产品里“一体化资源池”和“一表通填报结果”之间没有真正闭环的问题。

## 7.7 Journey 7：合规与减负治理持续观察

参与者：R8

用户动作：

- 查看谁在绕开平台要数；
- 查看哪些字段仍被反复补录；
- 查看哪些申请明明可复用仍发起新增采集；
- 查看减负指标和制度执行效果。

产品目标：

- 把“减负”从口号变成可量化、可审计、可追责的运营结果。

## 八、各角色最适合看到的页面

为了服从 v4 的减法原则，所有角色都应落在现有页面体系中，不新增并列大平台。

## 九、第一阶段最该优先服务哪些人

如果按 Wave 0 的收敛原则，zw-brain 首阶段不应同时把 8 类人都做到很深，而应优先打通一条真实黄金链路。

推荐优先顺序：

1. **R1 上级业务需求发起人**：验证“先发现可复用资源，而不是先要新表”。  
2. **R3 镇街道基层填报人员**：验证“预填 + 差异补录”的减负体验。  
3. **R5 镇街 / 区县审核汇总人员**：验证“异常处理 + 自动汇总”的审核体验。  
4. **R6 / R7 供数与共享角色**：验证“共享资源赋能前台填报、填报结果回流资源池”的闭环。  
5. **R8 合规督查角色**：验证“有没有真正减少重复要数”的治理证据。  

这比先把全部角色都做成“后台功能”更符合 Jobs 和 OPC 的减法。

## 十、首轮验收标准

如果这份用户角色与 journey 定义是成立的，首轮应至少满足以下标准：

1. 不再把用户笼统描述为“政府用户”或“平台管理员”。  
2. 已明确区分一体化共享侧用户与一表通基层填报侧用户，并说明 zw-brain 要打通两者。  
3. 已形成 8 类真实角色清单，并给出其原岗位职责。  
4. 已把这些角色映射到 v4 既有 J1/J2/J3/J4/S1/S2 主旅程。  
5. 已形成一条完整的 end-to-end 蓝图：发现 → 复用判断 → 准入 → 预填补录 → 审核汇总 → 回流共享 → 合规治理。  
6. 已明确 zw-brain 的核心目标不是再造一个共享平台，也不是再造一个填表系统，而是打通跨层级数据协同链。

## 十一、推荐的下一步动作

1. 以“R1 需求发起人 → R3 基层填报人 → R5 审核汇总人”作为首条黄金链路，补一版交互草图。  
2. 将“法人单位基础信息台账模板”嵌入这条角色链，明确哪些字段来自共享资源池、哪些字段需要基层补录。  
3. 为 Journey 2–Journey 6 补一版责任边界和能力映射：谁发起、谁审批、谁补录、谁回流、谁审计。  
4. 同步抽取最小能力清单，形成后续 `capability_version` 与页面动作映射底稿。  
5. 在 P6 预定义一组减负治理指标，用于验证 zw-brain 是否真的减少重复填报。

## 十二、一句话判断

zw-brain 的真实用户不是单一“平台用户”，而是分布在政府跨层级协同链上的具体岗位人群；它的产品价值，也不在于单独服务共享侧或填报侧，而在于把“要数、供数、填数、审数、查责”真正打通成一条统一链路。
