# 政务"一表通"产品调研与 zw-brain 结合分析

> 关联架构：`docs/approved/zw-brain-architecture.md`
> 角色权威源：`docs/approved/zw-brain-roles.md`
> 结论摘要：zw-brain 的重构目标不是再造一个并列大平台；"一表通"应被吸纳为政务数据大脑在基层报表减负方向上的代表性应用场景与落地验证路径，优先落在共享专区 / 专题包、供给侧治理、合规运营与统一 Capability 契约之上。**一表通从默认路径降级为可选预填 adapter**（基线 §3.4 C / Wave 2）；首条黄金链路仍为基线 §10.1 J1 找数→用数。

## 一、调研结论

政务“一表通”本质上是围绕基层报表减负的数据共享与台账治理产品。其核心目标不是“做一个报表工具”，而是把过去上级部门多头向基层要数据的模式，改造成“统一入口、标准业务表、动态台账、按权限取数、全程留痕”的数据流转机制。

从重庆、江苏、内蒙古、江西等公开案例看，“一表通”产品有几个稳定共性：

- **统一入口**：基层不再面对多个部门、多个系统、多个微信群或临时报送渠道。
- **报表整合**：将历史报表按字段、口径、主题去重合并，形成标准业务表或数字台账。
- **台账沉淀**：将常态填报变为动态维护，将“反复填表”转为“首次录入、动态更新、按需复用”。
- **临时报表准入**：对确需下发的临时报表进行审批、下派、填报、审核、汇总。
- **数据共享回流**：上级业务系统、公共数据平台和基层采集数据双向流动，减少基层重复维护。
- **分析调度**：基于台账和报表沉淀数据，形成统计分析、风险预警、治理调度能力。
- **制度约束**：通过标准规范和运行管理办法，约束部门绕开平台向基层重复要数。

因此，“一表通”的产品价值在于：它把“基层填表”从一个低价值重复劳动，重构成一个可治理、可共享、可审计的数据供需链路。

## 二、典型产品形态

### 2.1 重庆“一表通”

重庆案例最接近完整产品形态。公开材料中明确提到“131”架构：

- 1 个统一入口：依托“渝快政”。
- 3 个核心模块：数字台账、智能报表、分析调度。
- 1 个镇街数据池。

其关键机制包括：

- 将历史报表梳理成各领域、各条线台账。
- 数字台账承载日常数据维护和报送。
- 智能报表承载临时、紧急报表任务。
- 分析调度基于台账和报表沉淀数据挖掘治理价值。
- 通过数据关联、智能填充、自动汇总减少人工重复填报。
- 通过报表准入、一键下派、辅助填报控制临时要数。

重庆还发布了《“一表通”智能报表市级业务数据规范》，明确业务表名称、数据元分类、格式、值域等核心要素，说明“一表通”后续竞争点会从应用组件走向数据标准、全生命周期管理和制度执行。

### 2.2 江苏“一表通”

江苏的公开表述强调省级统建和制度约束：全口径整合精简面向基层采集的报表，建设省级“一表通”系统，不再以其他渠道向基层采集数据。

这说明“一表通”的成败不只取决于系统功能，更取决于是否能形成“唯一取数渠道”的治理约束。若部门仍可绕开系统用线下表格、群消息或自建系统要数，减负效果会被迅速稀释。

### 2.3 内蒙古“一表通”

内蒙古案例强调跨层级贯通和标准数据表压缩：公开材料提到从大量部门报表压缩为少量标准数据表，并依托基层“根数据库”和专题库实现数据回流。

这类案例说明“一表通”有两条数据主线：

- 自下而上：基层采集、维护、反哺上级数据资源。
- 自上而下：上级公共数据、部门业务数据回流基层，支撑基层治理。

### 2.4 江西“一表同享”

江西“一表同享”与“一表通”同属基层报表减负方向，重点在表格压减、数据项压减、高频数据自动生成、一键填报、省级统建、五级覆盖。

它对 zw-brain 的启发是：产品命名可以不同，但核心模式稳定，即“表单治理 + 数据共享 + 自动填充 + 统一入口 + 制度约束”。

## 三、与 zw-brain 的总体关系

`docs/approved/zw-brain-architecture.md` 的一句话定位是：让政务数据从发现、申请、审批到交付，在一个简洁产品里被人和 Agent 通过同一能力面完成，并且全程合规可证迹。

"一表通"和本基线高度契合，但不应改变主架构方向。它不是新的顶层平台，也不是替代目录、申请、交付、审计主旅程的新中心，而是一个能验证基线价值的高频政务场景。

二者关系可以概括为：

- **基线提供底座**：统一 Capability、目录资源、申请审批、交付交换、审计回放、权限租户、注册治理。
- **一表通提供场景**：基层报表减负、台账维护、报表准入、数据复用、分析调度。
- **结合后的产品表达**：用户不再只是“找数据、申请数据”，还可以围绕某个专题台账实现“维护一次、复用多次、部门按权限取数”。

这意味着“一表通”适合成为 zw-brain 用来验证上游共享资源池与下游基层填报链路能否真正打通的代表性专题场景，而不是让 zw-brain 退回到旧式“大平台 + 大菜单 + 报表中心”的形态。

## 五、结合点

### 5.1 作为 P7 共享专区 / 专题包中的代表性验证场景

基线已经保留 `P7 共享专区 / 专题包`，而"一表通"最合适的进入方式，是作为 zw-brain 前台共享场景中的一个高频专题入口被组织进去。

建议将“一表通”设计为一个专题包，而不是新增主导航：

- 专题名称：基层报表减负 / 一表通。
- 核心对象：标准业务表、台账、临时报表任务、数据项、取数部门、基层维护责任。
- 用户目标：基层维护一次，部门按权限取数；确需临时报表时可准入、可追踪、可审计。
- 产品边界：只做高频基层报表减负链路，不做通用 BI 平台，不做任意表单搭建平台。

这样既承接"一表通"的市场热点，又不破坏本基线的产品减法原则。

### 5.2 作为 Wave 2 的高优先级落地验证场景

基线路线图中 Wave 2 包括"AI 原生差异化三引擎 + B1 合规底线 + 共享专区"。"一表通"之所以适合在这一阶段落地，是因为它正好能验证 zw-brain 是否已经具备把标准资产、共享入口、准入审批和治理约束串成闭环的能力：

- 它需要供给侧治理：谁定义台账、谁维护字段、谁发布标准业务表。
- 它需要共享专区：多个部门围绕同一台账按权限取数。
- 它需要最小注册治理：报表模板、字段标准、自动填充能力、分析能力都可以作为 Capability 注册和暴露。

不建议把完整一表通提前塞进 Wave 0。Wave 0 应继续验证“统一能力契约 + 合规边界 + 首条黄金链路”。但可以把基层报表减负链路作为候选黄金链路之一做最小切片，例如“残疾人信息业务表：字段标准化、自动回填、基层确认、部门取数、审计留痕”。

### 5.3 对 zw-brain 主旅程的补强

一表通可以补强本基线的两条核心旅程 + 后台支撑面：

- **J1 找数→用数**：部门发现已有台账和字段（不再重复下发表格）→ 新增报表任务必须经过准入审批 → 按权限获取台账数据、导出报表或订阅更新。
- **J2 挂数→维数**：基层和业务部门共同维护台账、字段、口径和数据质量。
- **B1 看全局→处异常**：合规与运营审计基层数据补差与共享异常。

这比单纯做"报表填报页面"更符合架构方向。

### 5.4 对数据模型的补强

基线数据模型中的 `CatalogModel`、`Catalog`、`Resource`、`Application`、`ApprovalTask`、`DeliveryTask`、`AuditEvent` 已能覆盖一表通的大部分语义。

建议先用现有聚合表达：

- 标准业务表 / 台账模板：作为 `CatalogModel` 的一种模板类型。
- 台账实例 / 主题数据集：作为 `Catalog` + `Resource` 的组合。
- 部门取数：作为 `Application` 或轻量授权申请。
- 报表准入：作为 `ApprovalTask`。
- 数据导出 / 订阅：作为 `DeliveryTask`。
- 填报、审核、取数、导出：全部写入 `AuditEvent`。

只有在实现临时报表任务时，如果现有 `ApplicationApprovalAggregate` 无法自然表达“下派、填报、审核、汇总、退回、关闭”的生命周期，再新增轻量概念：

- `ReportTask`：临时报表任务。
- `ReportSubmission`：基层填报提交。
- `ReportFieldMapping`：报表字段到标准数据元 / 台账字段的映射。

这三个概念应作为 Wave 2 的扩展，不应在 Phase 1 抢先膨胀成独立子系统。

### 5.5 对 zw-brain Capability 契约的补强

基层报表减负场景很适合作为 Capability 统一契约的验证面。建议后续设计以下能力：

- `ledger.template.create`：创建台账 / 标准业务表模板。
- `ledger.template.publish`：发布标准业务表。
- `ledger.record.upsert`：维护台账记录。
- `report.request.submit`：提交临时报表取数需求。
- `report.request.approve`：审批报表准入。
- `report.task.dispatch`：下派临时报表任务。
- `report.submission.submit`：基层提交报表。
- `report.submission.review`：审核退回或通过。
- `ledger.data.deliver`：按权限交付台账数据。
- `ledger.analysis.summarize`：生成分析调度摘要。

其中，涉及发布、准入、下派、提交、审核、交付的能力都应声明 `human_confirmation_required`，并写入审计与回执。

## 六、AI 结合方式

一表通很适合使用 AI，但只能作为副驾，不应替代结构化主流程。

适合 AI 的点：

- **字段去重与标准化建议**：识别多张历史报表中的同义字段、重复字段、冲突口径。
- **字段映射**：把临时报表字段映射到已有标准数据元、台账字段或公共数据源。
- **智能预填**：根据已有台账、公共数据平台、部门业务数据生成候选值。
- **缺项提醒**：提示哪些字段无法自动生成，需要基层补录或部门澄清。
- **口径解释**：解释统计口径、值域、数据来源和更新时间。
- **准入辅助**：判断临时报表是否可由已有台账满足，辅助审批人拒绝重复要数。
- **审计摘要**：总结某张表从创建、下派、填报、审核、取数到导出的全链路证据。

不适合 AI 自动完成的点：

- 自动批准报表准入。
- 自动下派责任性填报任务。
- 自动替基层提交带责任的数据。
- 自动授权跨部门或跨层级取数。
- 自动修改标准业务表口径。

这与本基线的原则一致：自然语言负责减摩，不负责越权提交。

## 七、风险与边界

### 7.1 最大风险：为了场景落地把 zw-brain 又做成另一个大平台

基层报表减负是强场景，但也最容易诱导产品膨胀：表单设计器、报表中心、BI 大屏、流程引擎、数据治理平台、低代码平台都可能被塞进来。

zw-brain 应避免这条路。正确边界是：只围绕基层报表减负和数据复用做必要能力，把长尾表单、复杂统计分析、行业专题应用外部化为 Capability 包。

### 7.2 制度不闭环会削弱产品价值

一表通不是纯技术系统。如果没有“不得绕开一表通向基层要数”的制度约束，部门仍会通过线下 Excel、微信群、自建系统重复要数。

因此在产品上必须内建：

- 报表准入。
- 取数留痕。
- 绕行线索记录。
- 部门取数统计。
- 基层负担度量。

### 7.3 数据标准是核心资产

一表通真正的长期资产不是报表页面，而是标准业务表、数据元、字段口径、值域、来源、更新频次、权限边界。

这部分应纳入 `CatalogModel` / Capability schema / Registry 治理，而不是散落在页面配置里。

### 7.4 基层维护责任必须可见

一表通容易从“减少填表”变成“换一种方式维护更多台账”。产品必须明确区分：

- 可由公共数据平台下沉的数据。
- 可由部门业务系统反哺的数据。
- 必须由基层走访维护的数据。
- 临时任务产生的一次性数据。

否则系统只是把报表负担换了名字。

## 八、建议落地路径

### 8.1 最小切片：作为 Wave 2 共享专区 P7 候选专题包

建议选择一个高共性场景作为 zw-brain Wave 2 共享专区 P7 候选专题包（**不抢镜首条黄金链路**——基线 §10.1 J1 找数→用数已固定为 Wave 0 唯一黄金链路），例如：

> 残疾人信息业务表：将民政、残联、镇街共同使用的历史报表整合为一张标准业务表，公共数据自动下沉，部门业务数据自动反哺，基层只维护无法自动获得的动态信息，部门按权限取数，全程审计。

这个切片的优点：

- 政策案例充分，便于对标。
- 字段重复、部门协同、基层维护责任都很典型。
- 能验证标准业务表、自动填充、权限取数、审计回放。
- 不需要一开始做通用表单平台。
- 与 §3.4 C"一表通可选预填 adapter"边界一致：基层补差是按需触发，不是默认路径。

### 8.2 Wave 建议

- **Wave 0**：**不进入**——首条黄金链路是基线 §10.1 J1 找数→用数（已固定），一表通仅作为概念输入。
- **Wave 1**：仍**不进入**——Wave 1 聚焦 J1 异议 / 供需对接子流程 + J2 最小闭环（基线 §10.2）。
- **Wave 2**：正式纳入 `P7 共享专区 / 专题包`（基线 §10.3 共享专区段），作为标杆专题包之一；补齐台账模板、临时报表任务、报表准入、基层提交、分析调度；一表通预填能力作为可选 adapter（基线 §3.4 C）。
- **Wave 3**：再考虑跨层级大规模推广、多租户策略深化、A2A / MCP 接入。

### 8.3 产品判断

zw-brain 值得把基层报表减负场景纳入统一底座，但进入方式必须克制：

- 进入的是“基层报表减负专题包”，不是“万能表单平台”。
- 复用的是本基线的 Capability、Catalog、Application、Delivery、Audit，不另起一套平行领域模型。
- 强化的是 P7 / P5 / B1.1，不新增普通用户主导航。
- AI 做字段、口径、预填、摘要，不做责任性动作。
- 制度约束和审计指标必须和功能一起设计。

2. **Wave 2 路线图中**：将“一表通最小专题包”列为共享专区的标杆场景。

不建议补：

- 不新增“一表通中心”主导航。
- 不新增完整报表平台章节。
- 不把一表通提前放入 Wave 0 必做项。
- 不把低代码表单、BI 报表、大屏分析全部塞进一表通范围。
