# zw-brain 角色规范：7 角色 + 牵头标签

## 一、设计原则

1. **沿用旧平台 ROLE_* 码**：客户、经理、运维已认知；零迁移摩擦
2. **角色 ≠ 方向**：部门管理员/操作员同时可为提供方/需求方，方向由数据归属决定，不由角色拆分决定
3. **菜单数决定权重**：高频角色对应 78-138 项菜单（部门双角色 + 主管部门），低频角色对应 11-49 项（运维 + 安全双角色）
4. **稀疏权限做标签位**：牵头部门只有 2 项菜单覆盖，不独立成角色，作为 `tag_lead_dept` 依附 `ROLE_ORGAN_MANAGER`
5. **零兼容**：全新项目无存量数据；`role_code` 仅允许 7 角色码集合，旧字面值（r1-r8 等）由数据库 CHECK 约束 + 启动检查拒绝

## 二、角色总览

| 角色码 | 中文名 | 旧平台菜单数 | 主要旅程参与 | 颁发主体 |
|---|---|---|---|---|
| `ROLE_SYSTEM` | 平台运维员 | 49 | 不在 J1/J2/B1 主面；运维专属页 | 平台承建方 |
| `ROLE_BUSIAUDIT` | 业务运营员 | 132 | J1 审批 / J2 复核 / B1 主面 | 数据主管部门 |
| `ROLE_ORGAN_MANAGER` | 部门管理员 | 138 | J1 申请审批 / J2 资源管理审核 | 各业务部门 |
| `ROLE_ORGAN_OPERATER` | 部门操作员 | 78 | J1 申请发起 / J2 资源编目挂接 | 各业务部门 |
| `ROLE_SECURITY_ADMIN` | 安全管理员 | 17 | B1 数据安全策略管理 | 数据主管部门 / 安全部门 |
| `ROLE_SECURITY_AUDIT` | 安全审计员 | 11 | B1 审计督查 | 数据主管部门 / 审计部门 |
| tag `tag_lead_dept` | 牵头部门标签 | 2 | 依附 ORGAN_MANAGER；仅基础主题分类审核 | 数据主管部门标定 |

## 三、各角色权限清单（xlsx 严格对照）

### ROLE_SYSTEM 平台运维员

**职责**：平台承建方运维，不参与业务流程；负责用户/组织/网关/消息/拨测/告警/工单。

**典型菜单覆盖**（49 项摘要）：

- 基础支撑 bsp：平台首页、组织机构、用户管理、权限管理、应用管理、参数设置
- 消息中心：消息任务、消息发送明细、消息监控、模板配置、业务类型配置
- 服务管理：服务流量控制、网关节点管理、黑白名单配置、过滤器配置
- 运行监控：运维管理工作台、系统运维工作台、服务调用日志、错误分析、告警配置、工单管理、巡检管理、知识库管理、服务拨测
- 目录管理（运维侧）：目录分类维护、目录分类授权、检测规则管理

### ROLE_BUSIAUDIT 业务运营员（数据主管部门 = 大数据局）

**职责**：**省/市大数据局**视角；平台业务处理；最终审批/发布权。立项会议（2026-04-17）红军原话定位为"数据主管部门"，对应客户现场即"省大数据局 / 市大数据局"。是供需对接里**做需求汇总（多部门相似需求合并）**的角色，也是**国家目录代认领**的发起方。

**典型菜单覆盖**（132 项摘要）：

- 目录管理首页、目录审核、**目录发布**、目录导出、目录查询
- 国家目录管理首页、主管部门目录审核、目录清单（与部门管理员共享视图）
- 资源挂接管理：**资源挂接发布**（部门管理员审核后由本角色发布）
- 目录开放管理：**开放目录发布**、**开放资源发布**
- 目录质量检测：人工质量检测、自动检测任务定义/管理、质量检测报告
- 统计分析：目录编制情况统计、目录关系图谱
- 资源系统概览、数据源管理、资源管理之资源发布
- 申请审核：受理申请、申请汇总、需求合并（meta 汇总，非数据汇总）
- 异议系统：异议受理、异议处置
- 数据直达：本级转报审核（非编制流程，是国家平台衔接）

### ROLE_ORGAN_MANAGER 部门管理员（= 各委办厅局管理人员）

**职责**：本部门内目录/资源/申请的审批权；既可代表提供方也可代表需求方部门。立项会议原话："各委办厅局它进行那个目录审核 / 资源审核 / 申请审批"。对应客户现场即各厅局（如省民政厅/省公安厅/省人社厅等）的内部管理人员。

**典型菜单覆盖**（138 项摘要）：

- 目录编制：在线编制、反向编目、批量导入（与操作员共享）
- 目录管理：目录维护、目录审核、目录撤销、目录导出、目录迁移审核（迁入部门审核）、目录查询、**目录上报**
- 国家目录管理：基本要素目录导入、目录下发、目录认领（垂管下级部门）、目录认领异议审核、目录编制、**业务部门目录审核**、历史目录处理审核
- 资源挂接管理：国家目录资源挂接、资源挂接、**资源挂接审核**、资源撤销审核、资源维护
- 资源系统：数据源/资源管理（部门视角）
- 申请审核：本部门发起的申请的提交后跟踪 / 本部门作为提供方时的审批
- 异议系统：作为提供方时的异议处置

**特殊：tag_lead_dept 标签位附加权限**：

- 基础主题分类关联管理：牵头部门审核
- 基础主题分类关联管理：牵头部门撤销

### ROLE_ORGAN_OPERATER 部门操作员（= 各委办厅局具体经办人员）

**职责**：本部门内目录/资源/申请的具体操作权；无审批权。立项会议原话："各委办厅局里边进行目录梳理目录编制的人员"。对应客户现场即各厅局的具体业务经办人（如某厅 IT 处的目录编制员、数据使用申请经办员）。

**典型菜单覆盖**（78 项摘要）：

- 目录编制：在线编制、反向编目、批量导入
- 目录管理：目录维护、目录撤销、目录导出、目录查询
- 国家目录管理：目录编制、历史目录处理
- 资源挂接管理：资源挂接、资源维护
- 资源系统：资源注册、资源开发
- 申请审核：申请提交、需求提交
- 应用中心：应用注册、我的应用、我的资源、资源申购车

### ROLE_SECURITY_ADMIN 安全管理员

**职责**：数据安全中心独立模块管理；不参与目录/资源/申请业务流程。

**菜单覆盖**（17 项完整）：

- 数据安全中心 / 工作台
- 数据资产：数据源管理、数据资产透视
- 数据识别：数据分类分级、识别规则管理、识别任务管理、识别任务记录、敏感数据管理
- 数据保护：分级保护策略、脱敏策略配置、静态脱敏任务、密码应用配置、平台密钥管理
- 风险治理：数据风险视图、风险识别规则、风险告警处置
- 系统设置

### ROLE_SECURITY_AUDIT 安全审计员

**职责**：审计/存证/溯源；只读为主。

**菜单覆盖**（11 项完整）：

- 基础支撑 bsp / 日志管理
- 运行监控 / 日志审计：登录日志、审计日志
- 数据安全中心 / 风险治理 / 日志事件查询
- 数享链 / 数据存证：用户存证、机构存证、系统存证、目录存证、资源存证、申请授权存证
- 数享链 / 数据溯源：接口调用溯源

## 四、字段建模

`actor_org_role_binding` 表（沿用现有 `models.py:773-785` 结构，仅加约束）：

| 字段 | 类型 | 说明 |
|---|---|---|
| `tenant_id` | str | 单租户 sd-default |
| `external_actor_id` | str | IAM 主键（OIDC sub） |
| `org_code` | str | 部门统一社会信用代码或机构码 |
| `role_code` | enum(7) | 限定上述 7 个 ROLE_* 之一 + admin / system |
| `tags` | jsonb | 含 `tag_lead_dept: bool` 等可选标签位 |
| `valid_from` / `valid_to` | datetime | 角色绑定有效期 |
| `granted_by` | str | 颁发主体 actor_id |

**约束**：

- 同一 `(tenant_id, external_actor_id, org_code, role_code)` 唯一
- 同一 `external_actor_id` 可在多个 `org_code` 持有不同角色
- `role_code` CHECK 约束限定 7 角色 + admin/system；写入 `r1`-`r8` 拒绝

## 五、提供方 vs 需求方方向如何判断

7 角色码**取消方向角色**——同一角色（如 `ROLE_ORGAN_MANAGER`）既可代表提供方也可代表需求方，方向由运行时计算：

| 场景 | 判断逻辑 |
|---|---|
| 申请受理（J1） | `application_record.applicant_org_code == actor.current_org_code` → 申请方视角 |
| 资源管理（J2） | `resource_asset.owner_org_code == actor.current_org_code` → 提供方视角 |
| 目录审核（J1/J2） | `catalog_entry.owner_org_code == actor.current_org_code` → 编目部门视角 |

`actor.current_org_code` 来自 session 携带的 `org_code`；同一角色（如 ORGAN_MANAGER）在不同上下文自然展现不同入口与按钮。

## 六、UI 暴露原则（IA 引用）

- 角色码（`ROLE_*`）**不在前端显示**，只用中文名（如"业务运营员"）
- 标签位（`tag_lead_dept`）**在个人信息页**展示为"基础主题分类牵头资格"
- 跨部门授权场景（同一人持多角色），登录后由用户**显式切换部门上下文**，不静默合并
- 工程术语（`policy_decision` / `capability_call` / `projection` / `package` 等）**全部从 UI 隐藏**，只留业务语义

## 七、角色 → 旅程典型任务地图

以下表格回答"每个角色在 J1 / J2 两条核心旅程 + B1 后台支撑面分别承担哪些高频任务"。任务名为业务语义，技术细节见对应 skill manifest。

### `ROLE_ORGAN_OPERATER` 部门操作员

| 旅程 | 典型任务 | 频度 |
|---|---|---|
| J1 找数→用数 | 检索目录、提交申请、查看自家申请进度、领取凭据、调用 API、提交服务评价 | 高 |
| J2 挂数→维数 | 在线编制目录、反向编目（基于 schema 草拟）、批量导入、资源挂接、提交审核 | 高 |
| J1 补差（基层场景） | 接收上级派发的补差任务、字段补录、异常回传 | 中（仅基层归口部门） |

### `ROLE_ORGAN_MANAGER` 部门管理员（含可选 `tag_lead_dept`）

| 旅程 | 典型任务 | 频度 |
|---|---|---|
| J1 找数→用数 | 审批本部门申请（按 owner_org 决定提供方/需求方视角）、暂停/收回授权、汇总确认 | 高 |
| J2 挂数→维数 | 部门内目录审核、资源挂接审核、资源维护、目录撤销、目录上报 | 高 |
| J1/J2 国家通道 | 国家目录认领、基本要素目录导入、目录下发、历史目录处理 | 中 |
| J2 牵头部门（仅持 `tag_lead_dept`） | 基础主题分类审核、基础主题分类撤销 | 极低 |

### `ROLE_BUSIAUDIT` 业务运营员（数据主管部门）

| 旅程 | 典型任务 | 频度 |
|---|---|---|
| J1 找数→用数 | 平台侧申请受理与最终授权、数据直达申请审核（国家通道）、异议受理 | 高 |
| J2 挂数→维数 | **目录发布 / 资源发布 / 开放目录发布**（主管部门最终发布权）、字段口径裁决、挂接审核驳回复核 | 高 |
| B1 看全局→处异常 | 目录质量人工检测、自动检测任务管理、统计分析、关系图谱、共享专题与能力包注册 | 中 |

### `ROLE_SECURITY_ADMIN` 安全管理员

| 旅程 | 典型任务 | 频度 |
|---|---|---|
| B1 看全局→处异常 | 数据分类分级、识别规则管理、敏感数据管理、脱敏策略配置、密钥管理、风险识别规则、风险告警处置 | 中（独立模块） |

### `ROLE_SECURITY_AUDIT` 安全审计员

| 旅程 | 典型任务 | 频度 |
|---|---|---|
| B1 看全局→处异常 | 审计日志查询、登录日志、数享链存证（用户/机构/系统/目录/资源/申请授权）、接口调用溯源、合规事件案件调查 | 中 |

### `ROLE_SYSTEM` 平台运维员

| 旅程 | 典型任务 | 频度 |
|---|---|---|
| 平台底座（不在 J1/J2 用户旅程内） | 组织/用户/权限管理、消息任务监控、服务网关配置、服务流量控制、运维工单与巡检、服务拨测 | 中（按需） |

## 八、安全约束

- 角色码集合**冻结**，新增角色需走 GATE 流程 + 业务方 sign-off
- 任何代码中出现 r1-r8 字面值由 `policy.assert_no_legacy_role_codes()` 启动检查 + `scripts/check_no_legacy_role_codes.py` preflight 段 19 双层兜底
- IAM 同步：组织上若需 IAM 端调整 realm_roles 列表，必须先在本文新增角色码并 sign-off
- 跨文件角色码一致性由 `tests/test_role_codes_alignment.py` 机械验证
