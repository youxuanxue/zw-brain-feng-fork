## 1. 这份文档解决什么

旧平台（一体化政务大数据平台 / 数据共享平台）能力不缺，缺的是**任务化的入口**：23 个产品功能、38 个子项目，
用户卡在三件事上——**入口爆炸**（菜单驱动非任务驱动）、**术语混乱**、**待办投影不准**（见 `old/问题反馈/`、`old/使用日志分析情况/`）。

zw-brain 已把它重构为三条黄金旅程（J1 找数→用数、J2 挂数→维数、B1 后台支撑）和单一能力契约（185+ 能力 → 5 消费面）。
**场景智能体的机会**：在这条已经收敛的能力底座上，沿旅程把"多步骤 + 多菜单 + 靠人记"的任务，
压成"一句话 → 智能体起草 / 分诊 / 推荐 → 人按角色拍板"的副驾体验。

## 2. 设计包络（硬约束，先框边界再发散）

来自 `schemas/agent.schema.json`、`agent-runtime.yaml`、`docs/approved/zw-brain-architecture.md` §8、`docs/agent-runtime-t1-readiness.md`：

| 维度 | 约束 | 对场景设计的含义 |
| --- | --- | --- |
| **承载形态** | anp-agent/v1.2 manifest；`AGENT.yaml` 写 `tools: []`，真实工具在 `capabilities.json` 的 `capability_tools[]` 里把 `skill_id → LLM 工具` 动态注入（两个现有 agent 都这么写） | 一个场景智能体 ≈ 指令 + 选定的既有能力子集 + 模型/限额。**默认零新后端**。 |
| **能力来源** | 只能调用 Capability Registry 已注册的 185+ 能力（`data.search`/`catalog.entry.create`/`approval.review_decide`/…） | 发散时每个设想必须能映射到现有能力簇；映射不上的标记为"需新增能力"另立项。 |
| **§8.5 禁区** | 智能体**禁止**：租户策略评估、权限裁决（改 ROLE_*）、写审计、改 canonical 状态机（Application/Approval/Delivery）、直连模型入口 | **铁律：场景智能体只做"起草 / 分诊 / 校验 / 推荐 / 问答"，最终落库的状态变更永远由对应角色的人拍板。** 这条直接决定了下面每个智能体的"安全形态"。 |
| **运维员生命周期** | 运维员（ROLE_SYSTEM）在 B1.2 管理面：trust_level 升降、`tenant.capability.{enable,disable}`、版本回滚、5 消费面暴露配置；**不改**注册者的指令/工具 | 构建/配置/启用/停用全在运维员权限内 —— 与本任务约束一致。每个智能体声明 `trust_level: platform`、`exposes_chat/exposes_a2a`。 |
| **模型** | D68 后模型出口只在独立 AgentRuntime 服务侧：`default_model_provider: openai_compatible`，默认模型由 `${env:AGENT_RUNTIME_DEFAULT_MODEL}` 注入，网关由 AR 服务读取 `OPENAI_COMPATIBLE_*`（集团推理平台，trusted_gateway，不允许 LLM 外联） | 所有智能体共用集团推理，温度/最大 token/工具调用上限按场景调；现有 agent 用 `max_tool_calls: 10` 防循环。 |

**由此推出贯穿全局的乔布斯式原则：**

- **聚焦**：一个智能体 = 一个角色、一条旅程里的一件事。不要"全能政务助手"。
- **简洁**：智能体是叠在既有能力上的副驾，生命周期是运维员"开/关一个开关"，不是为每个智能体写一套后端。
- **端到端**：智能体沿旅程串成链（发现→申请→跟踪→交付），但每个都能独立发布、独立产生价值。
- **设计即工作方式**：manifest 就是规格，`capabilities.json` 绑单一能力契约，5 消费面自动投影。
- **精品意识**：先把 Wave 1 做到能演示、能签收，再铺后面；不出"假面 / 半成品"智能体（延续 honesty 文化）。

## 3. 收敛判据（自上而下砍取的五条尺子）

发散之后用这五条收敛，每条都能让用户独立调权重：

- **C1 真实痛点支撑**：有 `old/问题反馈/` 或 `使用日志` 的实证支撑，不是凭空想象的"看起来有用"。
- **C2 复用既有能力**：能映射到现有 185+ 能力（零/低新后端）。需大量新能力的降级或推迟。
- **C3 落在副驾安全区**：只做起草/分诊/校验/推荐/问答，不碰 §8.5 禁区与 canonical 写。
- **C4 黄金链路优先**：J1/J2 高频旅程 > 周边低频工具（共享专区、绩效看板等已被业务方判为低频）。
- **C5 角色清晰**：服务对象是某个明确角色的明确任务（用数方操作员 / 供数方管理员 / 运营员 / 运维员 / 审计员）。

## 4. 发散全景（multi-directional 设想）

不按"清单"罗列，而按四个正交轴铺开可能性空间，便于看清"还能往哪长"和"哪些是重复"。

**轴 A · 黄金旅程**：J1 找数→用数 ｜ J2 挂数→维数 ｜ B1 后台支撑/治理
**轴 B · 服务角色**：用数方(操作员/管理员) ｜ 供数方(操作员/管理员) ｜ 业务运营员 ｜ 平台运维员 ｜ 安全审计员 ｜ 业务决策者
**轴 C · 智能体原型**：发现/搜索 ｜ 向导/起草 ｜ 校验/质检 ｜ 分诊/路由 ｜ 匹配/推荐 ｜ 监控/告警 ｜ 报表/洞察 ｜ 问答/指南
**轴 D · 数据域钩子**：目录(catalog) ｜ 资源元数据(metaresource) ｜ 服务/API(service) ｜ 应用/申请(app) ｜ 交换/对账(connect/pipelines) ｜ 供需(require) ｜ 异议(handling) ｜ 主题库/画像(basesubject) ｜ 区块链审计(block) ｜ 监控(monitor)

把轴 A×C 交叉，就是下面收敛集的来源（每格至少一个候选）：

```
                发现   向导/起草   校验/质检   分诊/路由   匹配/推荐   监控/告警   报表/洞察   问答
J1 用数方        ①        ②           ④           —          ①          —           —        ⑲
J2 供数方        —        ⑥⑦          ⑨           —          —          —           —        —
申请/审批        —        ②           —           ⑫          ⑭          ⑬          —        ③
交付/对账        —        —           ④           —          —          ⑬          —        —
供需对接         —        ⑪          —           —          ⑩          —           —        —
B1 运维/治理     —        ⑳          ⑰          ⑮          —          ⑯          ⑱        ⑲
```

（圈号对应第 5 节收敛集编号；空格＝该格暂判为低杠杆或落 §8.5 禁区，发散保留、收敛砍掉。）

## 5. 收敛提案：~20 个场景智能体

分 4 个 Wave（聚焦：先核心链路，后周边）。每条标注：**服务角色 · 痛点 · 消费能力(示意 skill_id，构建时校验) · 形态**。
两个已存在的智能体（`zw-platform-guide`、`zw-search-helper`）纳入清单但标注「已有」，净新增约 18 个。

### Wave 1 · 核心黄金链路（先做、做到能演示签收）

**① 数据发现副驾 `data-discovery-copilot`**（升级现有 `zw-search-helper`）
服务：用数方操作员/管理员 · 痛点：搜索反复、术语对不上、找不到（J1 首步） ·
能力：`search.intent.parse`、`data.search`、`catalog.browse`、`catalog.entry.query` · 形态：发现+可行性评分+TOP-N 推荐（只读）。

**② 申请起草副驾 `application-draft-copilot`**
服务：用数方 · 痛点：申请表难填（应用场景/使用计划/保密承诺）、分不清有条件 vs 无条件路径 ·
能力：`catalog.entry.query`、相似历史申请检索、`application.resource.submit`（**仅生成草稿，人提交**） · 形态：表单预填+路径解释。

**③ 申请进度跟踪副驾 `application-tracker`**
服务：用数方 · 痛点：「我的申请到哪了」反复查、待办不准 ·
能力：`delivery.list/view`、`approval.case` 查询、`credential.query` · 形态：进度问答+下一步提示（只读）。

**⑥ 目录编制向导 `catalog-compile-wizard`**
服务：供数方操作员 · 痛点：编目多步骤、1200+ 字段遗漏、规范难记 ·
能力：`catalog.entry.create`（草稿）、`catalog.model.query`、`recommendation.similar_catalog.suggest` · 形态：字段值推荐+规范前置校验。

**⑦ 元数据补齐副驾 `metadata-enrich-copilot`**
服务：供数方 · 痛点：应用场景/所属领域/更新周期/字段级元数据空缺（客户三轮重提 P0） ·
能力：`catalog.entry.query`、资源元数据查询、字段映射 · 形态：从来源系统/业务对象推导补齐建议。

**⑭ 审核研判副驾 `review-decision-copilot`**
服务：部门管理员/业务运营员 · 痛点：审核负担、有条件共享两级把关易被旁路（断点 C） ·
能力：`application.resource.review`/`approval.review_decide`（**仅给研判建议，人决策**）、申请人历史+相似裁决检索 · 形态：摘要+通过/补正/驳回建议。**严守 §8.5：不自动裁决。**

**⑲ 平台使用指南 `zw-platform-guide`（已有）**
服务：全角色 · 痛点：平台使用/部署/权限/AgentRuntime 怎么用 · 能力：`platform.docs.search/read` · 形态：文档问答（只读）。

### Wave 2 · 链路完整化（把黄金链路补成端到端）

**④ 交付与对账副驾 `delivery-recon-copilot`**
服务：用数方 · 痛点：不知道去哪领数据、术语混乱（「交换任务」）、对账靠手工 ·
能力：`delivery.view`、库表对账查询（提供数 vs 接收数） · 形态：交付解释+完整性预检+异常标记（只读）。

**⑧ 资源挂接与发布副驾 `resource-publish-copilot`**
服务：供数方操作员/管理员 · 痛点：审了资源发不出去、发布队列卡壳、无 UI 入口（断点 A/B） ·
能力：`resource.mount.table.prepare`、`resource.asset.publish`、`resource.api.register` · 形态：挂接发布引导+「待发布」精准呈现。

**⑩ 供需匹配撮合 `supply-demand-matchmaker`**
服务：业务运营员 · 痛点：供需对接纯手工梳理（供需盲人摸象） ·
能力：`data_business` 查询、`data.search`、推荐 · 形态：需求→现有资源匹配+供数方认领推荐（只读）。

**⑫ 异议分诊副驾 `objection-triage-copilot`**
服务：业务运营员/部门 · 痛点：异议多角色流转慢、受理待办缺投影 ·
能力：`objection.case.create/query/review`（**分诊+起草，人处置**） · 形态：四维分类(catalog/resource/authz/content/use)+路由+处置建议。

**⑬ 数据质量哨兵 `data-quality-sentinel`**
服务：供数方/运营员/审计员 · 痛点：质量问题事后才发现 ·
能力：异议历史查询、对账异常、`audit.event.anomaly` · 形态：高风险资源前置预警（只读）。

### Wave 3 · 运维与治理（B1 后台支撑）

**⑮ 工单分诊副驾 `ticket-triage-copilot`**
服务：平台运维员 · 痛点：工单人工分类分派、常见问题反复答 ·
能力：工单/`pub_app_issue` 查询、FAQ 检索 · 形态：自动分类路由+自助答疑（建议，不自动结案）。

**⑯ 告警聚合与根因副驾 `alert-rca-copilot`**
服务：平台运维员 · 痛点：告警噪声大、根因定位慢 ·
能力：监控查询（automonitor/dsp_perform）、`audit.event.query` · 形态：告警关联聚合+根因推导+响应建议（只读）。

**⑰ 权限申请与合规自查副驾 `access-compliance-copilot`**
服务：运维员/部门管理员 · 痛点：21 条权限诉求、越权/缺失、权限矩阵散落 4 处一致性脆弱 ·
能力：`governance.actor.list`、`governance.access_matrix`（**只读自查+建议，不裁决**） · 形态：权限模板预填+合规前置检查+漂移提示。**严守 §8.5：不改 ROLE_*。**

**⑱ 运营报表与洞察副驾 `ops-insight-copilot`**
服务：运营员/业务决策者 · 痛点：月度/季度报表纯复制粘贴 ·
能力：`audit.event.query`、目录/资源/使用统计查询 · 形态：定时抽数→格式化→推送干系人（只读生成）。

**⑳ 审批流/表单自然语言起草 `nl-flow-form-builder`**（Wave 2 三引擎）
服务：运维员/运营员 · 痛点：审批流与表单配置复杂 ·
能力：`approval_flow.nl_draft`、`form_schema.nl_draft` · 形态：自然语言→流程/表单 schema 草稿（人审核启用）。

### Wave 4 · 拓展候选（验证 Wave 1–3 后再决定）

**⑤ API 集成开发者副驾 `api-integration-copilot`**
服务：用数方开发者 · 痛点：接口集成学习曲线陡（取密钥/调试/排错） ·
能力：服务目录查询、`credential.issue/query`、样例/mock 生成 · 形态：API 文档检索+mock+错误诊断。

**⑨ 字段血缘与质量自查 `schema-lineage-copilot`**
服务：供数方/治理 · 痛点：库表字段 vs 目录定义不一致、SchemaSnapshot 恒空 ·
能力：metaresource 查询、`archive_data_link` 血缘、目录查询 · 形态：一致性自查+血缘构建+发布前修复建议。

**⑪ 需求起草与成效副驾 `demand-impact-copilot`**
服务：业务方/运营员 · 痛点：业务需求难起草、成效（减跑腿/减材料）难量化 ·
能力：`data_item` 查询、`data_business.performance` · 形态：需求草稿+事项/材料建议+成效测算。

**㉑（可选）安全审计回放副驾 `audit-replay-copilot`**
服务：安全审计员 · 痛点：审计链路回放、异常排查靠手工 ·
能力：`audit.event.query/replay/anomaly`（**纯只读，审计员零写**） · 形态：链路回放+异常归因问答。

## 6. 收敛逻辑：为什么是这 20，砍了什么

**收进来的逻辑**：上表每个都过 C1–C5 —— 有实证痛点、能映射现有能力、落副驾安全区、压在 J1/J2/B1 高频链路、角色单一清晰。
Wave 1 五个直接覆盖"找数→申请→审核 / 编目→补元数据"这两条最高频、痛点最实的子链路，是"先做精一条链"的聚焦点。

**主动砍掉/降级的方向（发散里有、收敛里没有）**：
- **共享专区 / 绩效看板 / 多渠道消息**等：使用日志实证低频、业务方 0609 已判退本期 → 不立智能体（违 C4）。
- **自动审批 / 自动授权 / 自动改权限 / 自动写审计**：落 §8.5 禁区 → 一律降为"研判/建议"形态（违 C3 的不收）。
- **"全能政务大脑助手"**：违 C5（角色/任务不单一），且与聚焦原则冲突 → 不做。
- **数据安全中心相关（分类分级/脱敏自动处置）**：旧平台本期未立项、模块全缺 → 暂不立智能体（违 C1/C2）。

**需要新增能力才能落地的（标注、不阻塞 Wave 1）**：⑮ 工单、⑯ 告警根因若现有 Registry 无对应查询能力，则先立"新增能力"子项再接智能体。

## 7. 下一步（协同收敛的钩子）

这是底稿，请就以下维度自上而下拍板，我据此改稿并开始把选定项落成 `AGENT.yaml` + `capabilities.json`：

1. **总量**：~20 是否合适？要更聚焦（如先锁 Wave 1 的 5–7 个）还是更全？
2. **切法**：Wave 分层 / 角色分组，哪种作为主线索？
3. **逐项**：哪些 merge（如 ②③④ 合成"用数方全程副驾"）、哪些 drop、哪些补（你心里已有但表上没有的场景）？
4. **判据权重**：C1–C5 里，这一期最看重哪条（决定砍取松紧）？
5. **落地顺序**：Wave 1 先落哪 1–2 个做成可演示样板（建议 ① 数据发现 + ⑥ 目录编制向导，正好一条用数、一条供数）？

> 附：本稿所有 `skill_id` 为示意，落地前会用 `docs/agent_integration.md` 的能力清单逐一校验绑定；
> 映射不上的能力一律标"需新增"另立项，不在智能体里偷偷造后端（守 C2 / 确定性自动化原则）。
