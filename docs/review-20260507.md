## 关键发现

### [R-001] zw_brain/command/brain.py:1418 catalog_entry → discovery card 在两处近乎逐字重复
- 严重程度：high（design-quality）
- 问题描述：`get_resource`（line 1418-1436）与 `search_resources`（line 1937-1956）两处用 13 个字段的字面量字典重复构造同一份「真目录卡片」结构，仅差一个 `kind` 字段。任何新增字段或默认值调整都需要同时改两处，标准的 OPC「同一规则多份维护」反模式。
- 建议修复：抽取私有 helper `_catalog_record_to_card_dict(record, *, include_kind=True)`；二者复用。

### [R-002] zw_brain/command/brain.py:1405 get_resource 在双 miss 时悄悄返回 `{}`
- 严重程度：medium（code-quality / contract）
- 问题描述：snapshot 与 DB 双双 miss 时 try/except 后 `resource = {}`，最终 return `{}` 而非抛 NotFoundError。前端 `app.js:139` 把空对象 unshift 进 RUNTIME_DISCOVERY.resources，`resourceById` 的 `|| resources[0]` 让用户在错误的 resource_id 上看到首张 curated card；即便不 fallback，详情页 `${item.name}` 等仍渲染 undefined。0634f11 commit 想修「fallback 到第一张卡」但只补了前端字段 fallback，没有从契约层恢复 404。
- 建议修复：双 miss 时 `raise NotFoundError(resource_id)`；或把 snapshot 与 repo 改成串联 lookup，全 miss 即抛 404。

### [R-003] tests/test_brain_service.py:1641 test docstring 与 PR description 均声明 limit clamp 已覆盖，实际并未断言
- 严重程度：medium（validation）
- 问题描述：docstring 与 PR body 都声明覆盖 `limit clamp（999→100）`，但测试体只断言 `limit=1` 的合法情形，缺少 `limit=999 → 实际返回 limit=100` 的断言。给作者「已验证 clamp」错觉，下次 clamp 上限被改不会被测试发现。
- 建议修复：补一行 `clamped = service.invoke_skill('catalog.browse', {'role':'r1','limit':999}); assert clamped['limit'] == 100`。

### [R-004] zw-brain-web/js/pages.js:558 catalogBrowse 未走 escapeHtml
- 严重程度：medium（security）
- 问题描述：`PAGES.catalogBrowse` 在 `${item.title}` / `${item.catalog_code}` / `${item.owner_org_id}` / `${item.lifecycle_status}` 等处直接把 catalog_entry 字段拼进 innerHTML，未走仓内已有的 `escapeHtml`（pages.js:16）。catalog 数据来源是 importer 灌入的 legacy 库，客户级 WebUI 一旦遇到含 HTML 特殊字符的 title / owner_org 就会渲染异常，最差成为 XSS 入口。
- 建议修复：catalogBrowse 内渲染外部字段时统一 `escapeHtml(x)` 包裹；href 已 `encodeURIComponent(catalog_code)` 不动。
