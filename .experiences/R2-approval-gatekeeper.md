# R2 区县/部门审批承接人员：把住重复要数阀门

## 这一页解决什么事

你不是把 R1 的需求原样转发给基层，而是判断它该复用、补录、驳回还是调整授权边界。旧平台里的申请、部门审批、授权、续期能力都要承接进 zw-brain，但审批心智从“看表单”变成“看证据链”。

## 你手上拿到的真实输入

- R1 提交的 `application_record`：用途、时间窗、申请目录、申请字段、责任部门。
- 应用与代理证据：应用查询/应用注册信息、我的应用、资源申购车、代理授权申请、脚本管理摘要。
- 候选目录：`医保码信息`、`异地就医统筹区开通信息`。
- 提供方与责任边界：`省医保局`、`省大数据局`、相关区县承接部门。
- 状态：`待受理`、`审核中`、`已驳回`、`已核查`。
- 审批人视角：旧 `catalog-front` 的 `/approve`、`/business-examine`、`/manager-examine` 在 zw-brain 收敛为同一份 `approval_case` 的两类视角——业务审批人看准入与口径，管理员审批人看授权边界与责任分配，不是两个产品入口。
- 授权清单：旧 `catalog-front /authorize` 与 `/inventory` 在新平台分别对应"新授权动作"与"已授权清单 projection"，由 R2 主审，R7 监督。
- 证据：字段口径、资源状态、授权策略、历史申请、quality projection、M0 验收后的来源引用。
- 分级授权策略决策边界：R2 决定"允许哪一档授权 / 字段脱敏粒度 / 频次上限 / 有效期"；R7 只把 R2 决策落到可见组织、专题分组与策略解释。两端不重叠。
- API 服务化授权边界证据：R6 提交的 API 草稿（路径、入参、出参、字段脱敏档位、订阅应用清单）、`api_access_ip`、`api_service_fuse` 配置。
- 旧状态映射：旧 `审核中(2)/发布(3)/撤销` ↔ 新 `pending_review/active/revoked`；扩展态以 catalog3-metadata3 重构方案 §八 为准，审批意见落 `approval_case` + `approval_step` + `approval_decision`。

## 一条主旅程

1. 打开 `待受理` 申请，先看申请目的、范围、牵头部门、关联部门、应用用途和目录分级授权边界是否清楚。
2. 如果申请来自资源申购车，先合并重复资源、删除非必要字段，避免把“购物车”变成批量要数通道。
3. 系统提示 `省医保局` 已发布 `医保码信息` 时，先判断是否能复用，而不是批准新增采集。
4. 对 `异地就医统筹区开通信息` 检查目录项、字段敏感级别、可授权范围、交付频次、续期条件和级联授权限制。
5. 对应用注册、应用审核或代理授权申请，检查应用用途、责任人、代理调用范围、有效期、频次、审计要求和脱敏/汇总粒度；脱敏策略以 R6 维护的字段脱敏证据为准，本步骤只裁决是否允许、按哪一档放行。
6. 查看申请和资源的证据链：申请是否能关联 `application_record`，资源是否能关联 `resource_asset` 与 `resource_schema_mapping`。
7. 检查目录或资源是否存在撤回、下架、active 版本切换、schema 变更或来源验收证据缺失等风险。
8. 做准入判断：直接复用、局部补录、退回缩小范围、驳回重复需求、缩小授权、改为脱敏/汇总交付，或转 R6/R7 做口径确认。
9. 对脚本管理或接口调用类需求，只审批能力边界、执行责任和审计要求；脚本执行逻辑不进入主产品心智。
10. 写入审批意见，形成 `approval_case`、`approval_decision` 和审计回执；撤回、退回、驳回和通过一样必须可回放。
11. 通过后生成授权、代理授权、续期提醒或补录边界，交给 R3/R4/R5 或进入 `delivery_task`。
12. 对分级授权策略变更（旧 `/authorize` 中"决策档位"半边），只决定"允许哪一档授权、脱敏粒度、频次上限、有效期、是否级联"；不替 R7 实施"哪些组织看得到"。
13. 对 API 服务化授权边界（R6 提交的 API 草稿），只审 IP 白名单覆盖范围是否合理、限流阈值与场景匹配、字段脱敏档位是否符合分级、订阅应用是否符合用途；通过后 R7 才能允许 R6 上线。
14. 对资源撤回引发的"在途授权与订阅清单"做处置：保留历史授权快照、决定是否替代资源、决定是否中止订阅；不允许"目录撤了授权悄悄失效"。
15. 对数据直达申请，只审是否符合已审批主链路；任何想跳过 `application_record` 直接对 dc_catalog 取数的请求一律驳回。

## 关键判断点

| 你看到什么 | 该怎么判断 | 系统证据 |
| --- | --- | --- |
| 同主题目录已发布 | 优先复用，避免重复采集 | `catalog_entry`、专题 projection |
| 资源 active 但授权策略受限 | 通过但缩小字段、频次或脱敏粒度 | `resource_asset.access_policy_json`、`delivery_task` |
| 字段缺口真实存在 | 批准局部补录 | `catalog_item` 与 `resource_schema_mapping` 差异 |
| 申请与历史在途申请重复 | 合并或驳回 | 历史 `application_record`、审计时间线 |
| 质量证据异常 | 不直接放行，转提供方修复 | quality projection、schema snapshot |
| 牵头部门或关联部门意见冲突 | 保留争议并进入治理裁决 | `approval_step`、部门责任快照 |
| 目录分级授权超出边界 | 缩小范围或改为脱敏/汇总交付 | `tenant_capability_policy`、授权策略快照 |
| 目录或资源处于撤回或 active 版本切换中 | 暂缓审批，等待 active 版本稳定 | `catalog_entry_version`、schema version |
| 应用用途说不清 | 退回补充责任边界，不批准代理调用 | 应用用途快照、代理授权边界 |
| 脚本或接口调用越界 | 只批准受控能力边界，拒绝自由执行 | capability policy、audit requirement |
| 我的资源已有有效授权 | 要求复用或续期，不重复审批 | `delivery_subscription`、access grant snapshot |
| 业务审批人与管理员审批人视角不一致 | 用 `approval_step` 留两类意见，最终结论合并到同一 `approval_case` | `approval_step`、责任快照 |
| 授权清单（旧 `inventory`）过载 | 用 `delivery_task` projection 抽查超期、未生效或已废弃授权 | 已授权清单 projection |
| API 草稿 IP 白名单写成 `0.0.0.0/0` | 直接驳回；要求按订阅应用清单收敛 | API 草稿、`api_access_ip` |
| API 字段脱敏档位低于目录分级 | 驳回；要求按分级最高档为准 | API 草稿、字段策略快照 |
| 分级授权变更影响已生效订阅 | 同步决定订阅续期或终止；不允许策略静默生效而订阅照常 | 授权策略快照、`delivery_subscription` |
| 资源撤回但仍有 active 授权 | 决定替代资源或中止订阅；不能让授权指空 | 撤回影响范围、`delivery_task` |
| 数据直达申请绕过申请审批 | 驳回；转回 `application_record` 主链路 | direct-access projection、approval case |

## 异常分支

- **申请范围过大**：要求按区域、字段、时间窗拆分，避免“一次申请全库”。
- **缺口字段没有用途说明**：退回补充最小必要性。
- **目录发布但资源不可交付**：转 R6 处理资源状态、schema 或字段绑定，不把问题下压给基层。
- **授权未生效**：抽查 `delivery_task.access_grant_snapshot`，确认是审批未完成、授权回写失败还是策略不允许。
- **多部门责任不清**：保留争议证据，进入治理裁决，不在线下口头协调后绕过平台。
- **分级授权或续期争议**：只调整授权边界、频次、有效期或脱敏粒度，不在共享专区单独放权。
- **来源验收证据缺失**：不把证据缺口对象当作可交付目录；退回 M0 验收缺口或 R7 目录运营问题，不在审批页补造来源。
- **代理授权申请像“代人无限取数”**：缩小为具体应用、接口、时间窗、频次和审计责任。
- **脚本管理请求绕过审批**：拒绝自由执行，转为受控外部执行器或能力包审计。
- **分级授权策略与可见组织被同步外发**：本端只决策档位；可见性落地由 R7 实施；不在 R2 直接改专题分组。
- **API 草稿与目录主授权策略不一致**：以目录主策略为准；API 草稿必须等目录策略修订后重新提交。
- **撤回引发授权悬空**：要求提交方在撤回审批前给出"替代资源或订阅终止方案"，否则驳回。

## 成功判据

- 每个通过的申请都有明确字段、范围、授权边界和完成时限。
- 每个驳回或退回都能回放理由、证据和责任人。
- 重复采集被压降，审批成为治理阀门而不是传话筒。
- 授权、续期、频次变更都能在同一条链路里追踪。

## 旧平台能力在这里怎么落地

| 旧平台能力 | zw-brain 表达 | 用户感知 |
| --- | --- | --- |
| 申请表 `data_apply` / `data_apply_item` | `application_record` | 看需求、字段、用途、范围 |
| 审批过程 `data_apply_course` / `data_apply_dept_approve` | `approval_case` / `approval_step` | 做准入判断并留痕 |
| 授权与续期 `data_apply_authrization` / `data_apply_renewal` | `delivery_task` / `delivery_subscription` | 通过后授权可回放 |
| 目录审核 / 牵头部门审核 / 关联审核 / 业务审批 / 管理员审批 | 同一份 `approval_case` 的多类审批人视角；最终合并为一条决策 | `approval_step` 留两类意见 |
| 授权 `/authorize` 与已授权清单 `/inventory` | 写动作进 `delivery_task`；已授权清单作为可重算 projection | 区分"新授权"与"清点已授权" |
| 目录分级授权 / 级联授权 | `tenant_capability_policy` + access grant snapshot | 授权边界清楚，不靠线下放权 |
| 资源审核待办 `audit_todo_task` | 统一审批待办 | 不再有 metadata 流程岛 |
| 资源申购车审批 | `approval_case` + requested items snapshot | 把候选清单收敛为最小必要授权 |
| 应用注册 / 应用审核 | 应用用途快照 + `approval_case` | 应用用途成为审批证据，不成为第二套中心 |
| 代理授权申请 | 代理授权边界 + `delivery_task` | 代理调用有边界、有效期、频次和审计 |
| 脚本管理 | external executor / capability audit | 只审批边界，不把脚本执行塞进主旅程 |
| 质量与统计接口 | source-tagged projection | 用证据判断，不用口头确认 |
| 分级授权策略决策（旧 `/authorize` 决策半边） | R2 决定档位/脱敏/频次/有效期/级联；R7 只实施可见组织 | 两端不重叠，策略与可见性可解释 |
| API 服务化授权边界审 | R6 提交 API 草稿 → R2 审 IP/限流/字段脱敏档位/订阅应用 → R7 上线复核 | API 边界由审批锁，不靠 R6 自觉 |
| 撤回引发授权悬空 | R6 提撤回 → R2 决处置替代或终止订阅 → R7 实施 → R8 抽查 | 撤回不静默断订阅 |
| 数据直达申请 | 一律走 `application_record` 主链路；dc_catalog 只读 | 数据直达 ≠ 数据库直连 |
