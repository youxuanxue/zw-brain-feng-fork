## 8800 main web vs 8801 dashboard 谁面谁

| 端口 | 服务 | 受众 | 写权 | 登录方式 |
| --- | --- | --- | --- | --- |
| 8800 | `zw_brain.entry.rest` (main web) | R1-R8 业务用户 + 实施工程师 (`?role=admin`) | 完整业务写权（受 IAM + skill `human_confirmation_required` 控制） | IAF/OIDC 或 dev-bypass |
| 8801 | `zw_brain.entry.dashboard_bff` (大屏) | 指挥中心 / 高层 / 投影会议室 | **只读**（消费 `dashboard.*` skill；写动作 preflight 段 11 阻塞） | 同 IAM；通常配独立 read-only 账号 |

## zw-brain 解决什么问题

**旧平台的痛点**：找数据靠问人，要数据靠填表，追数据靠电话，证明合规靠截图。16 个独立子系统、190 个页面分散在不同入口，同一件事要跳 3-4 个系统才能做完。

**zw-brain 的答案**：把 16 个系统压缩成 8 个角色的清晰旅程。每个人只做自己该做的最小动作，系统替你串联证据、追踪状态、证明合规。

## 从旧平台切换到新平台（M0 迁移）

这是一次性的事。做完之后旧平台退场，所有人在新平台工作。

**迁移只回答一个问题：旧平台的数据，到新平台里丢没丢？**

| 步骤 | 做什么 | 完成标志 |
|---|---|---|
| 1. 导出 | 从旧平台一键导出全量数据（目录、资源、字段、申请、审批、授权、异议、交换任务） | 导出包生成 |
| 2. 导入 | 批量导入到 zw-brain，每条旧数据自动生成回指记录 | 导入完成，无失败批次 |
| 3. 核验 | 抽样检查：高频目录能搜到、字段能看到、审批历史能追到、授权仍有效 | 核验报告无缺口 |
| 4. 验收 | R6/R7/R8 分别确认资源、目录、合规证据完整 | 验收签字 |

**异常处理**：导入失败 → 冻结该批次 → 可重跑或回滚 → 不会丢数据、不会半手工绕过。

## 各角色的核心旅程

### R1 需求发起人：找到数据、提出申请、跟踪交付

**旧平台你要跳 4 个系统（门户搜目录 → 应用中心加购物车 → 资源申请提交 → 供需对接登需求），现在一条线走完。**

```
搜索目录 → 看字段和交付方式 → 加入申请车 → 提交申请 → 跟踪进度
                                                          ↓
找不到？→ 登记需求 → R7 判断能否复用 → 能复用回来申请
                                       → 不能复用 → 派任务给基层
```

**日常动作**：
- 搜索想要的数据（如"医疗救助"、"医保码"、"停车场"）
- 看目录详情：谁提供、什么字段、能不能申请、交付方式（库表/文件/API）
- 把需要的加入申请车，写清用途、时间窗、字段范围，提交
- 在"我的申请"跟踪状态：待受理 → 审核中 → 通过/驳回补正/驳回
- 通过后在"我的资源"领取数据或 API 凭据
- 授权快到期时做续期，不用重新申请
- 对结果不满意时提异议（数据/资源/授权/使用四类），不靠线下沟通
- 完成后评价服务质量

**关键原则**：不鼓励一上来就"新建采集"。系统会优先告诉你哪些数据已经有了。

---

### R2 审批人：判断该复用、补录还是驳回

**旧平台你在目录审核、资源申请审核、融合服务审核之间来回切。现在统一成一个审批工作台。**

```
收到申请 → 看证据链 → 做判断 → 写意见
                         ↓
              复用：直接授权，无需基层补差
              缩小：减字段/改脱敏/限频次
              补录：通过但需 R3/R4 补差
              驳回补正：退回让 R1 改了再来
              驳回：写明理由，终止
```

**日常动作**：
- 看申请目的、范围、字段是否清楚
- 查系统提示：同主题目录是否已发布（防重复采集）
- 对 API 类申请审 IP 白名单、限流、字段脱敏档位
- 对授权续期/暂停/收回做处置
- 写意见，自动进入授权或补录链路
- 延迟未审的会收到预警提醒

**关键原则**：你是治理阀门。同样的数据已经有了，就不批第二次采集。

---

### R3 镇街填报：只补差异字段

**旧平台你在供需对接的"待办任务"里收到整张表。现在系统帮你预填了，你只改变化的。**

```
收到补差任务 → 看预填值 → 只改标红字段 → 提交
                                          ↓
                               不确定 → 标"需确认" → R5 判断
```

**日常动作**：
- 打开任务，看哪些字段需要补（标红的）
- 核实现场是否变化，补齐差异
- 格式不对会有提示，按提示改
- 不确定的标异常，不硬填
- 退回的只改指定字段，不重填整张表

---

### R4 社区填报：看任务卡，快速完成

```
领任务卡 → 核实现场 → 提交 → 完成
                       ↓
              不匹配 → 标异常 → 上级处理
```

**关键原则**：你不需要懂任何后台概念。任务卡告诉你补什么、为什么补、怎么提交。网络不好可以存草稿，恢复后提交。

---

### R5 汇总审核：盯异常、处理异议、确认交付

**旧平台你在供需对接汇总、异议处理、治理大盘三个系统之间跳。现在合到一起。**

```
看完成率和异常 → 退回有问题的 → 确认自动汇总 → 进入交付
        ↓                                        ↓
  口径问题 → 转 R6/R7                    交付后收到异议？
  授权问题 → 转 R2                              ↓
                                   受理 → 评估 → 处置 → 确认闭环
```

**日常动作**：
- 看完成率、逾期、异常分布
- 退回有问题的给 R3/R4，写清是哪个字段、什么原因
- 口径或授权问题转给上游，不在汇总页临时改规则
- 异常收敛后确认汇总，结果进入交付或回流资源池
- 收到异议时按四类归因（数据/资源/授权/使用），走受理→评估→处置→确认闭环
- 从 R7 收到"不可复用"的需求时，按区域/字段切片成任务卡派给 R3/R4

---

### R6 数据提供方：让资源可交付、API 可调用

**旧平台你在资源管理注册资源、在融合服务创建 API、在数据交换配数据源。现在统一成"把资源交付出去"。**

```
整理资源（表/文件/文件夹/链接/API）→ 补齐字段证据 → 绑定到目录项 → 提交审核
                                                                      ↓
                                                               R7 审核通过 → 发布
API 类：创建 API 草稿 → 配 IP/限流/脱敏 → R2 审边界 → R7 审上线 → 发布 → 监控调用
```

**日常动作**：
- 注册资源：选类型（库表/文件/文件夹/链接/API），填基本信息
- 补齐字段：中文注释、格式、敏感级别、脱敏规则
- 绑定到目录项（让 R1 搜到目录后能真正拿到数据）
- 元数据采集：系统自动采集表结构和字段，你核对结果
- API 服务化：创建服务 → 配参数/流控/黑白名单 → 提交审核 → 上线后看调用量和错误
- 资源变更（下架/修字段/换版本）走审批，不偷偷改
- 自动质量检测规则维护：配必填率、格式、值域规则

**关键原则**：目录能看到但资源交不了 = 没用。你的目标是让别人（R1）能真正拿到数据。

---

### R7 目录管理员：让发布的目录真正被找到、需求真正被对接

**旧平台你在目录管理做维护/审核/授权/挂接/派发，在供需对接做平台方对接，在数据直达做上报。现在统一成"让目录可用"。**

```
目录审核通过 → 组织专题入口 → 确认搜索可达 → 监控发现率
                                                 ↓
收到 R1 需求 → 判断能否复用现有目录 → 能复用：对接完成
                                     → 不能复用：派任务给 R5
国家直达通道：目录/资源上报 → 需求受理 → 申请审核 → 订阅管理
```

**日常动作**：
- 处理目录工作队列：派发/认领/审核/发布/撤回
- 新发布的目录放进合适的专题（民生保障、医保协同等）
- 确认说明、字段、申请条件写清楚
- 同主题目录太多就合并入口
- 审核 R6 提交的资源挂接和 API 上线请求
- 判断 R1 的需求能否用现有目录满足（供需对接的平台方角色）
- 国家数据直达通道：处理目录/资源/需求/申请的上报和受理
- 跟踪发现率、申请成功率、授权生效率

---

### R8 合规督查：用证据回答三个问题

**旧平台你在治理大盘看数据、在数据安全查审计、在运行监控处理工单和告警、在异议处理做督办。现在合到一个督查视图。**

```
是否减负？ → 看重复申请趋势、基层填报量变化
是否绕行？ → 查线下导出、直达绕过审批、API 越权
哪里断链？ → 下钻到具体环节（发布/投影/授权/schema/交付）
```

**日常动作**：
- 选重点目录和部门，看减负指标
- 抽查一条完整链路：发现 → 申请 → 审批 → 授权 → 交付
- 发现断点就定位环节和责任人
- 安全证据审查：脱敏策略、加密状态、敏感识别、访问审计
- 异议督办：异议处理超期或被线下推进的，追责
- API 绕行检查：IP 白名单私改、限流被临时放开、错误回流敏感字段
- 运维工单：告警处理、巡检结果、交接班
- 输出整改建议

## 角色之间怎么串联

```
                    ┌─ R6 准备资源（注册/字段/API）
                    │        ↓
                    │  R7 发布目录（审核/专题/上报）
                    │        ↓
                    │  R1 发现 → 申请（或登记需求）
                    │        ↓
                    │  R2 审批（复用/补录/驳回/授权）
                    │        ↓
                    │  R5 派发任务 ←── R7 供需对接判断
                    │        ↓
                    │  R3/R4 现场补录
                    │        ↓
                    │  R5 汇总确认 → 交付给 R1
                    │        ↓
                    │  R1 使用数据（异议？→ R5 处理）
                    │        ↓
                    └─ R8 全程督查证据链
```

**一条数据的完整生命周期**：
R6 注册资源 → R7 发布目录 → R1 发现并申请 → R2 审批授权 → R3/R4 补差 → R5 汇总交付 → R1 使用 → R1 评价/异议 → R8 确认合规。
