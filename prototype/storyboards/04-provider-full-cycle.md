# 场景 4：提供方全周期（K1 → K2 → K3 → K4 → K5 → K8）

**角色**：陈科长，市卫健委信息中心，负责本厅数据资源的对外提供与运维。

**目标**：把一份新的「医疗机构基础信息」表注册成可对外共享的目录、发布为融合服务，处理一笔申请方提交的审批，跟进交换任务状态，并响应一条数据质量异议。

**对应架构主张**：
- §7.3 第 3 / 4 / 5 / 6 页（资源 / 目录 / 服务 → 申请审批 → 数据交换 → 异议处理）端到端跑通
- K1 catalog + K2 resource + K3 service 三层在同一页（`/manage`）用 tab 切换 — 验证 §7.1 不做 20+ 子系统
- 写操作（注册 / 发布 / 下线 / 重跑 / 异议处理）一律按角色 ACL + 二次确认 + audit_event 同步落库（D4 上半）
- K4 → K5 自动衔接：审批通过自动产生交换任务，二者共享同一 request_id 形成审计链

---

## 旅程

**第 1 步：在 `/manage` 注册新数据资源**

陈科长（角色切到「**提供方管理员**」）点工作台快捷入口「资源 / 目录 / 服务」。进入 `/manage`，默认 catalog tab。三 tab 编号清晰：📋 数据目录 / 🗄️ 数据资源 / 🔌 融合服务。他切到「数据资源」tab，看到本厅已注册的 5 个资源，其中 1 个 `flu-realtime-api` 状态是「⚠ 降级」。他点「重新探活」，toast 提示「已重新探活（mock）」。

接着点右上「+ 新增」，原型 toast 说明：「打开『+ 新增 数据资源』表单（原型仅展示，提交后将写入 audit_event 并更新目录）」。陈科长理解：实施层会有完整 wizard（CSV/JDBC 拖拽识别字段 → 自动生成 schema → 一键注册）。

**第 2 步：发布融合服务**

切到「融合服务」tab。看到 4 个服务，其中 `flu-weekly` 状态是「暂停」、QPS 为 0；其他 3 个都「✓ 在线」。他对暂停的服务点「下线」按钮 — **弹出二次确认弹窗**，说明此操作会写 audit_event。点确认后 toast 显示新 audit_id。验证 §3.1 K10 + D4 上半。

**第 3 步：审批一笔申请**

陈科长回工作台，看到「我的待办」中有 2 条待审批申请。点 `REQ-2026-04-15-0042`（紧急标记），跳到 `/review/:id`。

页面顶部显示申请详情；中部「**大脑辅助决策**」蓝卡：
- 同部门（市发改委综合处）历史 3 次 → 通过 3 / 驳回 0
- 申请理由含公文号 `OA-2026-Q1-208`，关联系统已校验有效
- **建议：通过（置信度 0.91）**

但 — 卡片底部明确写「**不替你点按钮，需要你检视后人工决定（§7.5 写操作不让 NL/Agent 自决）**」。陈科长在右侧「审批决定」面板写完审批意见，点绿色「通过」。toast 显示「已通过（mock）· audit_id: AE-... 已写入」。

**第 4 步：跟进交换任务**

跳回工作台，左 sidebar 切「数据交换」。在 `/exchange` 列表里，他看到自己刚通过的申请已自动产生新交换任务（与 EX-2026-Q2-014 同款）；同时注意到 `EX-2026-Q2-018` 状态是「✗ 失败」。

点进 `EX-2026-Q2-018` 详情页：
- 运行历史最后一行的错误是「**audit_event 写入失败 → 终止（D4 上半熔断）**」
- 这正是架构基线承诺的「写操作必须先成功落审计才返回成功」的实际表现 — 业务侧不会得到「假成功」

他点「立即重跑」，二次确认后 toast 提示新 audit_id。

**第 5 步：处理一条异议**

左 sidebar 「异议处理」红色 badge 显示「2」。点 `/dispute`，看到 3 条异议：1 条 open（中严重度，缺数据）、1 条 resolved（已修正）、1 条 escalated（升级到平台合规组，怀疑申请方违规营销）。

他点开 open 那条 `DSP-2026-04-15-007`：详情页显示完整背景 + 处理建议 + 时间线。他在右侧填写处理说明（≥4 字校验），点「已修正 / 接受」。toast 显示新 audit_id。状态变更同步写入 audit_event 链。

---

## 验证什么

- ☐ K1+K2+K3 在 `/manage` 同一页用 tab 切换，是否清楚不混乱
- ☐ 「+ 新增 / 下线」按钮按角色 ACL 自动启用 / 禁用，提供方操作员能看到什么、做不了什么是否符合预期
- ☐ 审批页「大脑辅助决策」是否到位（**建议但不替你点**这个边界是否被用户理解）
- ☐ K4 → K5 自动产生交换任务的衔接是否清楚（用户能否跟着 request_id 串起来）
- ☐ 「audit_event 写入失败 → 终止」作为可见错误，是否能让用户感知「合规优先于业务」的取舍
- ☐ 异议处理「已升级到平台合规组」的状态机是否对提供方足够透明
