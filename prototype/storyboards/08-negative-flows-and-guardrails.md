# 场景 8：负面流与边界守卫（真实角色链路版）

**角色**：R1、R2、R3 / R4、R5、R7、R8，以及外部能力建设方。

**目标**：验证主旅程不是只在理想路径上成立，而是在失败、补正、熔断、鉴权和注册退回等场景下，仍保持统一 Capability 契约、人工确认边界和合规优先原则。

> 前提：所有 `submit`、`review-and-decide`、`reconcile-receipt`、`register-version`、`apply-tenant-policy` 一类责任写动作都由平台内建能力落账；外部包最多提供草拟、解释、摘要、预检查与适配，而且这些辅助能力即使全部失效，也不能阻断核心业务流程。

## 负面流 0：外部辅助全部失效，主流程必须降级但不断裂

- **触发条件**：意图解析、申请草拟、状态解释、证据摘要、manifest 预检查等外部辅助能力同时离线或超时。
- **用户可见现象**：页面失去推荐文案、草拟内容或解释卡片，但目录浏览、模板详情、结构化表单、显式按钮、时间线、回执、审核字段仍然可用。
- **平台处理方式**：退化到平台 baseline 交互；R1 仍能发现模板并提交复用申请，R3 / R4 仍能补录差异字段，R5 仍能确认自动汇总，R7 仍能审核 package，R8 仍能查看原始证据。
- **审计要求**：记录外部辅助失效事件，但不得把失败伪装成“业务不可办理”。

## 负面流 1：R1 意图信息不足，AI 只能追问，不能代填提交

- **触发条件**：R1 在 `#/p2-discovery` 只输入“我要企业数据”，缺少专题、对象边界和用途说明。
- **用户可见现象**：系统提示仍需补充场景、范围和用途，而不是直接生成可提交申请。
- **平台处理方式**：继续停留在发现与意图收敛阶段，等待用户补齐上下文。
- **审计要求**：记录一次解析尝试，但不生成申请提交类审计事件。

## 负面流 2：R2 / R5 退回补正，AI 只能草拟补件建议

- **触发条件**：审批承接人员发现字段边界不清，或审核汇总人员发现异常项缺少说明。
- **用户可见现象**：在 `#/p3-request-flow/review/:id` 中，R2 / R5 可以选择“退回补正”；R1 或 R3 / R4 在状态时间线上看到退回原因与待补项。
- **平台处理方式**：AI 可以草拟补正建议，但最终退回动作与意见写入必须来自人工确认。
- **审计要求**：保留建议摘要、最终决定、时间戳和责任人。

## 负面流 3：R3 / R4 补录任务出现外部通道波动，不得假装成功

- **触发条件**：预填任务下发、回执同步或外部交换通道响应抖动、延迟或缺失。
- **用户可见现象**：在 `#/p4-delivery-exchange/task/:id` 中，页面明确提示“外部通道波动”或“等待回执”，而不是笼统显示已完成。
- **平台处理方式**：保持任务可追踪、可重试、可人工接管，不掩盖外部依赖存在。
- **审计要求**：记录任务状态变化、外部响应摘要和后续重试动作。

## 负面流 4：关键审计写入失败，动作必须阻断而不是假成功

- **触发条件**：申请提交、汇总确认或回流确认时，关键审计事件写入失败。
- **用户可见现象**：页面明确提示本次动作未完成，并说明是审计写入失败触发阻断。
- **平台处理方式**：拒绝进入下一状态，要求稍后重试或人工介入。
- **审计要求**：至少保留故障事件与阻断记录，不能完全静默失败。

## 负面流 5：AI 只能解释熔断，不能把熔断伪装成智能决策

- **触发条件**：系统因风险、回执缺失或审计问题触发主动熔断。
- **用户可见现象**：任务页和时间线明确展示“主动熔断保护”以及原因摘要。
- **平台处理方式**：AI 负责把技术状态翻译成业务语言，但不能用模糊措辞掩盖失败事实。
- **审计要求**：记录熔断原因、责任边界与后续动作建议。

## 负面流 6：外部调用方无权限或租户范围不匹配

- **触发条件**：外部 Agent、CLI 或管理员以错误租户、错误身份调用能力。
- **用户可见现象**：调用被拒绝，并明确提示权限或租户范围不匹配。
- **平台处理方式**：拒绝执行，保留最小必要错误说明，不泄露敏感信息。
- **审计要求**：记录调用来源、租户、能力标识和拒绝原因。

## 负面流 7：能力包 schema 缺项，R7 必须退回补充

- **触发条件**：外部 ANP 构建的 package 缺少输入输出 schema、ACL、side effects、审计声明或示例。
- **用户可见现象**：R7 在 `#/p8-integration-admin/package/:id` 中看到结构化缺项清单与 AI 草拟退回意见。
- **平台处理方式**：package 只能停留在待审核或补件态，不得进入可注册态。
- **审计要求**：保留审核意见、缺项列表、责任人和版本号。

## 负面流 8：能力包暴露面或写权设计越界，不允许回注册

- **触发条件**：外部能力包试图直接声明 `submit`、`review-and-decide`、`reconcile-receipt`、`register-version`、`apply-tenant-policy` 等责任写动作，或为不同消费面分别定义不同业务语义。
- **用户可见现象**：R7 在审核时看到“暴露面与统一契约不一致”或“写权越界”的阻塞项。
- **平台处理方式**：注册被驳回，要求回到单一契约并收回越界写权后重新提交。
- **审计要求**：记录驳回原因、受影响消费面与审核结论。

## 这条旅程验证什么

- AI 是否在所有失败场景中都保持“辅助解释”而不是“替代判断”
- 主旅程是否把合规、审计、回执和租户边界当作默认能力，而不是事后补丁
- 外部辅助即使全部失效，R1–R8 主链是否仍可通过结构化页面闭环
- 平台在失败时是否诚实表达状态，而不是靠模糊语言掩盖问题
