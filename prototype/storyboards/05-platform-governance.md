# 场景 5：平台治理（合规回溯 + Skill 审批 + 运营面板）

**角色**：王平台管理员，市政府办公厅政务大脑平台组，负责日常合规督导、Skill 注册审批、平台运行健康。

**目标**：
1. 响应 `DSP-2026-04-10-002` 升级上来的「申请方疑似违规使用低保数据」异议 — 调审计回溯证据链
2. 审批一笔市公安局提交的 `population.query` Skill 注册申请
3. 检查今日平台运营 KPI，看是否需要调整资源池配额

**对应架构主张**：
- §7.3 第 7 / 8 / 9 页（合规督导 + Skill 市场 + 平台运营面板）端到端跑通
- 「§7.5 上周谁调用过 X 数据」即时可查（K8 / K9）
- D11 契约稳定性：Skill 一旦发布即「公开承诺」，破坏性变更需 v2 + 保留 v1 ≥ 6 个月
- 平台运营面板 vs K12 大屏受众分层（§7.7.3）：前者面向**平台管理员**关注「平台自身健康」，后者面向**领导**关注「全市数据流通价值」

## 旅程

**第 1 步：合规审计回溯（K8/K9）**

王管理员（角色已切到「**平台管理员**」）打开工作台，看到左 sidebar「治理」分组下有红色 badge 提示「Skill 市场 2」（待审批数量）。先处理升级上来的异议线索。

进入 `/compliance`：
- 顶部检索条件 — **时间窗、主体（人/Agent/系统）、数据集、操作类型** 4 个维度
- 他选「数据集 = 城乡低保救助金发放台账」「时间窗 = 7 天」「操作 = 仅写操作」，点「检索」
- 结果列表显示 28 条 audit_event（原型固定演示）：每条含时间、主体、Skill、数据集、request_id、chain_anchor
- 第 6 行有个 ⚠ 标记的「retry-ok」事件：这是首次上链失败 → 自动重试 → 成功的证据；业务侧不感知中断（D4 下半不阻塞业务）
- 他点右上「▷ 触发上链一致性校验」，toast 显示「已对当前结果集做上链一致性校验（mock 全部通过 ✓）」— 这是 K9 「事后核验」能力

王管理员把异议涉及的 request_id 链路截屏，作为后续调查的客观证据。

**第 2 步：审批一笔 Skill 注册申请（§7.3 第 8 页）**

左 sidebar 切到「Skill 市场」，进入 `/skill-market`。
- 上半部分：12 个**已发布 Skill**按 K1/K3/K4/K5/K7/K8/K11/K12 分组展示，验证 baseline §3.1 的 12 必保留功能确实有 Skill 落地
- 下半部分：**Skill 注册申请**列表 — 1 条 pending（市公安局 `population.query`）、1 条 pending（市税务局 `tax.summary.read`，已有审核意见）、1 条已驳回（市教育局 `edu.enroll.bulk_update`，理由是「不符合最小 API 表面 + N4 政策」）

他点开 `PROP-2026-04-17-002`（公安局）：
- 描述：「常住人口属性查询（年龄段 / 籍贯 / 学历，已脱敏）— 用于人口流动分析」
- 是只读 Skill（非写操作），但仍需平台合规审核：脱敏维度是否到位、PII 风险评估
- 他点「**批准并发布**」，toast 显示「Skill population.query 已批准 · 即将写 audit_event 并发布到 Agent 入口」，900ms 后自动跳到 `/agent/skills`，他在 catalog 域看到新 Skill 已就位

驳回案例的教训：`edu.enroll.bulk_update` 是写操作，且是 bulk 一把改 — 平台不接受这种**违反 §7.5（写操作必须人工逐条审）+ N6（不做裸的批量改）**的 Skill 设计。

**第 3 步：平台运营面板（§7.3 第 9 页）**

左 sidebar 切「平台运营面板」，进入 `/ops`。

页顶蓝色提示明确：「**区别于 K12 指挥中心大屏**：本面板给**平台管理员**看，关注『平台自身健康 + 资源配额』；K12 给**厅局领导**看，关注『全市数据流通价值』。两个面板共用底层 audit_event 流但视角不同 — 验证 §7.7.3 受众分层。」

他扫一眼 KPI：
- 已发布 Skill 12 / 在线服务 4 / 今日总调用 17,428 / 今日 audit_event 9,237
- 近 7 日调用量趋势：明显上升（接近峰值 17K）
- TOP Skill：`compliance.audit` 4218 居首（合规相关访问 / 平台主动审计），`request.status.query` 3104 第二
- 资源池利用率：计算 41% / AI 27% / 网络 18% / 数据库 34% — 都在健康区间
- 拒绝率 6.3%（显示在橙色提示里，未到阈值）

他注意到右下「**调整配额**」按钮 — 这是平台管理员独有的写操作。点击后二次确认弹窗说明「调整资源池配额会触发滚动重启 + audit_event」。他确认环境健康，本次不调整。

**第 4 步：旁证 — 切换其他角色看「调整配额」是否消失**

为了验证 K10 ACL 真的生效，他把右上角色临时切到「厅局领导」再回到 `/ops` — **「调整配额」按钮被替换为提示「配额调整仅平台管理员可见 — K10 ACL」**。切到「提供方操作员」也一样。完美对齐 baseline §3.1 K10 三类角色 + Skill 级 ACL。

## 验证什么

- ☐ 合规审计回溯的检索条件 4 维（时间 / 主体 / 数据集 / 操作）是否覆盖业务方真实问法
- ☐ 「retry-ok」事件作为 D4 下半的可视化证据，是否能让用户理解「业务不阻塞 + 上链最终一致」
- ☐ 上链一致性校验是「事前 lint」还是「事后核验」？原型展示的是事后核验（K9 兜底）
- ☐ Skill 注册审批流（pending → approved/rejected + 驳回理由公开）是否对外部开发者足够透明
- ☐ 已驳回的 `edu.enroll.bulk_update` 案例是否能让 reviewer 直观看到「§7.5 + N6 + 最小 API 表面」三条原则在 Skill 治理上的统一落地
- ☐ 平台运营面板与 K12 大屏的「受众分层」边界是否清晰（reviewer 是否能区分两者各自的取舍）
- ☐ 「调整配额」按钮按角色显隐 — K10 ACL 在跨页面的一致性是否过关
