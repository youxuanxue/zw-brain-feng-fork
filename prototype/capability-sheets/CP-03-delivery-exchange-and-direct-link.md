# CP-03｜Delivery, Exchange & Direct Link

## 1. 业务目标与边界

**目标**：把“审批通过之后到底有没有交付成功、为什么还在等、为什么被熔断”讲清楚，让交付链路既可追踪、又可解释、还能保持合规优先。

**解决的 Job**：
- 自动创建并跟踪交付任务
- 区分正常交付、外部通道波动、内部故障与主动熔断
- 提供回执、对账与下一步处理建议
- 支撑大屏的只读态势展示与异常钻取

**明确不做**：
- 不把交付链路伪装成“点一下就成功”
- 不用 AI 掩盖失败事实
- 不在大屏侧重复维护另一套交付状态机

## 2. 覆盖的主旅程环节与页面

- 主旅程：S6 / S7 / S9
- 页面：P4 交付 / 交换 / 直达、K12 指挥中心大屏
- 定位：主旅程交付闭环能力

## 3. 归属判定 / Ownership boundary

CP-03 以平台内建为主。交付任务、回执确认、恢复动作和熔断状态都直接影响主旅程事实状态，必须由平台掌握写权与审计责任。即使没有状态解释、恢复建议或外部通道适配增强，平台仍应能展示任务状态、回执字段、异常类型并允许人工确认后的恢复动作。

### 3.1 平台内建能力
- `delivery.create-task`
- `delivery.track-progress`
- `delivery.reconcile-receipt`
- `delivery.trigger-recovery`
- 任务列表、时间线、回执字段、异常状态与恢复入口

### 3.2 外部 ANP 可建设的辅助能力
- `delivery.interpret-status`
- 外部通道适配
- 恢复建议与波动解释

### 3.3 明确禁止外部包拥有的范围
- 不得直接确认交付成功或写入最终回执
- 不得绕过平台熔断与审计门禁推进任务状态
- 不得把外部通道响应静默包装成平台成功结果
- 不得让任务跟踪、回执对账或恢复触发依赖外部解释能力是否在线

## 4. 统一 Capability 契约要求

### 4.1 输入 / 输出要点
- 输入：申请结果、交付渠道、任务标识、回执信息、操作者身份
- 输出：交付任务状态、回执、异常分类、解释文本、后续建议、必要的熔断原因

### 4.2 Side effects 与边界
- 任务创建、恢复重试、回执确认属于 `confirm-required` + `write-with-audit`
- 状态解释与读侧钻取为 `read-mostly`
- AI 只负责解释状态，不得把失败包装成成功

### 4.3 ACL / tenant / audit
- 不同角色看到的交付明细应按租户和职责裁剪
- 所有任务状态变化、回执写入和恢复动作必须产生审计事件
- 若关键审计失败，动作必须阻断

### 4.4 回执与外部依赖
- 必须显式支持交付回执与对账结果
- 可依赖国家平台、集团平台或其他外部交换通道
- 外部依赖波动必须被建模为显式状态，而不是静默失败
- 即使没有外部解释与建议能力，平台仍需保留任务跟踪、回执查询与恢复动作的 baseline 路径

## 5. 五消费面映射

- **WebUI**：P4 显示任务队列、时间线、回执、异常解释；K12 只读展示 KPI、异常与责任链
- **REST**：暴露交付任务查询、回执确认、异常解释和恢复动作接口
- **CLI**：支持任务查询、回执检查、恢复触发与解释输出
- **MCP**：暴露为交付类状态查询、解释与运维辅助 tool
- **A2A**：暴露为 agent 可调用的交付状态检查与恢复建议 action；正式任务写动作回到平台内建能力

要求：同一任务状态、回执语义、熔断原因和恢复规则在五消费面保持一致。

## 6. ANP 外部建设要求

- 适合外部建设的原因：回执适配、状态解释、外部通道对接与恢复策略具备较强模块化特征
- 与主仓边界：主仓保留主旅程事实源、状态机和合规门禁；外部包只提供统一契约下的适配、解释与建议能力
- 回注册前需准备：manifest、任务状态 schema、回执 schema、side effects 说明、外部依赖列表、熔断与恢复策略说明

## 7. 负面流与验收口径

### 7.1 负面流
- 外部通道波动时必须保持中间态与可追踪性，不得直接宣称成功或失败
- 审计写入失败时必须阻断状态推进，并显式说明原因

### 7.2 设计验收标准
- 用户能读懂“正常交付 / 外部通道波动 / 主动熔断”的区别
- 回执、时间线、下一步建议形成一个完整闭环
- 即使外部辅助失效，交付任务、回执和恢复动作仍可独立完成
- 大屏只读消费事实，不重新长出新的业务逻辑

### 7.3 回注册核对项
- 是否定义了清晰的任务状态与回执结构
- 是否明确了熔断、恢复和责任边界
- 是否保证交付写动作伴随审计记录
