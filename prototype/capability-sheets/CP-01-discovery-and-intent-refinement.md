# CP-01｜Discovery & Intent Refinement

## 1. 业务目标与边界

**目标**：帮助申请方在最短路径上完成“我想要什么数据、为什么要、下一步去哪”的判断，把自然语言意图收敛成可检索、可申请的结构化上下文。

**解决的 Job**：
- 快速发现与当前任务最相关的数据资源
- 识别申请前仍缺哪些关键信息
- 用最少跳转进入后续申请流

**明确不做**：
- 不直接提交申请
- 不替用户决定最终资源选择
- 不长成独立搜索平台或标准平台

## 2. 覆盖的主旅程环节与页面

- 主旅程：S1 / S2 / S3
- 页面：P1 工作台、P2 资源发现、P7 共享专区
- 定位：主旅程入口能力

## 3. 归属判定 / Ownership boundary

CP-01 不是“把发现能力整体外包”的意思。平台自身必须先提供可独立闭环的 discovery baseline：用户至少可以通过目录浏览、条件筛选、资源详情和进入申请流按钮完成发现与判断；外部 ANP 只负责把这条路径变得更快、更自然。

### 3.1 平台内建能力
- 目录浏览、条件筛选与资源详情查看
- 共享专区主题聚合入口与进入申请流按钮
- 目录与资源的正式可见边界
- 基于租户 / 部门 / 角色的 ACL 过滤
- 与主旅程一致的审计记录与页面组织

### 3.2 外部 ANP 可建设的辅助能力
- `intent.parse-and-refine`
- 检索增强 / 结果重排
- `catalog.recommend-next-step`
- `zone.topic-projection`（仅作主题聚合建议或投影增强）

### 3.3 明确禁止外部包拥有的范围
- 不得直接提交申请或推进申请状态
- 不得让“能否发现资源 / 能否进入申请流”依赖外部辅助是否在线
- 不得绕过平台 ACL 暴露高权限资源详情
- 不得把推荐结果伪装成平台最终判定

## 4. 统一 Capability 契约要求

### 4.1 输入 / 输出要点
- 输入：自然语言需求、上下文约束、租户信息、当前角色
- 输出：解析出的主题 / 时间 / 用途 / 缺失项、候选资源、推荐理由、下一步建议

### 4.2 Side effects 与边界
- 默认 `read-only`
- 可以记录查询与推荐行为审计，但不写主业务状态
- AI 只能追问与解释，不能直接生成“已提交申请”结果

### 4.3 ACL / tenant / audit
- 按租户、部门、角色过滤可见目录与资源
- 审计等级以查询与推荐记录为主
- 不暴露超出当前权限边界的资源详情

### 4.4 回执与外部依赖
- 不要求业务回执
- 可依赖外部目录索引、推荐服务或历史行为投影
- 即使外部辅助不可用，平台仍需保留目录浏览、条件筛选、资源详情查看与进入申请流的 baseline 路径

## 5. 五消费面映射

- **WebUI**：P1 / P2 内联显示解析结果、推荐理由、缺口追问、下一步建议
- **REST**：暴露统一检索与意图解析接口，供页面与集成方调用
- **CLI**：支持快速检索、条件补全和下一步建议输出
- **MCP**：暴露为检索 / 解析 / 推荐类 tool 或 resource
- **A2A**：暴露为可被外部 agent 调用的发现类 action

要求：五消费面共享同一检索与意图收敛语义，不允许页面是一套推荐逻辑、MCP 是另一套推荐逻辑。

## 6. ANP 外部建设要求

- 适合外部建设的原因：意图解析、检索增强、推荐排序与下一步建议属于高复用、可独立迭代能力
- 与主仓边界：主仓保留 discovery baseline、页面组织、主旅程编排与合规边界；外部包只提供统一契约下的解析 / 重排 / 推荐增强能力
- 回注册前需准备：manifest、输入输出 schema、示例请求、ACL 说明、推荐理由字段、审计声明

## 7. 负面流与验收口径

### 7.1 负面流
- 信息不足时只能返回缺失项与追问，不得直接进入申请提交态
- 权限不足时只能返回受限结果或拒绝说明，不得泄露高权限资源详情

### 7.2 设计验收标准
- 能清楚区分“已识别”和“仍缺失”的上下文
- 能在不替代结构化页面的前提下，把用户导向申请流
- 即使外部辅助失效，用户仍可通过目录浏览、筛选和详情页完成发现与判断
- 推荐理由可读、可信，不像一块泛泛而谈的 AI 大提示卡

### 7.3 回注册核对项
- 是否明确 `read-only`
- 是否明确租户与角色过滤要求
- 是否提供统一输出字段，供 P2、CLI、MCP、A2A 一致消费
