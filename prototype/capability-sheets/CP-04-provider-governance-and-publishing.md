# CP-04｜Provider Governance & Publishing

## 1. 业务目标与边界

**目标**：让提供方在同一治理面上完成目录、资源、服务的持续治理与发布，不再在多个后台岛之间来回切换。

**解决的 Job**：
- 识别今天最该优先治理的目录、资源或服务
- 完成发布、更新、下线、说明修正等治理动作
- 为后续共享专区与主旅程提供稳定供给面

**明确不做**：
- 不把治理面扩张成完整运营平台
- 不让 AI 直接替用户执行发布或下线动作
- 不重新照搬旧平台的烟囱式治理子系统

## 2. 覆盖的主旅程环节与页面

- 主旅程：为 S2 / S3 / S10 提供供给侧支撑
- 页面：P5 提供方管理、P7 共享专区
- 定位：供给侧治理支撑能力

## 3. 归属判定 / Ownership boundary

CP-04 以平台内建为主。目录、资源、服务的治理与发布直接决定哪些资产能正式被发现、申请和投影，属于平台供给侧主状态机。即使没有优先级建议、发布前检查或主题投影建议，提供方仍应能在同一治理面完成发布、下线、说明修正等核心动作。

### 3.1 平台内建能力
- `catalog.manage-entry`
- `resource.manage-asset`
- `service.publish-or-suspend`
- `zone.publish-topic-projection`
- 治理状态展示、发布动作区、说明变更入口与共享专区正式投影控制

### 3.2 外部 ANP 可建设的辅助能力
- `provider.prioritize-governance-work`
- 目录校验与发布前检查
- 主题投影建议

### 3.3 明确禁止外部包拥有的范围
- 不得直接发布 / 下线目录、资源或服务
- 不得绕过治理状态把未发布内容投影到共享专区
- 不得替提供方写入最终治理说明与发布结果
- 不得让供给侧核心治理动作依赖外部建议能力是否在线

## 4. 统一 Capability 契约要求

### 4.1 输入 / 输出要点
- 输入：目录标识、资源标识、服务状态、治理说明、操作者身份
- 输出：治理建议、目录 / 资源 / 服务状态、发布结果、可见性范围

### 4.2 Side effects 与边界
- 治理建议类能力为 `read-mostly`
- 发布、下线、说明变更类能力为 `confirm-required` + `write-with-audit`
- AI 负责排序和草拟，不负责最终执行

### 4.3 ACL / tenant / audit
- 治理动作必须按提供方角色、租户与资源归属控制权限
- 发布、下线、变更必须留痕并可回放
- 共享专区的主题投影不能绕开治理状态直接暴露未发布内容

### 4.4 回执与外部依赖
- 必须支持治理动作结果和状态更新时间回显
- 可依赖外部目录底座、资源目录索引或 legacy 只读映射
- 即使没有外部建议与检查能力，平台仍需保留完整治理、发布和下线的 baseline 路径

## 5. 五消费面映射

- **WebUI**：P5 显示治理优先级、三段式治理区、状态与说明；P7 消费经过治理后的主题投影
- **REST**：暴露目录、资源、服务治理动作和查询接口
- **CLI**：支持批量治理、状态变更和发布操作
- **MCP**：暴露为治理检查、优先级建议和发布前校验 tool
- **A2A**：暴露为供给侧治理辅助与注册前整理 action；正式发布语义回到平台内建能力

要求：所有消费面共享同一治理状态、发布语义和权限边界。

## 6. ANP 外部建设要求

- 适合外部建设的原因：治理建议、目录校验、发布前检查、主题投影建议可独立迭代
- 与主仓边界：主仓保留页面、状态机与最终权限控制；外部包只提供统一契约下的治理辅助与校验能力
- 回注册前需准备：manifest、治理状态 schema、发布动作 side effects 说明、ACL 说明、主题投影输出结构

## 7. 负面流与验收口径

### 7.1 负面流
- 未发布或状态异常的目录 / 资源不得直接出现在共享专区正式投影中
- 提供方无权限操作的资源或服务必须被拒绝并留痕

### 7.2 设计验收标准
- 提供方能在一个治理面里完成主任务，而不是依赖多个后台模块
- AI 建议明显提升优先级判断，但不替代治理动作确认
- 即使外部辅助失效，供给侧治理与发布主任务仍可独立完成
- P7 的主题聚合清楚来自已治理资产，而不是另起一套状态机

### 7.3 回注册核对项
- 是否明确供给侧治理状态和发布边界
- 是否保证主题投影只消费已发布、可见的资产
- 是否清楚定义了需要人工确认的治理动作
