# CP-06｜Integration Admin & Package Registry

## 1. 业务目标与边界

**目标**：让平台管理员在一个纤薄后台里审核、注册、暴露和治理外部能力包，使新增能力走统一回注册路径，而不是继续在主仓库内膨胀为新模块。

**解决的 Job**：
- 审核外部 ANP 构建的能力包是否满足统一 Capability 契约
- 检查 schema、ACL、side effects、审计声明和暴露面
- 控制能力包版本、租户策略和可见范围

**明确不做**：
- 不把接入中心做成普通用户的主入口
- 不把 registry 演化成一个大而全的能力市场产品
- 不允许 AI 越权批准或驳回能力包

## 2. 覆盖的主旅程环节与页面

- 主旅程：S10
- 页面：P8 平台接入与扩展中心
- 定位：管理员后台支撑能力

## 3. 归属判定 / Ownership boundary

CP-06 以平台内建为主。注册事实源、暴露矩阵和 tenant policy 的正式生效动作属于平台控制面本身，不应被外部能力包接管。即使没有 manifest 预检查、schema 检查或审核意见草稿，管理员仍应能通过控制面字段、缺项核对和显式确认完成审核、注册与策略生效。

### 3.1 平台内建能力
- `package.register-version`
- `package.configure-exposure`
- `package.apply-tenant-policy`
- package 详情查看、缺项核对、暴露矩阵配置与租户策略生效动作

### 3.2 外部 ANP 可建设的辅助能力
- `package.validate-manifest`
- `package.review-and-comment`
- schema / ACL / side effects 预检查

### 3.3 明确禁止外部包拥有的范围
- 不得直接批准 / 退回 / 驳回包注册
- 不得写入最终 package / version / exposure / tenant policy 生效结果
- 不得为五消费面分别定义分叉注册语义
- 不得让审核、注册或策略生效依赖外部预检查能力是否在线

## 4. 统一 Capability 契约要求

### 4.1 输入 / 输出要点
- 输入：package manifest、schema、版本信息、ACL、side effects、暴露面、租户策略、审核意见
- 输出：校验结果、缺项清单、审核建议、注册结果、版本记录、暴露矩阵、租户策略结果

### 4.2 Side effects 与边界
- 校验和建议为 `read-mostly`
- 审核决定、注册版本、配置暴露与租户策略为 `confirm-required` + `write-with-audit`
- AI 只能指出缺项并草拟审核意见，不得自动批准 / 退回 / 驳回

### 4.3 ACL / tenant / audit
- 仅管理员可执行注册治理动作
- 所有审核和注册动作都必须留下可追踪审计记录
- 租户暴露策略必须在契约层被显式声明，不能靠口头约定

### 4.4 回执与外部依赖
- 必须保留 package 版本、审核意见与最终注册结果
- 可依赖外部 ANP 平台、镜像仓、包仓或能力目录底座
- 即使没有外部预检查与审核草稿，平台仍需保留完整审核、注册与策略生效的 baseline 路径

## 5. 五消费面映射

- **WebUI**：P8 展示能力包详情、缺项清单、审核意见、暴露矩阵和策略配置
- **REST**：暴露包校验、审核、注册、策略配置接口
- **CLI**：支持批量校验、版本注册与策略查看
- **MCP**：暴露为包校验、注册前检查和治理辅助 tool
- **A2A**：暴露为可被治理 agent 调用的审查辅助 action；正式注册语义回到平台内建能力

要求：无论从哪个消费面发起治理动作，都必须回到同一 package 与 version 事实源，不允许分叉注册语义。

## 6. ANP 外部建设要求

- 适合外部建设的原因：manifest 校验、schema 检查、暴露面检查、审核建议生成可以作为独立能力化组件
- 与主仓边界：主仓保留管理员后台、最终审批与统一注册事实源；外部包只提供统一契约下的预检查、校验和建议能力
- 回注册前需准备：manifest、版本号、输入输出 schema、side effects 声明、ACL / tenant policy、暴露面映射、示例调用、审计声明

## 7. 负面流与验收口径

### 7.1 负面流
- manifest 或 schema 缺项时，包只能停留在待补件态，不得进入可注册态
- 暴露面设计与统一 Capability 契约不一致时，注册必须被驳回

### 7.2 设计验收标准
- 管理员能快速看清哪个包最接近可发布、哪个仍需补件、哪个应被驳回
- 控制面字段保持最小可用，不膨胀成另一套平台产品
- 即使外部辅助失效，管理员仍可通过控制面完成审核与注册
- AI 审核助手始终处于“辅助审核”位置，而不是代替管理员决策

### 7.3 回注册核对项
- 是否明确 package / version / exposure / tenant policy 的最小元数据
- 是否明确哪些治理动作需要人工确认
- 是否保证统一 Capability 契约先于各消费面投影
