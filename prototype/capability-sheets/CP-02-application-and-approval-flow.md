# CP-02｜Application & Approval Flow

## 1. 业务目标与边界

**目标**：把申请、补件、审批、意见、跟踪回执放回同一条强状态链路里，让 AI 负责草拟与解释，让人保留最终确认权。

**解决的 Job**：
- 基于已发现资源快速发起申请
- 在边界不清时补件或退回补正
- 让审批人看到理由、风险、影响预估和后续链路
- 让申请方实时跟踪状态、回执和下一动作

**明确不做**：
- 不自动替申请人提交
- 不自动替审批人通过或驳回
- 不把审批流改造成聊天对话

## 2. 覆盖的主旅程环节与页面

- 主旅程：S4 / S5
- 页面：P3 申请 / 审批 / 跟踪
- 定位：主旅程核心强状态能力

## 3. 归属判定 / Ownership boundary

CP-02 以平台内建为主。因为申请提交、补件、审批决定、状态跟踪都属于主状态机推进与 `write-with-audit` 范围，不能让外部包拥有正式写权。即使没有任何草拟或解释能力，申请人与审批人仍应能通过结构化表单、显式按钮和必填意见完成完整闭环。

### 3.1 平台内建能力
- `application.submit`
- `application.request-supplement`
- `approval.review-and-decide`
- `application.track-status`
- 结构化申请表单、审批动作区、状态时间线与回执展示

### 3.2 外部 ANP 可建设的辅助能力
- `application.draft-from-context`
- 审批意见草稿生成
- 补件建议与状态解释

### 3.3 明确禁止外部包拥有的范围
- 不得直接提交申请
- 不得替审批人写入最终通过 / 驳回 / 退回决定
- 不得伪造申请时间线、回执或审计结果
- 不得让申请发起或审批完成依赖外部草拟能力是否在线

## 4. 统一 Capability 契约要求

### 4.1 输入 / 输出要点
- 输入：申请上下文、资源标识、用途说明、审批意见、补件信息、操作者身份
- 输出：申请单状态、审批建议摘要、人工确认结果、时间线、`audit_id`、必要回执

### 4.2 Side effects 与边界
- `application.submit`、`approval.review-and-decide` 为 `confirm-required` + `write-with-audit`
- `application.track-status` 消费统一事实源，不自造并行状态
- AI 草稿只供参考，不得在未确认情况下写入最终决定

### 4.3 ACL / tenant / audit
- 申请人与审批人的权限模型必须明确区分
- 所有状态变化必须产出审计记录
- 高风险审批动作需要保留意见、时间戳与责任人

### 4.4 回执与外部依赖
- 必须支持状态跟踪与必要回执展示
- 可依赖外部组织、权限、通知等底座，但不在包内复造
- 即使没有外部草拟与解释能力，平台仍需保留完整申请、审批、补件和跟踪的 baseline 路径

## 5. 五消费面映射

- **WebUI**：P3 中展示申请表单草案、审批副驾、状态时间线与回执解释
- **REST**：暴露申请提交、补件、审批、状态查询接口
- **CLI**：支持申请发起、补件提交、状态查询和审批确认
- **MCP**：暴露为申请草拟、状态解释和审批辅助 tool；正式提交与决定必须保留人工确认边界
- **A2A**：暴露为可编排的申请辅助与状态查询 action；正式状态推进回到平台内建能力

要求：五消费面可以有不同交互形态，但申请状态机、审批语义、确认边界和审计规则必须完全一致。

## 6. ANP 外部建设要求

- 适合外部建设的原因：申请草拟、补件建议、审批辅助和状态解释可作为高复用能力独立演进
- 与主仓边界：主仓保留主旅程页面、结构化表单、状态机编排和合规门槛；外部包只提供统一契约下的草拟、辅助判断与状态解释能力
- 回注册前需准备：manifest、输入输出 schema、side effects 声明、ACL 模型、审计与确认边界说明

## 7. 负面流与验收口径

### 7.1 负面流
- 信息不足时，申请只能停留在草稿或待补充态，不得直接提交
- 审批人退回补正或驳回时，系统必须明确保留 reason、decision 和时间线

### 7.2 设计验收标准
- AI 草拟和审批建议始终清楚地位于“辅助”位置
- 用户能读懂状态时间线与回执，而不是只看到一个结果标签
- 即使外部辅助失效，申请与审批动作也能通过结构化页面独立完成
- 申请与审批动作都保留清楚的人为确认边界

### 7.3 回注册核对项
- 是否明确哪些 Capability 需要 `confirm-required`
- 是否明确申请人与审批人的 ACL 差异
- 是否保证所有状态推进都伴随审计记录
